# Purpose

Дать команде 10–12 человек внутри крупной компании единую open source систему, в которой
ведутся проекты и задачи сотрудников, база клиентов и воронка продаж, со сквозной связью
**«клиент → сделка → проект → задача»** (ТЗ §1).

Конечная цель продукта — проверить гипотезу: задачи с досками и воронка продаж в одной
системе закрывают сценарий, ради которого в корпорации держат отдельные таск-трекер и CRM
(ADR-0002). Корпоративная обвязка (SSO, мультикомандность) в пилоте не реализуется, но модель
данных и проверка учётных данных закладываются так, чтобы её можно было добавить без
переписывания (ТЗ §1, §3).

Цель R1 (с v0.16, ADR-0012) — как можно быстрее показать заказчику localhost-прототип
таск-трекера: проекты, задачи, подзадачи, комментарии, личный список и канбан-доску на основе
учётных записей и ролей R1.0. CRM (клиенты, контакты, сделки, воронка) и сквозная связь
«клиент → сделка → проект → задача» делаются в следующей версии продукта, после того как
заказчик одобрит таск-трекер. Тогда же проверяется гипотеза ADR-0002.

# Scope

## Входит в R1 (ТЗ §2 в объёме ADR-0012)

| Блок | Состав |
|---|---|
| Пользователи и роли | Локальные учётные записи, создаёт техадминистратор; 4 роли; вход по логину и паролю; журнал аудита учётных записей, сессий, ролей и передачи владения проектом (ADR-0006 в объёме ADR-0012) |
| Проекты | Название, описание, участники, владелец, передача владения; мягкое удаление без восстановления |
| Задачи | Название, описание, исполнитель, срок, приоритет, статус; подзадачи (1 уровень) с прогрессом; комментарии (простой текст, без упоминаний); мягкое удаление без восстановления |
| Представления | Личный список «мои задачи»; список задач проекта с фильтрами по исполнителю и статусу; канбан-доска с перетаскиванием и ручным порядком карточек; опрос сервера (FR-29) |
| Эксплуатация | Развёртывание `docker compose up`; демо-данные одной командой (без сделок); ротация логов |

Приёмка R1 проходит по этому объёму (решение владельца продукта по Q-M2, OI-119). Пункты ТЗ
§6 п.8 (сделка), п.9 (связь сделки с проектом), п.11 (экспорт) и п.12 (восстановление из
резервной копии) в приёмку R1 не входят и переходят в следующую версию (ADR-0012). Пункты ТЗ
§6 п.7 (изоляция CRM) и п.10 (производительность) тоже опираются на отложенные функции
[ВОПРОС ВЛАДЕЛЬЦУ: входят ли они в приёмку R1 и в каком виде — OI-125, OI-126].

Решение владельца продукта от 2026-10-15. Номера требований сохранены, тексты в редакции v0.15

## Следующий релиз R2 — не делать (ТЗ §2)
Учёт времени, повторяющиеся задачи, обращения клиентов через веб-форму и email,
отчёты и дашборды. Кроме того, решением по OI-25 в R2 перенесены клиенты-физлица.

## Вне рамок (ТЗ §2, ADR-0002)
Диаграмма Ганта, зависимости задач, маршруты согласования, Telegram/VK/телефония, SSO,
SCIM, цели (OKR), мобильное приложение, встроенный мессенджер, WebSocket,
мультикомандность (несколько рабочих пространств), валюты кроме RUB, загрузка реальных ПДн,
антивирусная проверка вложений (OI-21), фоновый планировщик задач (OI-12).
Решениями v0.14 вне рамок R1 также: связь «задача → цель» в модели данных (OI-2);
несколько ролей у одного пользователя (OI-6); уведомления вне приложения — email, push
(ADR-0008); аудит входа и неудачных попыток входа (ADR-0006); несколько воронок и доска
сделок с перетаскиванием (OI-28, OI-91); настройка часового пояса (OI-62); экспорт и импорт
через HTTP API и импорт со слиянием в непустую систему (ADR-0010); поиск по контактам
(OI-32); настраиваемые «системные настройки», кроме учётных записей и ролей (OI-34).

- **C-5 Данные:** только синтетические клиенты и сотрудники.

# Functional Requirements

## FR-A. Аутентификация и учётные записи

- **FR-1:** Система ДОЛЖНА аутентифицировать пользователя по логину и паролю (ТЗ §3).
- **FR-73:** Логин ДОЛЖЕН соответствовать шаблону `^[a-z0-9][a-z0-9._-]{2,63}$` (3–64
  символа: строчные латинские буквы, цифры, точка, подчёркивание, дефис; первый символ —
  буква или цифра). Регистр букв в логине не различается: логин, введённый заглавными
  буквами, приводится к строчным до проверки шаблона; при входе логин принимается в любом
  регистре; логины, отличающиеся только регистром, считаются одинаковыми. Логин уникален;
  создание учётной записи с логином, не соответствующим шаблону или уже занятым, ДОЛЖНО
  отклоняться с 422. Последнее правило (упоминание `@логин` распознаётся по тому же шаблону
  без учёта регистра, FR-71, OI-112) отложено (следующая версия) вместе с FR-71, ADR-0012
  (SC-6).
- **FR-2:** Пароль ДОЛЖЕН храниться только в виде хеша Argon2id (ТЗ §3). Параметры хеша
  задаются в конфигурации так, чтобы хеширование занимало 100–500 мс на стенде C-2 (ADR-0004).
- **FR-3:** Проверка учётных данных ДОЛЖНА быть изолирована за интерфейсом провайдера
  аутентификации так, чтобы добавление OIDC-провайдера не требовало изменений в остальной
  системе (ТЗ §3). OIDC в R1 не реализуется.
- **FR-4:** Учётные записи ДОЛЖНЫ создаваться только пользователем с правом «Создание и
  блокировка учётных записей» (техадмин, смешанная роль) (ТЗ §4). Самостоятельной
  регистрации нет. Учётная запись создаётся без роли (FR-66); роль назначается отдельным
  действием по FR-12. Создание и назначение роли — два действия и две записи журнала аудита
  (FR-41) (OI-117).
- **FR-5:** Пользователь с тем же правом ДОЛЖЕН иметь возможность заблокировать учётную
  запись; заблокированный пользователь НЕ ДОЛЖЕН проходить аутентификацию, а все его
  активные сессии ДОЛЖНЫ завершаться в момент блокировки (ADR-0004). Ответ на попытку входа
  заблокированного пользователя ДОЛЖЕН совпадать по коду и телу с ответом на неверный пароль
  (FR-61, OI-88). Задачи
  заблокированного пользователя ДОЛЖНЫ сохраняться; бизнес-администратор (и СМ, BR-1)
  ДОЛЖЕН иметь возможность переназначить их другому сотруднику (OI-5). Исполнитель задач
  при блокировке НЕ снимается автоматически: он остаётся до явного переназначения, и такие
  задачи находятся фильтром по исполнителю в списке задач проекта (FR-27). Задачи
  переназначает БА только в своём проекте (где он владелец, FR-19) или СМ в
  любом проекте, где участвует; СМ может сначала добавить себя в проект (FR-15) — BR-1 не
  расширяется (OI-53, OI-71, ADR-0009). Заблокированного пользователя нельзя назначить
  получателем (FR-70). Блокировка себя последним обладателем права — FR-69.
  Часть про сделки (сделки сохраняются и находятся фильтром по ответственному, их переназначают
  БА и СМ с правом «CRM: создание и изменение») отложена (следующая версия) вместе с CRM,
  ADR-0012 (SC-1).
- **FR-5a:** Пользователь с правом «Создание и блокировка учётных записей» (ТА, СМ) ДОЛЖЕН
  иметь возможность разблокировать учётную запись; после разблокировки вход проходит, ранее
  завершённые сессии не восстанавливаются (OI-53).
- **FR-6:** При первом запуске на чистой установке система ДОЛЖНА сама сгенерировать
  секретный ключ приложения и учётную запись первого техадминистратора со случайным
  паролем. Пароль записывается в файл в томе данных, доступный на чтение только оператору
  (владельцу тома), и НЕ ДОЛЖЕН появляться в логах (FR-57). При первом входе система ДОЛЖНА
  требовать смены пароля; после смены файл ДОЛЖЕН удаляться. Повторный запуск не создаёт
  второго техадминистратора, не меняет ключ и не пересоздаёт файл (OI-4, OI-46, OI-49).
- **FR-6a:** Порт базы данных НЕ ДОЛЖЕН публиковаться за пределы внутренней сети
  контейнеров (OI-46). Поставляемая конфигурация, которую поднимает `docker compose up` без
  дополнительных параметров, НЕ ДОЛЖНА публиковать порт 5432 и НЕ ДОЛЖНА отключать флаг
  `Secure` (FR-58). Конфигурация для разработки подключается только явно (отдельным файлом
  через `-f` или профилем). Файл `docker-compose.override.yml`, который Docker Compose
  подхватывает автоматически, в репозитории запрещён (OI-70).
- **FR-7:** Запрос без действующей аутентификации к любому эндпоинту, кроме входа и
  проверки живости, ДОЛЖЕН получать 401. Исключение — синтаксически невалидный JSON в теле
  запроса. На него любой эндпоинт с телом, с сессией и без неё, ДОЛЖЕН отвечать 400 с кодом
  `bad_request` до проверки аутентификации и прав, без бизнес-логики. Фрагменты тела в
  ответ не попадают (FR-57). Синтаксически валидный JSON с неверными полями по-прежнему
  получает сначала 401/403 и только потом 422 (решение владельца по Д-7, OI-121, ADR-0012,
  SC-21).

Пароли и сессии — ADR-0004 (OI-39):

- **FR-52:** Пароль ДОЛЖЕН содержать не менее 12 символов; правил на состав символов нет.
  Более короткий пароль ДОЛЖЕН отклоняться с 422.
- **FR-53:** Пароль, совпадающий с одним из 10 000 самых частых паролей, ДОЛЖЕН отклоняться
  при установке с 422. Список поставляется вместе с системой (NFR-4). Совпадение — точное, с
  учётом регистра: пароль, отличающийся от записи списка хотя бы регистром одной буквы,
  частым не считается (OI-111).
- **FR-54:** Принудительной смены пароля по расписанию НЕТ.
- **FR-55:** Учётная запись, созданная техадминистратором, получает одноразовый пароль.
  После входа с ним система ДОЛЖНА отклонять любые действия, кроме установки нового пароля
  и выхода из системы (FR-60), пока новый пароль не задан (OI-109).
  Одноразовый пароль задаёт администратор в запросе на создание учётной записи или сброс
  пароля (FR-65); интерфейс генерирует случайный пароль на стороне клиента и показывает его
  администратору. Одноразовый пароль подчиняется FR-52 и FR-53 (иначе 422). Сервер
  одноразовый пароль не генерирует и ни в каком ответе API его не возвращает; FR-57
  действует без исключений (OI-108).
- **FR-56:** Пользователь ДОЛЖЕН иметь возможность сменить свой пароль. Смена пароля
  ДОЛЖНА завершать все остальные сессии этого пользователя.
- **FR-57:** Пароль ни в каком виде НЕ ДОЛЖЕН попадать в логи, трассировки ошибок и ответы API.
- **FR-58:** Сессия ДОЛЖНА храниться на сервере; клиент получает только её идентификатор в
  cookie с флагами `HttpOnly`, `SameSite=Lax`, `Secure`. Флаг `Secure` отключается только
  явной настройкой окружения для локальной разработки вне поставляемой конфигурации
  `docker compose` (FR-63).
- **FR-59:** Сессия ДОЛЖНА становиться недействительной после 8 часов без активности и не
  позднее 7 суток с момента входа. Фоновые запросы опроса (FR-29), отправляемые интерфейсом
  без действия пользователя, НЕ ДОЛЖНЫ продлевать 8-часовой тайм-аут неактивности (OI-86).
- **FR-60:** Выход из системы ДОЛЖЕН удалять сессию на сервере.
- **FR-61:** Ответы на вход с несуществующим логином и с неверным паролем ДОЛЖНЫ совпадать
  по коду и телу. После 5 неудачных попыток подряд вход по этому логину ДОЛЖЕН отклоняться
  в течение 15 минут, в том числе с верным паролем; ответ при этом идентичен ответу на
  неверный пароль (код и тело). Через 15 минут вход снова проходит (OI-50).
- **FR-62:** Пользователь с правом «Создание и блокировка учётных записей» (ТА, СМ) ДОЛЖЕН
  иметь возможность завершить все сессии любого пользователя; после этого запросы с этими
  сессиями получают 401 (ADR-0004).
- **FR-65:** Пользователь с правом «Создание и блокировка учётных записей» (ТА, СМ) ДОЛЖЕН
  иметь возможность сбросить пароль пользователя: администратор задаёт новый одноразовый
  пароль по правилам FR-55, все сессии пользователя завершаются, прежний пароль перестаёт
  действовать (ADR-0004, OI-108).
- **FR-63:** Поставляемая конфигурация ДОЛЖНА принимать подключения пользователей только
  по HTTPS (TLS 1.2 и выше); запрос по http ДОЛЖЕН перенаправляться на HTTPS и не получать
  данных. Оператор может подключить свой сертификат; если сертификата нет, при первом
  запуске генерируется самоподписанный (без доступа в интернет, без правки кода) (OI-51).
- **FR-64:** Команда загрузки демо-данных (FR-49) ДОЛЖНА создавать каждому
  демо-пользователю уникальный случайный пароль, соответствующий FR-52 и FR-53, и
  записывать пары «логин — пароль» в файл в томе данных, доступный на чтение только
  оператору. Пароли НЕ ДОЛЖНЫ попадать в логи и вывод команды (FR-57). Демо-пароли —
  одноразовые: при первом входе требуется смена (FR-55). В репозитории общих или
  известных демо-паролей нет (OI-48).

## FR-B. Роли и права (ТЗ §4)

- **FR-8:** Система ДОЛЖНА поддерживать 4 роли: техадминистратор, бизнес-администратор,
  смешанная, пользователь. Роль назначается в рамках рабочего пространства.
  Роль «Смешанная» сохраняется с правами по матрице ТЗ §4; связанный риск зафиксирован в
  ADR-0003 (OI-8). Смешанная роль = ТА + БА; при расхождении действует матрица ТЗ §4,
  в частности СМ может удалить любой проект (OI-52). Права СМ на задачи и комментарии
  действуют в проектах, где СМ участвует; добавить себя СМ может в любой проект (FR-15,
  OI-71, OI-72, ADR-0009).
- **FR-66:** У пользователя в рабочем пространстве ДОЛЖНО быть не более одной роли (OI-6).
  Допустимо состояние «без роли»: сразу после создания учётной записи и после снятия роли.
  Пользователю без роли разрешены только вход, выход и смена своего пароля (включая
  обязательную смену по FR-55); любой другой запрос ДОЛЖЕН отклоняться с 403 (OI-75).
  Назначение роли пользователю, у которого роль уже есть, заменяет её.
- **FR-9:** Права ДОЛЖНЫ соответствовать матрице ТЗ §4 (воспроизведена в Business Rules,
  BR-1) с уточнениями ADR-0009 (BR-11). Любое действие, не разрешённое матрицей, ДОЛЖНО
  отклоняться с 403; исключения — 404 по FR-45a, 409 для архивного проекта (FR-14b), 413 для
  вложения больше 10 МБ (FR-24), 422 для
  недопустимого получателя (FR-70) и для защиты последнего администратора (FR-69).
  Исключения 409 и 413 отложены (следующая версия) вместе с FR-14b и FR-24, ADR-0012 (SC-3,
  SC-5). В R1 таких ответов нет.
- **FR-10:** Все проверки прав ДОЛЖНЫ выполняться на сервере; скрытие элементов
  интерфейса не считается защитой (ТЗ §4).
- **FR-11:** Отказ по правам ДОЛЖЕН возвращаться и при прямом обращении к ресурсу по
  идентификатору, а не только в списках (ТЗ §6 п.7).
- **FR-12:** Назначение, смена и снятие любой из 4 ролей ДОЛЖНЫ быть доступны техадмину и
  смешанной роли, в том числе в отношении собственной учётной записи; остальным ролям —
  отклоняться с 403 (OI-7, ADR-0003). Ограничения: FR-66 (одна роль), FR-69 (последний
  администратор). Каждое назначение, смена и снятие роли, включая самоназначение,
  записывается в журнал аудита (FR-41, ADR-0006).
- **FR-67:** Назначение, смена и снятие роли ДОЛЖНЫ действовать со следующего запроса
  пользователя, без повторного входа: права НЕ кешируются в сессии (OI-76).
- **FR-68:** Смена или снятие роли НЕ ДОЛЖНЫ менять владение проектами, членство в
  проектах и исполнителей задач. Права пользователя определяет его
  текущая роль. Такие записи находят и переназначают БА и СМ так же, как после блокировки
  (FR-5) (OI-65). Часть про ответственных за сделки отложена (следующая версия) вместе с CRM,
  ADR-0012 (SC-1).
- **FR-69:** Последний активный (незаблокированный) обладатель права «Создание и блокировка
  учётных записей» НЕ ДОЛЖЕН иметь возможности снять с себя роль, сменить свою роль на роль
  без этого права или заблокировать себя: попытка ДОЛЖНА отклоняться с 422, роль и статус
  учётной записи не меняются (OI-74, OI-97, ADR-0009).
- **FR-70:** Недопустимый получатель (OI-9, OI-77, OI-79, ADR-0009). Если у инициатора есть
  право на действие, но выбранный пользователь не может быть получателем, запрос ДОЛЖЕН
  отклоняться с 422, а не с 403; данные не меняются. Недопустимые получатели:
  - пользователь с ролью ТА — как участник проекта, исполнитель задачи или владелец проекта
    (BR-2);
  - заблокированный пользователь — как исполнитель, участник или владелец;
    ответ — 422 с отдельным кодом ошибки «пользователь заблокирован»;
  - пользователь не той роли (например, владелец проекта с ролью «Пользователь», FR-14a) или
    не участник проекта (FR-20) — 422 с кодом, соответствующим причине;
  - пользователь без роли (FR-66) — как участник, исполнитель или владелец:
    422 как «не та роль» (OI-102). Участник, оставшийся без роли после её снятия, из проекта
    не исключается (FR-68).
  403 сохраняется для случая, когда права на действие нет у самого инициатора.
  Получатель «ответственный за сделку» (FR-33) отложен (следующая версия) вместе с CRM,
  ADR-0012 (SC-1).

## FR-C. Рабочее пространство

- **FR-13:** В R1 существует ровно одно рабочее пространство. Каждая доменная сущность
  ДОЛЖНА принадлежать рабочему пространству, и каждый запрос к данным ДОЛЖЕН
  ограничиваться рабочим пространством текущего пользователя (ТЗ §3, AGENTS.md).

## FR-D. Проекты

- **FR-14:** Система ДОЛЖНА позволять создавать проект с полями: название, описание,
  владелец, участники (ТЗ §2). Поле «статус» (ADR-0005) отложено (следующая версия) вместе с
  FR-14b, ADR-0012 (SC-3). Обязательно только название; проект без
  названия ДОЛЖЕН отклоняться с 422. Название — 1–255 символов, описание — не более
  10 000 символов; более длинное значение (при создании и при изменении) ДОЛЖНО отклоняться
  с 422 (OI-103). Создатель проекта становится его владельцем и участником (OI-10, OI-89).
  Срока у проекта нет (OI-3).
- **FR-14c:** Название и описание проекта меняют: владелец проекта с ролью БА — в своём
  проекте; СМ — в любом проекте, участие не требуется (как архивирование и передачу
  владения, FR-14a, FR-14b; BR-11).
  Попытка остальных, в том числе БА-участника, не являющегося владельцем, ДОЛЖНА отклоняться
  с 403; в архивном проекте — 409 (FR-14b) (OI-105).
  Уточнение v0.16 (SC-2, OI-120): БА, который не владеет проектом, получает 403, даже если
  он автор или исполнитель задач этого проекта. Права на проект дают только владение и роль
  СМ. Архивирование (FR-14b) и ответ 409 отложены (следующая версия), ADR-0012 (SC-3).
- **FR-14b:** Отложено (следующая версия), ADR-0012 (SC-3). Статус проекта и архив — текст в
  разделе «Отложено в следующую версию».
- **FR-14a:** Владение передаётся другому участнику проекта с ролью БА или СМ. Передаёт
  текущий владелец или СМ (OI-10, OI-55); СМ — в любом проекте, участие не требуется (OI-96,
  ADR-0009). Попытка передачи остальными ДОЛЖНА отклоняться с 403. Передача пользователю с ролью «Пользователь» или ТА,
  не участнику или заблокированному ДОЛЖНА отклоняться с 422 (FR-70, OI-79). Если владелец
  заблокирован, нового владельца назначает СМ. Если СМ в пространстве нет, ТА выдаёт роль СМ
  бизнес-сотруднику, а не себе (OI-56, З-5). Это рекомендуемая практика оператора: система
  её не проверяет, самоназначение по FR-12 остаётся возможным и фиксируется в журнале аудита
  (OI-95, ADR-0006, ADR-0009). ТА владельцев
  проектов не назначает: попытка ТА передать владение ДОЛЖНА отклоняться с 403 (BR-2).
  Передача владения пишется в журнал аудита (FR-41). Запись в ленту проекта (FR-38) отложена
  (следующая версия), ADR-0012 (SC-8).
- **FR-15:** Система ДОЛЖНА позволять добавлять участников в проект. Добавляет участников
  владелец проекта с ролью БА — в своём проекте, и СМ — в любом проекте, в том числе себя
  (OI-57, З-6, З-9, ADR-0009). Это намеренное сужение строки «Добавление участников в проект»
  матрицы ТЗ §4: БА, не являющийся владельцем, участников не добавляет — 403.
  Техадминистратор состав проектов не меняет (403). Бизнес-администратор не может добавить в
  проект самого себя (OI-13, OI-55). Добавление ТА или заблокированного пользователя — 422
  (FR-70).
- **FR-15a:** Исключают участников те же роли, что добавляют (OI-55, OI-57). Владельца
  проекта исключить нельзя: попытка ДОЛЖНА отклоняться с 422 и пояснением «сначала
  передайте владение». Участник, не являющийся владельцем, может исключить себя сам;
  интерфейс ДОЛЖЕН запросить подтверждение, так как доступ к проекту теряется.
  При исключении задачи участника остаются в проекте, их исполнитель очищается (null) у
  всех задач и подзадач проекта, где исключённый — исполнитель, в том числе у мягко
  удалённых (Q-7, OI-123, SC-16).
  Исключённый теряет доступ к задачам проекта. Переназначает задачи БА (в своём проекте,
  FR-19) или СМ (в проекте, где участвует) (OI-11, OI-55, ADR-0009).
  Событие ленты «исполнитель снят, участник исключён» отложено (следующая версия) вместе с
  лентой FR-38, ADR-0012 (SC-8, SC-16).
- **FR-16:** Проект удаляется мягко; вместе с ним мягко удаляются его задачи (OI-12,
  FR-25). Удаляет проект его владелец-БА или СМ (любой проект, BR-1, OI-52).
  Восстановление проекта (OI-63) отложено (следующая версия) вместе с корзиной, ADR-0012
  (SC-4). Снятие связи со сделкой при окончательном удалении проекта (FR-25b, OI-83) отложено
  вместе с CRM и окончательным удалением, ADR-0012 (SC-1, SC-4).
- **FR-17:** БА и СМ ДОЛЖНЫ видеть список всех проектов рабочего пространства с полями:
  название, владелец, число задач. «Число задач» — число неудалённых задач верхнего
  уровня, без подзадач (OI-23). Содержимое проекта (задачи, комментарии) доступно только
  участникам; запрос содержимого не участником ДОЛЖЕН
  отклоняться с 403. Роль «Пользователь» видит только проекты, где участвует (OI-13).
  Поле «статус» и фильтр архивных проектов (FR-14b) отложены (следующая версия), ADR-0012
  (SC-3).

## FR-E. Задачи

- **FR-18:** Задача ДОЛЖНА принадлежать проекту и иметь поля: название, описание,
  исполнитель, срок, приоритет, статус (ТЗ §2). Срок необязателен и является
  календарной датой без времени и часового пояса в формате `YYYY-MM-DD`; значение в другом
  формате (в том числе дата-время) или несуществующая дата ДОЛЖНЫ отклоняться с 422. Это
  явное исключение из FR-46 и ТЗ §3 (OI-15, OI-94, ADR-0007). «Сегодня» и «просрочено» для
  срока определяются по календарной дате в Europe/Moscow (FR-27a, OI-62).
  Название задачи обязательно, 1–255 символов; описание — не более 10 000 символов; пустое
  или более длинное название и более длинное описание (при создании и при изменении) ДОЛЖНЫ
  отклоняться с 422 (OI-103).
  Создание задачи в проекте, где инициатор не участвует, ДОЛЖНО отклоняться с 403 (OI-90).
  Отложено (следующая версия), ADR-0012: поле «метки» (FR-18b, SC-7), ответ 409 в архивном
  проекте (FR-14b, SC-3). Правило «сегодня»/«просрочено» применяется вместе с фильтрами по
  сроку FR-27a, которые тоже отложены (SC-10).
- **FR-18a:** Статус задачи ДОЛЖЕН принимать одно из значений фиксированного набора, в
  порядке: «К выполнению», «В работе», «На проверке», «Готово». Новая задача создаётся в
  статусе «К выполнению». Значение вне набора ДОЛЖНО отклоняться с 422. Приоритет задачи —
  одно из двух значений: «Базовый» или «Высокий»; новая задача получает «Базовый», если
  приоритет не указан; другое значение ДОЛЖНО отклоняться с 422 (OI-14). Закрытой
  (завершающий статус) считается задача в статусе «Готово» (OI-14, OI-19). Набор не
  настраивается в R1.
- **FR-18b:** Отложено (следующая версия), ADR-0012 (SC-7). Метки — текст в разделе
  «Отложено в следующую версию».
- **FR-19:** Создание, изменение, удаление и чтение задач ДОЛЖНЫ подчиняться BR-1 и BR-11.
  «Своя задача» — задача, которую сотрудник создал для себя: он её автор и исполнитель.
  «Свой проект» в строке BR-1 «Изменение чужой задачи в своём проекте» — для БА проект, где
  он **владелец** (решение владельца продукта по Q-6 и Q-M1, OI-120, ADR-0012; заменяет З-8 и
  ADR-0009 п.2). Если БА создал в чужом проекте задачу себе или другому или стал исполнителем
  задачи в нём, права «своего проекта» он не получает: права управлять проектом и чужими
  задачами в нём не появляются автоматически. Они задаются вручную — передачей владения
  (FR-14a) или ролью СМ. Признака «со-управляющий проекта» нет: у проекта один владелец, по
  умолчанию — создатель (FR-14). Право «Удаление проекта — только свой» относится только к
  проекту, где сотрудник владелец (OI-17). СМ читает и меняет задачи в проектах, где
  участвует; своя задача в проекте для этого СМ не нужна (OI-71, OI-72, З-9).
  Строка BR-1 «Изменение своей задачи» (БА — да) действует для БА и в проекте, где он не
  владелец [ВОПРОС ВЛАДЕЛЬЦУ: может ли БА — участник, но не владелец — менять и удалять свою
  задачу (автор и исполнитель — он сам) в этом проекте; по умолчанию — да, по матрице ТЗ §4,
  OI-127].
  Удаляет задачу тот, кто может менять все её поля: «Пользователь» — только свою задачу; БА —
  в своём проекте; СМ — в проекте, где участвует. Исполнитель чужой задачи удалить её не
  может — 403 (OI-63, OI-78, OI-80).
- **FR-19b:** Исполнитель задачи, поставленной ему другим, ДОЛЖЕН иметь возможность менять
  её статус (в том числе перетаскиванием на доске) и создавать к ней подзадачи с собой в
  качестве исполнителя. Изменение остальных полей такой задачи (название, описание, срок,
  приоритет, исполнитель) ролью «Пользователь» ДОЛЖНО отклоняться с 403 (OI-54).
  Создание подзадачи подчиняется строке BR-1 «Создание задачи другому» так же, как создание
  задачи. «Пользователь» не может создать подзадачу с другим исполнителем ни к своей задаче,
  ни к задаче, поставленной ему: ответ 403, подзадача не создаётся (SC-20). Поле «метки» в
  этом перечне отложено вместе с FR-18b, ADR-0012 (SC-7).
- **FR-19a:** Менять исполнителя задачи могут только БА и СМ (OI-42, ADR-0009).
  БА — только в своём проекте (FR-19), СМ — в любом проекте, где участвует (OI-71, ADR-0009).
  Попытка «Пользователя» сменить исполнителя любой задачи, включая свою, ДОЛЖНА
  отклоняться с 403 (OI-42).
- **FR-20:** Исполнитель задачи может быть не задан (null). Создать задачу без исполнителя
  могут БА и СМ. Если «Пользователь» создаёт задачу (в том числе подзадачу, FR-19b) и не
  указывает исполнителя, исполнителем становится он сам, и задача — «своя» (FR-19); явно
  переданный «Пользователем» пустой исполнитель (null) ДОЛЖЕН отклоняться с 403, задача не
  создаётся (OI-104). Назначенный исполнитель ДОЛЖЕН
  быть участником проекта; назначение не участника ДОЛЖНО отклоняться с 422 и отдельным
  кодом ошибки, по которому интерфейс предлагает сначала добавить человека в проект (OI-18).
  ТА и заблокированный пользователь исполнителем быть не могут — 422 (FR-70).
- **FR-21:** Задача может иметь подзадачи ровно одного уровня вложенности; создание
  подзадачи у подзадачи ДОЛЖНО отклоняться с 422 (ТЗ §2, OI-19).
- **FR-22:** Прогресс родительской задачи — доля подзадач в статусе «Готово» среди
  неудалённых подзадач, в целых процентах с округлением вниз. Значение вычисляется при
  запросе и не хранится. Удаление подзадачи пересчитывает прогресс. Если подзадач нет,
  прогресс — null, а не 0. Родителя можно закрыть при незакрытых подзадачах: API это не
  ограничивает, интерфейс показывает предупреждение (ТЗ §6 п.4, OI-19).
- **FR-23:** Комментарии к задаче (OI-20):
  - оставлять комментарий может пользователь с правом чтения задачи;
  - плоский список без веток, по времени создания по возрастанию;
  - текст 1–10 000 символов; HTML вырезается; пустой или более
    длинный текст ДОЛЖЕН отклоняться с 422;
  - в R1 интерфейс показывает текст комментария как простой текст: разметка markdown
    хранится так, как введена, и не отрисовывается (SC-11). Отрисовка markdown отложена
    (следующая версия), ADR-0012;
  - автор может править и удалять свой комментарий; при правке сохраняется время правки
    и показывается отметка «изменён»; БА может удалить любой комментарий в своём проекте
    (где он владелец, FR-19); СМ может удалить любой комментарий в проекте, где участвует
    (OI-72, З-9); попытка «Пользователя» править или удалить чужой комментарий — 403;
  - удаление мягкое: в списке вместо текста показывается «комментарий удалён», автор и
    время сохраняются;
  - отложено (следующая версия), ADR-0012: упоминание `@логин` с уведомлением по FR-71
    (OI-58, ADR-0008, SC-6) и ответ 409 в архивном проекте (FR-14b, SC-3).
- **FR-24:** Отложено (следующая версия), ADR-0012 (SC-5). Вложения задачи — текст в разделе
  «Отложено в следующую версию».
- **FR-25:** Мягко удаляются задачи, проекты и комментарии (OI-12).
  Удалённое не показывается в списках, на доске и в счётчиках; исключение —
  заглушка удалённого комментария (FR-23) (ТЗ §3, OI-12). Обращение к мягко удалённому
  объекту по идентификатору получает 404 (FR-45a).
  Удаление проекта мягко удаляет его задачи (FR-16). Удаление родительской задачи мягко
  удаляет её подзадачи и комментарии, удаление подзадачи — её комментарии (OI-63, OI-78).

  В R1 удаление необратимо: корзины, восстановления и окончательного удаления нет (SC-4).

  Отложено (следующая версия), ADR-0012: мягкое удаление вложений (SC-5), сделок, клиентов

- **FR-28:** Канбан-доска ДОЛЖНА показывать задачи проекта в 4 колонках, по одной на

  верхнего уровня; подзадачи видны в карточке родительской задачи вместе с прогрессом
  (FR-22) (OI-23).
- **FR-28a:** Порядок карточек внутри колонки задаётся вручную и хранится на сервере

  - при перемещении клиент передаёт соседей (`before_task_id`, `after_task_id`), а не

  - если промежуток исчерпан, колонка перенумеровывается шагом 1024 в одной транзакции;
  - новая задача добавляется в конец первой колонки;
  - если статус меняется не перетаскиванием (из карточки задачи или через API без
    указания соседей), задача ставится в конец целевой колонки (OI-66);
  - сортировка: позиция по возрастанию, при равенстве — время создания.
- **FR-29:** Интерфейс ДОЛЖЕН подтягивать изменения других пользователей опросом сервера
  не реже раза в 15 секунд; изменения ДОЛЖНЫ быть видны не позднее чем после обновления
  страницы (ТЗ §3, §6 п.5). В R1 опрос работает на экранах: доска, список задач проекта,
  личный список «мои задачи», карточка задачи с комментариями (OI-24, SC-17). Запросы опроса

  сделок, лент активности (проекта и сделки) и счётчика упоминаний отложен (следующая версия)
  вместе с этими экранами, ADR-0012 (SC-1, SC-6, SC-8).

## FR-I. API (требования к контракту, не к реализации)

- **FR-43:** Функции FR-1…FR-42 и FR-52…FR-73, кроме отложенных (ADR-0012), ДОЛЖНЫ быть
  доступны через REST API с префиксом версии `/api/v1` (AGENTS.md). Исключение — команда
  оператора FR-49 (демо-данные). Конкретные пути и схемы определяются в `plan.md`.
  Команды оператора FR-25c, FR-40, FR-50, FR-72 и автоочистка корзины по FR-25b отложены
  (следующая версия) вместе с этими требованиями, ADR-0012 (SC-12).
- **FR-44:** Описание API в формате OpenAPI ДОЛЖНО генерироваться автоматически (ТЗ §7).
- **FR-45:** Ответ с ошибкой ДОЛЖЕН иметь единый формат `{"detail": ..., "code": ...}`
  (AGENTS.md). Коды HTTP:
  - 400 — синтаксически невалидный JSON в теле запроса, код `bad_request` (FR-7; Д-7, OI-121,
    SC-21);
  - 401 — нет аутентификации;
  - 403 — нет прав;
  - 404 — ресурс не найден (FR-45a);
  - 422 — ошибка валидации, в том числе недопустимый получатель (FR-70) (OI-35, OI-85);
  - 503 — блокировка БД занята или возникла взаимоблокировка, код `service_busy`, с
    заголовком `Retry-After: 5` (решение владельца по Q-1, OI-122).
  Отложено (следующая версия), ADR-0012: 409 — изменение в архивном проекте, код
  `project_archived` (FR-14b, SC-3); 413 — вложение больше 10 МБ (FR-24, SC-5).
- **FR-45a:** Выбор между 403 и 404 (OI-35):
  - роль без доступа к разделу целиком (ТА — к бизнес-данным: проектам, задачам;
    пользователь без роли — ко всему, FR-66) получает 403 на любой
    идентификатор в этом разделе, существующий или нет;
  - существующий объект, на который у пользователя нет прав, — 403 (ТЗ §6 п.7);
  - несуществующий, мягко удалённый объект и объект другого рабочего пространства — 404.
  Отложено (следующая версия), ADR-0012: CRM-раздел (ТА и «Пользователь» — 403, SC-1),
  окончательно удалённые объекты и обращение через корзину (SC-4).
- **FR-46:** Все даты-время в API — UTC, ISO 8601; денежные суммы — целое число копеек
  плюс код валюты (ТЗ §3). Исключение — срок задачи: календарная дата `YYYY-MM-DD` без
  времени и часового пояса (FR-18, ADR-0007). Денежных сумм в R1 нет: они вернутся вместе с
  CRM (SC-1).
- **FR-47:** Списочные ответы ДОЛЖНЫ быть постраничными; размер страницы по умолчанию —
  50 (ТЗ §5). Исключение — доска (FR-28): все неудалённые задачи верхнего уровня проекта
  возвращаются одним ответом без постраничного вывода (SC-15). Исключение для поиска
  (FR-39) отложено вместе с поиском, ADR-0012 (SC-9).

- **NFR-1 (нагрузка):** 12 пользователей, до 5 одновременно активных (ТЗ §5).
- **NFR-2 (время отклика):** на стенде 3 vCPU / 6 ГБ RAM, на объёме 50 000 задач,

# Data Model

Логическая модель: сущности и атрибуты, названные в ТЗ и глоссарии. Типы, обязательность
и индексы определяются в `plan.md`. Атрибуты с пометкой «?» в ТЗ не заданы.

**Общие поля всех доменных сущностей:** `workspace_id` (ТЗ §3), `created_at`,
`updated_at` (UTC), `created_by` → user; у объектов, созданных автоматически (первый ТА),
автор — «система» (OI-40). `deleted_at` — у задач, проектов и комментариев (ТЗ §3, OI-84).

Сущности R1 (ADR-0012):

| Сущность (код) | Атрибуты | Связи |
|---|---|---|
| Рабочее пространство (`workspace`) | — (в R1 атрибутов сверх общих не требуется) | 1 в R1; владеет всеми сущностями |
| Пользователь (`user`) | логин (шаблон FR-73, уникален без учёта регистра), хеш пароля (Argon2id), признак блокировки, признак одноразового пароля (FR-55) | 0..1 роль в рабочем пространстве (FR-66) |
| Роль пользователя | роль ∈ {tech_admin, business_admin, mixed, user} | user × workspace, не больше одной; отсутствие роли допустимо (OI-6) |
| Проект (`project`) | название (обяз., 1–255), описание (≤ 10 000), `deleted_at`; срока нет | владелец → user; участники ↔ user (M:N) |
| Задача (`task`) | название (обяз., 1–255), описание (≤ 10 000), срок (календарная дата, ADR-0007), приоритет ∈ {базовый, высокий}, статус (FR-18a), позиция в колонке (только у задач верхнего уровня, FR-28a), `deleted_at`; прогресс — вычисляемый, не хранится | проект; автор → user (`created_by`); исполнитель → user, nullable; родитель → task (≤ 1 уровень) |
| Комментарий (`comment`) | текст (1–10 000, хранится как введён без HTML, показывается простым текстом — FR-23), автор, время создания, время правки, `deleted_at` | задача |
| Доска / колонка (`board`, `column`) | не хранятся отдельно: колонки = статусы FR-18a, не настраиваются | проект; на доске только задачи верхнего уровня (FR-28) |
| Запись аудита | автор, время UTC, тип сущности, идентификатор, действие, имена изменённых полей; значений и названий бизнес-сущностей нет (FR-41) | учётные записи, роли, сессии, проекты (передача владения) |

Отложено (следующая версия), ADR-0012: статус проекта (SC-3); связь проекта со сделкой
(SC-1); метки задачи и сущность «Метка» (SC-7); «Упоминание» (SC-6); «Вложение» (SC-5);
«Клиент», «Контакт», «Воронка», «Стадия», «Сделка», «История сделки» (SC-1); «Событие
активности» (лента, SC-8); `deleted_at` у вложений, сделок, клиентов и контактов; записи
аудита о стадиях и сделках. Строки модели в редакции v0.15 — в разделе «Отложено в следующую
версию».

Будущее (не реализуется в R1): связь «задача → цель» в модели R1 не закладывается; она
добавляется позже аддитивной миграцией, это фиксируется в `plan.md` (OI-2, OI-101,
ADR-0011 — уточняет ADR-0002).

# User Flows

Роли: **ТА** — техадмин, **БА** — бизнес-админ, **СМ** — смешанная, **П** — пользователь.

- **UF-1 Развёртывание** (ТЗ §6 п.1). Оператор клонирует репозиторий, копирует
  `.env.example` в `.env`, выполняет `docker compose up`, загружает демо-данные, входит в
  систему.
- **UF-2 Заведение команды** (ТЗ §6 п.2). ТА входит, создаёт учётные записи, назначает
  роли; пользователи входят по логину и паролю. ТА блокирует учётную запись — пользователь
  больше не может войти.
- **UF-3 Проект и задачи** (ТЗ §6 п.3). БА создаёт проект, добавляет участников, ставит
  задачи со сроками и исполнителями. Участник открывает личный список и видит
  назначенные ему задачи.
- **UF-4 Подзадачи** (ТЗ §6 п.4). Исполнитель делит задачу на подзадачи, закрывает их;
  прогресс родителя растёт.
- **UF-5 Доска** (ТЗ §6 п.5). Участник открывает доску проекта и перетаскивает задачу в
  другую колонку; другой участник после обновления страницы (или очередного опроса)
  видит новый статус.
- **UF-6 Работа с задачей.** Участник фильтрует список задач проекта по исполнителю и
  статусу, открывает карточку, комментирует. Прикрепление файла отложено (следующая версия)
  вместе с FR-24, ADR-0012 (SC-5).
- **UF-7 Сделка:** отложено (следующая версия), ADR-0012 (SC-1, ТЗ §6 п.8).
- **UF-8 Сделка → проект:** отложено (следующая версия), ADR-0012 (SC-1, ТЗ §6 п.9).
- **UF-9 Обзор активности:** отложено (следующая версия), ADR-0012 (SC-8).
- **UF-10 Поиск:** отложено (следующая версия), ADR-0012 (SC-9).
- **UF-11 Экспорт/импорт:** отложено (следующая версия), ADR-0012 (SC-12, ТЗ §6 п.11).
- **UF-12 Резервная копия:** отложено (следующая версия), ADR-0012 (SC-12, ТЗ §6 п.12, OI-124).
- **UF-13 Отказы по правам** (ТЗ §6 п.6–7). «Бизнес-пользователь» пытается создать
  задачу другому — отказ. «Бизнес-пользователь» ТЗ §6 = роль «Пользователь» (OI-43,
  `docs/glossary.md`). Вторая часть — «Бизнес-пользователь» и ТА запрашивают сделку по
  идентификатору, отказ — отложена вместе с CRM, ADR-0012 (SC-1)
  [ВОПРОС ВЛАДЕЛЬЦУ: как в R1 закрывается ТЗ §6 п.7 — OI-125].

Тексты UF-7…UF-12 в редакции v0.15 — в разделе «Отложено в следующую версию».

# Acceptance Criteria

Номера в скобках — проверяемые требования. Категория проверки — по NFR-10: AC без пометки —
API-автотест; пометки *инфра*, *замер*, *ручной*, *e2e* — другие категории.
Приёмка R1 (ADR-0012) — все AC, кроме помеченных «отложено (следующая версия)». У частично
отложенных AC в R1 проверяется приведённая здесь формулировка, отложенная часть названа в
самом AC. Тексты отложенных AC в редакции v0.15 — в разделе «Отложено в следующую версию».
Во всех автотестах время («сегодня», возраст объектов в корзине, тайм-ауты сессий)
задаётся фиксированными часами теста, генераторы — фиксированным seed.

- **AC-1** (NFR-3, FR-48, FR-49) *ручной*: Given чистая машина с Docker
  When `git clone`, `cp .env.example .env`, `docker compose up`, загрузка демо-данных
  Then вход в систему с демо-данными выполнен не позднее 10 минут от начала, без правки кода.
- **AC-2** (FR-1, FR-4, FR-8): Given ТА аутентифицирован When он создаёт 12 учётных
  записей и назначает им роли Then каждый из 12 пользователей проходит вход по своему
  логину и паролю и получает назначенную роль.
- **AC-3** (FR-2): Given создан пользователь When читается его запись в БД Then пароль
  хранится как хеш Argon2id, открытого пароля нет.

## Ограничения и требования, отложенные полностью (редакция v0.15)

- **C-7 Вложения без антивирусной проверки:** в пилоте вложения не проверяются антивирусом;
  защита — белый список типов и проверка содержимого (FR-24). Решение заказчика, OI-21.
- **FR-14b:** Статус проекта — «Активный» или «Архивный»; новый проект — «Активный»
  (OI-3, ADR-0005). Архивирует и разархивирует проект его владелец или СМ (OI-60, З-4); СМ —
  в любом проекте, участие не требуется: это управление проектом, а не чтение задач (OI-96,
  ADR-0009). Попытка остальных ДОЛЖНА отклоняться с 403. В архивном проекте разрешены только: чтение (проект,
  задачи, комментарии, вложения, лента), скачивание вложений, разархивирование, удаление
  проекта и передача владения. Любое другое изменение — в том числе создание, изменение,
  перетаскивание, удаление и восстановление задач, комментарии, загрузка и удаление
  вложений, изменение состава участников и полей проекта — ДОЛЖНО отклоняться с 409 и кодом
  ошибки `project_archived`, данные не меняются. Архивный проект по умолчанию НЕ
  показывается в списке проектов (FR-17) и его задачи — в личном списке задач (FR-26); и
  то и другое доступно через фильтр по статусу проекта. Связь проекта со сделкой при
  архивировании сохраняется (FR-36). Архивирование и разархивирование пишутся в ленту
  проекта (FR-38) и журнал аудита (FR-41).
- **FR-18b:** Задаче можно назначить только существующие метки; назначение несуществующей
  метки ДОЛЖНО отклоняться с 422, произвольный текст метку не создаёт. На задаче не более
  10 меток; 11-я ДОЛЖНА отклоняться с 422. Удаление метки снимает её со всех задач, сами
  задачи не меняются (OI-16). Метки общие для всего рабочего пространства: одна и та же
  метка назначается задачам любых проектов. Создают, переименовывают и удаляют метки БА и
  СМ; попытка «Пользователя» или ТА ДОЛЖНА отклоняться с 403. «Пользователь» только назначает
  существующие метки на свои задачи (FR-19) (OI-16, З-3). Название метки — 1–50 символов,
  уникально в рабочем пространстве без учёта регистра; пустое, более длинное или
  повторяющееся название ДОЛЖНО отклоняться с 422 (OI-100).
- **FR-24:** Вложения задачи (ТЗ §3, OI-21):
  - не более 10 МБ на файл (больше — 413) и не более 20 файлов на задачу (21-й — 422);
  - допустимые типы: png, jpeg, gif, webp, pdf, doc, docx, xls, xlsx, ppt, pptx, txt,
    csv, md, zip. Тип ДОЛЖЕН определяться по содержимому, а не только по расширению;
    файл недопустимого типа, исполняемый файл и архив, содержащий исполняемый файл,
    ДОЛЖНЫ отклоняться с 422;
  - вложенные архивы проверяются рекурсивно до глубины вложенности 3 включительно
    (загружаемый архив — уровень 1); архив,
    который не удаётся проверить целиком (вложенность глубже 3, зашифрованные элементы,
    повреждённое содержимое), считается непроверяемым и ДОЛЖЕН отклоняться с 422 (OI-113);
  - исходное имя файла сохраняется только для отображения; на диске файл хранится под
    сгенерированным именем, исходное имя в путь не попадает;
  - содержимое — в файловом хранилище, в БД — только метаданные;
  - скачивание — только через API с проверкой прав на задачу (не участник — 403);
    прямой раздачи файлов нет; в архивном проекте скачивание разрешено (FR-14b);
  - загружает вложение любой, кто может читать задачу; удаляет вложение автор загрузки или
    тот, кто может менять все поля задачи (FR-19); попытка остальных — 403 (OI-63, OI-80);
    в архивном проекте загрузка и удаление — 409 (FR-14b);
  - удаление задачи мягко удаляет её вложения; файлы физически удаляются при
    окончательном удалении (FR-25b).
- **FR-25a:** Удалённое попадает в корзину проекта и корзину рабочего пространства и
  хранится там 30 дней. Восстанавливает тот, у кого есть право удалить этот объект.
  Корзина показывает пользователю только объекты, которые он вправе восстановить; у ТА
  корзина пуста (OI-67).
  Восстановленная задача возвращается в ту же колонку и на ту же позицию; если эту позицию
  уже занимает другая неудалённая задача, восстановленная ставится сразу после неё (OI-114).
  Восстановление
  задачи удалённого проекта ДОЛЖНО отклоняться с 422, пока проект не восстановлен (OI-12).
  Права на удаление задачи — FR-19. Удаление родительской задачи мягко удаляет её
  подзадачи, комментарии и вложения; восстановление подзадачи при удалённом родителе ДОЛЖНО
  отклоняться с 422 (OI-63, OI-78). Восстановление родительской задачи возвращает
  подзадачи, комментарии и вложения, удалённые вместе с ней, но не удалённые раньше (OI-99).
  Восстановление проекта — FR-16; клиента и сделки — FR-37.
  (v0.16: каскад удаления родительской задачи без вложений перенесён в FR-25 и действует в R1.)
- **FR-25b:** Окончательное удаление выполняется кнопкой в корзине и автоматически через
  30 дней. Автоочистку выполняет команда обслуживания; фонового планировщика в R1 нет
  (OI-12). Окончательно удалить объект из корзины может тот, кто вправе его восстановить
  (FR-25a); попытка остальных ДОЛЖНА отклоняться с 403 (OI-107). Окончательно удаляются только задачи, проекты, комментарии и вложения (вместе с
  файлами). Сделки, клиенты и контакты окончательно НЕ удаляются: через 30 дней команда
  обслуживания убирает их из корзины, но записи остаются в БД; кнопка окончательного
  удаления для них ДОЛЖНА отвечать 422, данные не меняются (OI-59, З-7, ADR-0010).
  После окончательного удаления события ленты (FR-38) и журнала аудита (FR-41) об объекте
  сохраняются; объект в них показывается как «объект удалён» без содержимого (названия,
  текста, значений) (OI-83).
- **FR-25c:** Сделку, клиента или контакт, убранные из корзины по FR-25b, ДОЛЖНА
  восстанавливать команда оператора (вне ролей и HTTP API) по идентификатору объекта; через
  интерфейс и API такие объекты не восстанавливаются (OI-59, ADR-0010). Единственное
  действие с такой сделкой через API — снятие её связи с проектом (FR-36, OI-118).
- **FR-27a:** Фильтр по сроку (OI-22): «просрочено», «сегодня», «завтра», «ближайшие
  7 дней», «без срока», произвольный диапазон с границами включительно. «Просрочено» —
  срок строго раньше сегодняшней даты в часовом поясе Europe/Moscow и статус не
  «Готово». Часовой пояс — константа Europe/Moscow, не настраивается (OI-62, ADR-0007).
  «Ближайшие 7 дней» — срок от сегодняшней даты до сегодняшней + 6 дней включительно, по
  Europe/Moscow. Задачи в статусе «Готово» исключаются только из «просрочено»; в остальных
  фильтрах по сроку («сегодня», «завтра», «ближайшие 7 дней», «без срока», диапазон) они
  участвуют наравне с прочими (OI-106).
- **FR-30:** CRM ДОЛЖНА быть отдельным разделом интерфейса того же приложения и
  доступна только ролям с правом «CRM: чтение» (BR-1).
- **FR-31:** Система ДОЛЖНА вести клиентов (компании-контрагенты, `docs/glossary.md`).
  Клиент — организация; индивидуальный предприниматель тоже считается организацией;
  клиенты-физлица — R2 (OI-25). Поля клиента:
  - название — обязательно, 1–255 символов;
  - ИНН — необязательно; ровно 10 или 12 цифр; уникален среди неудалённых клиентов
    рабочего пространства;
  - телефон — до 50 символов; email — до 254 символов; сайт — до 255 символов; адрес — до
    500 символов; заметка — до 10 000 символов (все необязательны; предельные длины
    предложены аналитиком и приняты архитектором, OI-25).
  Нарушение любого ограничения ДОЛЖНО отклоняться с 422, клиент не создаётся и не меняется.
- **FR-32:** Система ДОЛЖНА вести контакты — людей на стороне клиента (OI-26). Поля
  контакта: ФИО — обязательно, 1–255 символов; должность — до 255; телефон — до 50; email —
  до 254; заметка — до 10 000 (предельные длины приняты аналитиком и архитектором, OI-26).
  Контакт принадлежит
  ровно одному клиенту. Нарушение ограничений — 422.
- **FR-33:** Сделка ДОЛЖНА иметь сумму, валюту, стадию и ответственного (ТЗ §2). Сумма
  хранится целым числом копеек; валюта в R1 — только RUB, другая валюта ДОЛЖНА
  отклоняться с ошибкой валидации (ТЗ §3). Поля сделки (OI-27):
  - название — обязательно, 1–255 символов (длина принята аналитиком и архитектором, OI-27);
  - клиент — обязательно, неудалённый клиент пространства;
  - сумма — обязательно, целое число копеек от 0 до 10^14 включительно; иначе — 422;
  - валюта — RUB;
  - стадия — по умолчанию первая по порядку активная стадия типа open (FR-34);
  - ответственный — активный пользователь с ролью БА или СМ; по умолчанию — создатель
    сделки; иной ответственный — 422 (FR-70);
  - контакты — 0..N; каждый ДОЛЖЕН принадлежать клиенту сделки, иначе 422 (OI-26);
  - проект — 0..1 (FR-36).
  Смена клиента у сделки с привязанными контактами ДОЛЖНА отклоняться с 422 и кодом
  «сначала отвяжите контакты» (OI-26).
- **FR-34:** Воронка ДОЛЖНА состоять из упорядоченного набора стадий, которые можно
  настраивать (ТЗ §2). Правила (OI-28):
  - воронка одна на рабочее пространство;
  - у стадии есть название (1–100 символов — длина принята аналитиком и архитектором;
    уникально в воронке), порядок и тип ∈ {open, won, lost};
  - создают, переименовывают, переупорядочивают, архивируют, разархивируют и удаляют стадии
    БА и СМ; попытка остальных — 403;
  - в воронке всегда ДОЛЖНЫ быть не меньше одной активной стадии типа open, ровно одна
    активная стадия типа won и ровно одна активная типа lost; операция, нарушающая это,
    ДОЛЖНА отклоняться с 422;
  - удалить можно только стадию, в которой никогда не было сделок; иначе — 422, стадию
    можно только архивировать;
  - архивная стадия не предлагается и не принимается для новых сделок и переходов (422);
    сделки в ней остаются и видны; стадию можно разархивировать;
  - переходы между стадиями свободные: через стадии и назад;
  - при первом запуске создаются стадии «Новая», «Квалификация», «Предложение»,
    «Переговоры» (тип open), «Выиграна» (won), «Проиграна» (lost), в этом порядке, с автором
    «система» (OI-40).
  Представление воронки в R1 — список сделок с фильтром по стадии плюс число сделок и сумма
  сумм по каждой стадии (неудалённые сделки); стадия сделки меняется полем. Доска сделок с
  перетаскиванием — вне рамок R1 (OI-91).
- **FR-35:** Каждое изменение сделки ДОЛЖНО фиксироваться в истории с указанием автора,
  времени (UTC), изменённого поля, старого и нового значения; история ДОЛЖНА показывать,
  кто и когда перенёс сделку между стадиями (ТЗ §2, §6 п.8). Историю читают роли с правом
  «CRM: чтение». Событие об изменении сделки ДОЛЖНО появляться в истории сделки, ленте
  сделки (FR-38) и журнале аудита (FR-41) вместе с самим изменением: либо сохранено
  изменение и все три записи, либо ничего; отклонённое изменение записей не создаёт.
  События хранятся бессрочно, с учётом FR-25b (OI-45, OI-83). Мягкое удаление и
  восстановление сделки (в том числе командой оператора, FR-25c) — тоже изменения сделки:
  каждое пишется одним событием в историю сделки, ленту сделки и журнал аудита (OI-116).
- **FR-36:** Сделку можно связать с проектом. На странице сделки ДОЛЖНЫ быть видны задачи
  связанного проекта, на странице проекта — связанная сделка (ТЗ §6 п.9). Правила
  (OI-29, OI-30, OI-92):
  - связь 1:1: у сделки не больше одного проекта, у проекта не больше одной сделки;
    повторная связь уже связанного проекта или сделки — 422;
  - связь с удалённым проектом — 422; с архивным — разрешена;
  - мягкое удаление сделки связь с проектом не снимает: восстановление сделки возвращает её
    вместе со связью (OI-115). Пока проект связан с удалённой сделкой (в корзине или уже
    убранной из корзины по FR-25b), связать его с другой сделкой нельзя — 422 с отдельным
    кодом ошибки «проект связан с удалённой сделкой» (OI-118);
  - на странице проекта, связанного с удалённой сделкой, роли с правом «CRM: чтение» видят
    только признак «связанная сделка удалена», без полей сделки; ролям без этого права
    по-прежнему не показывается ничего (OI-30, OI-118);
  - пользователь с правом «CRM: создание и изменение» может снять связь проекта с удалённой
    сделкой — и пока сделка в корзине, и после того, как она убрана из корзины; участвовать
    в проекте для этого не нужно. Снятие пишется одним событием в историю этой сделки, ленту
    сделки и журнал аудита (FR-35). После снятия проект свободен для связи с другой сделкой;
    при последующем восстановлении сделки снятая связь не возвращается (OI-118);
  - связь ставит и снимает пользователь с правом «CRM: создание и изменение»; участвовать в
    проекте для этого не нужно;
  - на странице проекта сделка показывается полями: название, стадия, сумма, ответственный.
    Роли без права «CRM: чтение» не получают о сделке ничего: поля связи нет в ответе;
  - на странице сделки задачи проекта видит только участник проекта; они выводятся
    постранично (FR-47) с полями: название, статус, исполнитель, срок, приоритет. Не
    участнику показываются название проекта и признак «нет доступа к задачам», без задач.
- **FR-37:** Сделки, клиенты и контакты удаляются мягко по FR-25…FR-25c (ТЗ §3, OI-12).
  Правила (OI-12, OI-59):
  - клиента с неудалёнными сделками удалить нельзя — 422;
  - удаление клиента мягко удаляет его контакты; восстановление клиента возвращает
    контакты, удалённые вместе с ним, но не удалённые раньше;
  - восстановление сделки при удалённом клиенте — 422;
  - удаляют и восстанавливают роли с правом «CRM: создание и изменение».
- **FR-38:** Система ДОЛЖНА показывать ленту активности по проекту и по сделке
  (ТЗ §2). Состав событий (OI-31, OI-45):
  - лента проекта: задачи (создание, смена статуса, исполнителя или срока, удаление,
    восстановление), комментарии (факт добавления и удаления, без текста), вложения,
    участники (добавление, исключение, в том числе «исполнитель снят, участник исключён»
    по FR-15a), передача владения, архивирование и разархивирование. CRM-событий в ленте
    проекта нет;
  - лента сделки: создание, переходы по стадиям, изменение суммы и ответственного, связь с
    проектом и её снятие, привязка и отвязка контактов, удаление и восстановление сделки
    (OI-116);
  - правка названия или описания отражается событием без старого и нового значения;
  - у события есть автор (пользователь или «система»), время UTC, тип события и объект.
  Ленту проекта читают участники проекта (не участник — 403); ленту сделки — роли с правом
  «CRM: чтение». События хранятся бессрочно; после окончательного удаления объекта —
  FR-25b.
- **FR-39:** Система ДОЛЖНА предоставлять базовый поиск по названиям; результаты ДОЛЖНЫ
  учитывать права пользователя (BR-1). Правила (OI-32):
  - ищутся задачи и проекты (с учётом прав на чтение, FR-17), клиенты и сделки — только для
    ролей с правом «CRM: чтение»; контакты не ищутся;
  - совпадение — по подстроке названия без учёта регистра;
  - запрос короче 2 символов ДОЛЖЕН отклоняться с 422;
  - не более 20 результатов на тип сущности — явное исключение из FR-47;
  - архивные проекты и их задачи в поиск входят; удалённые объекты — нет (FR-25).
- **FR-40:** Система ДОЛЖНА выгружать данные в JSON и загружать их обратно без потерь
  (ТЗ §2, §6 п.11). Правила (OI-33, OI-81, З-10, ADR-0010):
  - экспорт и импорт выполняет оператор CLI-командой, вне ролей; через HTTP API они
    недоступны;
  - состав выгрузки: всё рабочее пространство — пользователи с хешами паролей, роли, все
    доменные сущности (включая удалённые, `deleted_at`), журнал аудита, история сделок,
    лента активности, метаданные и файлы вложений. Сессии в выгрузку не входят;
  - формат — архив, содержащий `data.json` и каталог `files/` с файлами вложений;
  - файл выгрузки создаётся с правами на чтение только владельцем (как в FR-6);
  - импорт выполняется только в «пустую» систему, где нет данных, кроме созданных
    автоматически (первый ТА по FR-6, воронка по умолчанию по FR-34). Импорт заменяет эти
    данные, удаляет файл с паролем первого ТА и сохраняет идентификаторы;
  - импорт в непустую систему и импорт выгрузки другой версии схемы ДОЛЖНЫ отклоняться с
    понятным сообщением и ненулевым кодом завершения; данные системы не меняются;
  - «без потерь»: цикл экспорт → импорт → экспорт даёт идентичный `data.json` (без учёта
    метки времени экспорта) и файлы вложений с теми же sha256.
  Проверка — автотест команды, а не HTTP API: отступление от формулировки ТЗ §6 «автотест
  на уровне API» (ADR-0010).
- **FR-50:** Резервная копия БД и вложений ДОЛЖНА сниматься одной командой и
  восстанавливаться одной командой (ТЗ §5). (v0.16: не входит в R1 по решению владельца
  по Q-M3, технический долг следующей версии, OI-124.)
- **FR-71:** Упоминания `@логин` работают только внутри приложения (OI-58, З-11, ADR-0008):
  - упоминание в комментарии участника проекта создаёт ему уведомление; у пользователя есть
    счётчик непрочитанных упоминаний, список упоминаний и признак «прочитано» у каждого;
  - счётчик и список обновляются опросом (FR-29);
  - упоминание логина, не принадлежащего участнику проекта, ничего не создаёт;
  - правка комментария не создаёт повторного уведомления уже упомянутым; логин участника,
    впервые упомянутый при правке, получает уведомление (OI-98);
  - удаление комментария снимает уведомление; восстановление комментария возвращает
    уведомления, снятые при его удалении (OI-98);
  - уведомлений вне приложения (email, push) нет.
- **FR-72:** В репозитории ДОЛЖНА быть команда генерации нагрузочного набора для NFR-2
  (50 000 задач, 10 000 сделок, 5 000 клиентов): только синтетические данные (BR-9);
  результат детерминирован при заданном seed — одинаковый seed на чистой системе даёт
  одинаковый набор (OI-47).

## Бизнес-правила (редакция v0.15)

- **BR-5.** Вложение — не более 10 МБ на файл (ТЗ §3).
- **BR-6.** Деньги — целое число копеек + код валюты; в R1 допустима только RUB; дробные
  значения запрещены (ТЗ §3).
- **BR-7 (v0.15).** Удаление задач, проектов, сделок — мягкое (ТЗ §3); удаление
  комментариев, вложений, клиентов и контактов — тоже мягкое (FR-25). Окончательно через
  30 дней удаляются только задачи, проекты, комментарии и вложения; сделки, клиенты и

- **BR-13.** Архивный проект доступен только на чтение, кроме действий из FR-14b; прочие
  изменения — 409 `project_archived`.

## Сценарии (редакция v0.15)

- **UF-6 Работа с задачей (v0.15).** Участник фильтрует список, открывает карточку,
  комментирует, прикрепляет файл.
- **UF-7 Сделка** (ТЗ §6 п.8; «Менеджер» = БА или СМ, OI-41). БА/СМ заводит клиента, контакт и сделку на 500 000 ₽,
  переносит её по трём стадиям, открывает историю и видит, кто и когда переносил.
- **UF-8 Сделка → проект** (ТЗ §6 п.9). БА/СМ связывает сделку с проектом; на странице
  сделки видит задачи проекта, на странице проекта — сделку.
- **UF-9 Обзор активности.** Участник открывает ленту активности проекта; БА/СМ —
  ленту сделки.
- **UF-10 Поиск.** Пользователь вводит часть названия и получает доступные ему результаты.

## Частично отложенные критерии: полный текст в редакции v0.15

В R1 проверяются формулировки из раздела Acceptance Criteria. AC-48 и AC-50 в редакции v0.15
не откладываются, а заменяются решением OI-120 (история версий).

  удалена Then она не возвращается в списках, на доске, в поиске и в счётчиках, но
  доступна в корзине, а запись в БД сохранена с `deleted_at`.
