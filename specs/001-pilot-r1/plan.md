## 1. Подход

Модульный монолит: один FastAPI-процесс (`backend/app`) со слоями `api → domain → core`
(AGENTS.md), PostgreSQL 16 через SQLAlchemy 2 (async, asyncpg) и Alembic, один React-SPA,
который вместе с TLS-терминацией отдаёт контейнер `web` (nginx). Все права проверяются в
сервисном слое по единому модулю `domain/access` с фиксированным порядком проверок
(401 → 403 по разделу → 404 → 403 по объекту → 409 → 422). Сессии серверные, в таблице
БД; фоновые запросы опроса помечаются заголовком и не продлевают неактивность. История
сделки, ленты и журнал аудита — это **одна append-only таблица событий `domain_event`**:
одна строка, вставленная в той же транзакции, что и изменение, видна в нужных
представлениях — атомарность «изменение + история + лента + аудит» получается по построению,
а аудит физически не возвращает значений по бизнес-сущностям. Команды оператора (первый
запуск, демо-данные, экспорт/импорт, обслуживание, восстановление CRM, генератор нагрузки)
— один CLI `gostracker` внутри образа API; бэкап и восстановление — скрипты поверх
служебного сервиса compose `ops`. Новые внешние библиотеки добавляются только там, где своё
решение было бы рискованнее (Argon2id, разбор multipart, tzdata); определение типа файла,
очистка HTML, CLI, замер NFR-2 — на стандартной библиотеке.

## 4. Интерфейсы

### 4.1. Слои и правила (AGENTS.md)

- `api/v1/*` — только: схема запроса → вызов сервиса `domain/*` → схема ответа. Никакого SQL.
- `domain/*` — сервисы и запросы; каждая выборка фильтруется `workspace_id = actor.workspace_id`.
  Сервис получает `Actor` и `AsyncSession` аргументами.
- `core/*` — инфраструктура без бизнес-правил.
- Транзакция = запрос: `get_db` открывает `session.begin()`; исключение → откат. Подключать только как `DbSession` (scope="function", см. §4.2). **Исключение (ревью T11, PLAN_ISSUE):** состояние, которое должно пережить откат запроса (счётчик неудачных входов и `login_locked_until`, FR-61), закрепляется до броска `InvalidCredentials` единственным санкционированным помощником `core/db.py::commit_durably(session)`; прямой `.commit()` в сервисах по-прежнему запрещён (AST-тест), без помощника блокировка через API не работала бы — `get_db` откатывает транзакцию на исключении.
  Сервисы **не** вызывают `commit()`. Событие (§4.4) пишется в той же сессии.

Представления:
- **История сделки** (FR-35): `WHERE deal_id = :id` → плоский список `{occurred_at, actor, field, old, new}` по элементам `changes`.
- **Лента сделки / проекта** (FR-38): `WHERE deal_id = :id` / `WHERE project_id = :id`,
  `ORDER BY id DESC`, пагинация 50. Для `project.updated`/`task.updated` по title/description
  значения не отдаются. Если объект окончательно удалён — `{"entity": {"type", "id", "deleted": true}}`,
  `changes` не отдаются (FR-25b).
- **Аудит** (FR-41): `WHERE in_audit`, схема ответа `AuditEntry` = `{id, occurred_at, actor{kind,id,login},
  entity_type, entity_id, entity_deleted, action, changed_fields, details}` где `details`
  заполняется **только** для `entity_type = "user"`. Поля `changes` в схеме нет — значения и
  названия бизнес-сущностей не могут попасть в ответ.
- Каждая строка вставляется вызовом `record_event` в транзакции изменения; отклонённое
  изменение (исключение) откатывает и событие (AC-67).

Логика `LocalPasswordProvider.authenticate` (ревью T11, гонка FR-61/AC-37):
- попытка резервируется ДО verify одним атомарным `UPDATE app_user SET failed_login_count =
  CASE WHEN count+1 >= 5 THEN 0 ELSE count+1 END, login_locked_until = CASE WHEN count+1 >= 5
  THEN now+15 мин ELSE login_locked_until END WHERE login = :l AND (login_locked_until IS NULL OR
  login_locked_until <= now) RETURNING …`; строки нет (логина нет или он заблокирован) →
  `dummy_verify`, `None`; ответ одинаков;
- затем `checkpoint()` фиксирует резервирование, чтобы параллельные запросы видели занятый слот
  (блокировка строки на время Argon2 НЕ используется — иначе пачка запросов исчерпывает пул);
- пароль верен → условный сброс `SET failed_login_count = 0, login_locked_until = NULL WHERE id = :id
  AND (login_locked_until IS NULL OR login_locked_until <= now) RETURNING id` (при `needs_rehash` —
  перехеширование); строки нет → `None`; исключение: пятая попытка, сама поставившая блокировку,
  при верном пароле снимает её по `login_locked_until = <свой срок>`;
- пароль неверен → `None` (счётчик уже увеличен).
Свойства: не более 5 реальных проверок пароля между фиксациями блокировки при любом
параллелизме; **известное поведение:** верная попытка, зарезервированная до порога, отклоняется,
если параллельная неудача успела поставить блокировку (консервативный отказ, не обход);
прерванная отменой попытка остаётся засчитанной.

### 4.8. Позиции карточек (FR-28a; R1.1 — добавление и конец колонки, R1.2 — перемещение)

```python
# app/domain/tasks/positions.py
STEP: Final = 1024
async def lock_columns(db, project_id: UUID, *statuses: TaskStatus) -> None    # pg_advisory_xact_lock по hashtext в отсортированном порядке
async def append_position(db, project_id: UUID, status: TaskStatus) -> int     # max(position)+STEP или STEP
async def move_task(db, task: Task, *, status: TaskStatus, before_task_id: UUID | None, after_task_id: UUID | None) -> None
async def renumber_column(db, project_id: UUID, status: TaskStatus) -> None     # STEP, 2*STEP, … по (position, created_at)
```
Семантика API `POST /api/v1/tasks/{id}/move {status, before_task_id?, after_task_id?}`:
карточка встаёт **после** `after_task_id` и **перед** `before_task_id` (т.е. `after_task_id` —
сосед сверху, `before_task_id` — сосед снизу). Соседи должны быть неудалёнными задачами
верхнего уровня того же проекта в целевой колонке, иначе 422 `invalid_neighbors`.
Алгоритм: если задан `after_task_id` — нижняя граница = его позиция, верхняя = позиция его
текущего следующего соседа (если соседи уже не смежны из-за параллельного перемещения,
приоритет у `after_task_id`); иначе если задан `before_task_id` — верхняя граница = его
позиция, нижняя = предыдущий сосед или `верхняя − 2·STEP`; если оба `null` — конец колонки.
Позиция = `(low + high) // 2`; если `high − low < 2` — `renumber_column` и повторный расчёт.
Без соседей (смена статуса из карточки/PATCH) — `append_position` целевой колонки (FR-28a,
OI-66). Новая задача — `append_position(project, todo)`. Подзадачи позиции не имеют.
Восстановление задачи (FR-25a): позиция сохраняется; если в колонке уже есть неудалённая
задача с той же позицией — восстановленная ставится сразу после неё (FR-25a, OI-114, AC-118):
позиция между занимающей и её следующим соседом, при нехватке промежутка — перенумерация.

### 4.10. Корзина, окончательное удаление, импорт (FR-25…FR-25c, FR-37, FR-40, ADR-0010)

- Мягкое удаление ставит `deleted_at = now`, `deleted_batch_id = new uuid` объекту и его
  неудалённым зависимым: проект → его задачи (FR-16); задача → подзадачи, комментарии,
  вложения (FR-25a); клиент → контакты (FR-37). Восстановление — строки с тем же
  `deleted_batch_id`. Задача при удалённом проекте → 422 `project_deleted`; подзадача при
  удалённом родителе → 422 `parent_task_deleted`; сделка при удалённом клиенте → 422 `account_deleted`.
- `GET /api/v1/trash` — объединение удалённых объектов, которые actor вправе восстановить
  (FR-25a), без CRM-объектов с `trash_expired_at IS NOT NULL`. `POST /trash/{type}/{id}/restore`;
  `DELETE /trash/{type}/{id}` — окончательно (право = право восстановления, иначе 403 — FR-25b,
  OI-107; для deal/account/contact → 422 `permanent_delete_not_allowed`). Окончательное
  удаление проекта кнопкой выполняет тот же сервис, что и команда обслуживания (п.1 ниже),
  включая снятие связи со сделкой с автором «система» (FR-16).
- Команда обслуживания `gostracker maintenance` (идемпотентна, `--dry-run`):
  1. задачи, комментарии, вложения, проекты с `deleted_at <= now − 30 дней` — окончательно:
     собрать `storage_key` вложений (включая вложения задач удаляемых проектов) → для
     проекта, связанного со сделкой, `deal.project_id = NULL` + `record_event(deal.project_unlinked, actor_id=None)`
     (FR-16, OI-83) → `DELETE` (каскады FK) → после фиксации транзакции удалить файлы;
  2. сделки, клиенты, контакты с `deleted_at <= now − 30 дней` и `trash_expired_at IS NULL` →
     `trash_expired_at = now` (запись остаётся, FR-25b);
  3. удалить файлы в `attachments/` без строки в БД старше 1 часа (сироты после сбоев).
  `domain_event` не трогается (триггер это гарантирует, AC-66).
- `gostracker restore-crm {deal|account|contact} <id>`: снимает `deleted_at`,
  `deleted_batch_id`, `trash_expired_at` (для клиента — и контакты его пакета) с теми же
  проверками, что и API (сделка при удалённом клиенте — ошибка); событие `deal.restored` с
  `actor_id = NULL` для сделки — одно, в историю, ленту и аудит (FR-25c, FR-35, OI-116, AC-120).
  `project_id` не меняется: если связь была снята по OI-118, она не возвращается.
- Экспорт/импорт (R1.4): `gostracker export [--out PATH]` → tar-архив (`data.json` + `files/<storage_key>`),
  режим 0600. `data.json` = `{"format": "gostracker-export", "schema_version": "<alembic head>",
  "exported_at": "<UTC>", "tables": {"<table>": [rows…]}}`, строки отсортированы по PK,
  ключи отсортированы, `ensure_ascii=False`, `indent=2`; uuid — строки, `timestamptz` —
  ISO 8601 UTC с микросекундами и `Z`, `date` — `YYYY-MM-DD`, `bytea` нет (сессии не
  выгружаются). `gostracker import PATH`: проверка `schema_version == head` (иначе код 2);
  проверка «пустоты» (в бизнес-таблицах и `domain_event` нет строк; ровно один пользователь с
  `created_by IS NULL`; стадии — только созданные системой и не изменённые; иначе код 2);
  безопасное чтение архива (только `data.json` и `files/<hex>`); в одной транзакции
  `SET CONSTRAINTS ALL DEFERRED` → удаление автоданных (`user_session`, `workspace_member`,
  `app_user`, `stage`, `pipeline`, `workspace` — `domain_event` пуст и не трогается) → вставка
  всех таблиц с исходными id → `setval` для `domain_event.id`; файлы сверяются по sha256 и
  копируются; после фиксации удаляется `initial-admin-password.txt`. Коды выхода: 0 — успех,
  1 — ошибка выполнения, 2 — отказ по условиям (непустая система, другая версия схемы,
  бизнес-данные для demo-data).

### 4.11. Вложения (FR-24, R1.1)

```python
# app/domain/attachments/filetype.py
class DetectedType(NamedTuple):
    kind: Literal["png","jpeg","gif","webp","pdf","ole2","docx","xlsx","pptx","zip","text"]
    mime: str
class RejectedFile(Exception):
    reason: Literal["executable", "archive_with_executable", "not_allowed", "extension_mismatch", "unverifiable_archive"]
EXTENSION_KINDS: Final = {"png":{"png"}, "jpg":{"jpeg"}, "jpeg":{"jpeg"}, "gif":{"gif"}, "webp":{"webp"}, "pdf":{"pdf"},
    "doc":{"ole2"}, "xls":{"ole2"}, "ppt":{"ole2"}, "docx":{"docx"}, "xlsx":{"xlsx"}, "pptx":{"pptx"},
    "zip":{"zip"}, "txt":{"text"}, "csv":{"text"}, "md":{"text"}}
def detect(path: Path, original_name: str) -> DetectedType   # raises RejectedFile
```
Правила: сигнатуры PE (`MZ`), ELF (`\x7fELF`), Mach-O (`FEEDFACE/FEEDFACF/CAFEBABE` и
обратный порядок) → `executable`; PNG/JPEG/GIF/WEBP/PDF по магическим байтам; OLE2 (`D0CF11E0A1B11AE1`);
ZIP — по `zipfile`: OOXML по `[Content_Types].xml` + каталогу `word/`/`xl/`/`ppt/`, иначе
`zip`; для `zip` каждый элемент проверяется по имени (расширения exe, dll, com, bat, cmd,
msi, scr, ps1, vbs, js, jar, sh, apk, app) и первым 4 байтам; вложенные ZIP — рекурсивно: загружаемый
архив — уровень 1, проверяются уровни 1–3; ZIP на уровне 4, зашифрованный или повреждённый
элемент, превышение бюджета распаковки 100 МБ → `unverifiable_archive` (FR-24, OI-113, AC-117). Текст: нет байта `\x00` в первых 64 КБ и декодируется как UTF-8.
Тип по содержимому должен входить в множество для расширения, иначе `extension_mismatch`.
Любой `RejectedFile` → 422 `attachment_type_not_allowed`.

Загрузка: `POST /api/v1/tasks/{id}/attachments` (multipart, поле `file`) — потоковое
чтение во временный файл в `attachments/tmp/`, при превышении 10 485 760 байт → 413
`attachment_too_large`; 21-й файл → 422 `too_many_attachments`; затем `detect`, sha256,
`rename` в `attachments/<workspace_id>/<storage_key[:2]>/<storage_key>`; исходное имя — только
в столбце `original_name`. nginx: `client_max_body_size 12m`, его 413 отдаётся JSON
`{"detail": …, "code": "attachment_too_large"}`. Скачивание `GET /api/v1/attachments/{id}/content`:
`Content-Disposition: attachment; filename*=UTF-8''…`, `X-Content-Type-Options: nosniff`.

### 4.14. Фронтенд и генерация TS-типов

- `scripts/gen-api.sh`: `gostracker openapi --out docs/api/openapi.json` →
  `npm --prefix frontend run gen:api` (`openapi-typescript ../docs/api/openapi.json -o src/shared/api/schema.d.ts`).
  `operationId` = имя функции роутера (`generate_unique_id_function=lambda r: r.name`).
  CI: генерация + `git diff --exit-code docs/api frontend/src/shared/api/schema.d.ts`.
- `src/shared/api/client.ts`: `createClient<paths>({ baseUrl: "/", credentials: "same-origin" })`
  + middleware: ошибки → `ApiError {status, code, detail}`; 401 → сброс кэша и переход на `/login`;
  403 `password_change_required` → `/change-password`; 403 `no_role` → экран «нет роли».
- `src/shared/api/polling.ts`: `usePolledQuery(options)` = `useQuery` со своей цепочкой `setTimeout` (не `refetchInterval`: нужна пометка источника запроса); один таймер на ключ; якорь — `max(dataUpdatedAt, errorUpdatedAt)`: если данные моложе `POLL_INTERVAL_MS`, тик не шлёт запрос, а взводит дотик на остаток, поэтому между обновлениями не больше 15 с + время ответа (FR-29, AC-107); известный краевой случай: `refetch()` во время летящего фонового тика без данных присоединяется к нему и уходит с `X-GT-Background`;
  `queryFn` ставит `X-GT-Background: 1` для КАЖДОГО запроса, инициированного таймером опроса
  (независимо от того, есть ли у запроса данные: тик по определению повторяет запрос); первая
  загрузка, ручной `refetch()` и перезагрузка после мутации (`invalidateQueries`) — обычные
  запросы без заголовка, продлевают сессию (FR-29, FR-59, D-14).
  **Ревью T22:** прежняя формулировка `dataUpdatedAt > 0` помечала бы фоновым и действие
  пользователя; условие «есть данные» вредно в обратную сторону: после неудачной первой загрузки
  (5xx) тики шли бы без заголовка и неограниченно продлевали сессию открытого сломанного экрана. Опрос приостанавливается при `document.hidden`; 401,
  403 `password_change_required` и 403 `no_role` останавливают опрос (меняется состояние
  сессии), ошибки 5xx и сети — нет (транзиентные). Клиент: `baseUrl` — `"/"` (пути OpenAPI уже
  содержат `/api/v1`), на небезопасные методы всегда `Content-Type: application/json`;
  коды клиента `network_error` (status 0) и `invalid_response`; колбэк 401 снова
  взводится после любого успешного ответа.
- `src/shared/i18n/ru.ts` — словарь `as const`; `t(key: keyof typeof ru)`; строк интерфейса
  вне словаря нет (NFR-6); vitest-проверка ищет кириллицу в `src/**/*.tsx` вне `i18n/`.
- UI-кит `src/shared/ui`: видимый фокус (`:focus-visible` outline 2px), контраст AA (NFR-7).
- Тесты фронтенда — в `frontend/tests/**` (защищены хуком от исполнителя), vitest + jsdom.

|---|---|---|
| `PUT /api/v1/crm/deals/{deal_id}/project` `{project_id}` | CRM_WRITE | Сделка — неудалённая (иначе 404). ### 5.1. Методика NFR-2 (OI-37)

Инструмент: `backend/tools/nfr2_bench.py` (httpx.AsyncClient, HTTP/1.1 keep-alive, через
поставляемый HTTPS-вход `https://<host>` с `verify=False` для самоподписанного сертификата).
Подготовка: чистая система → `gostracker loadgen --seed 42` (50 000 задач в 20 проектах,
~30 % — подзадачи; 10 000 сделок; 5 000 клиентов; 15 000 контактов; события: создание каждой
задачи и сделки + 2–3 изменения → ~250 000 строк `domain_event`; 12 пользователей, пароли в
`/data/secrets/loadgen-passwords.txt`) → `VACUUM ANALYZE`. Параметры: 5 параллельных
клиентов (разные пользователи — 2 БА, 1 СМ, 2 П; СМ упразднена фичей 002 (ADR-0013) — состав
клиентов уточнить при возврате замера NFR-2), прогрев 20 запросов на тип запроса без учёта,
затем ≥ 100 замеров на тип запроса; p95 — по ближайшему рангу; время = от отправки до
получения полного тела. Каждая операция NFR-2 = набор запросов; норматив применяется к
каждому запросу набора:

| Операция | Запросы (страница 50) |
|---|---|
| Открытие списка задач | `GET /api/v1/projects/{id}/tasks?page=1`; `GET /api/v1/me/tasks?page=1`; `GET /api/v1/projects?page=1`; `GET /api/v1/crm/deals?page=1` |
| Открытие карточки задачи или сделки | `GET /api/v1/tasks/{id}` (с подзадачами, прогрессом, метками, метаданными вложений); `GET /api/v1/tasks/{id}/comments?page=1`; `GET /api/v1/crm/deals/{id}` (с контактами и связью); `GET /api/v1/crm/deals/{id}/tasks?page=1` |
| Сохранение изменений | `PATCH /api/v1/tasks/{id}` (title); `POST /api/v1/tasks/{id}/move`; `PATCH /api/v1/crm/deals/{id}` (stage_id) |
| Поиск и фильтрация | `GET /api/v1/search?q=<2–4 символа>`; `GET /api/v1/tasks?status=in_progress&due=overdue&assignee_id=…`; `GET /api/v1/tasks?project_id=…&due=next7`; `GET /api/v1/crm/deals?stage_id=…`; `GET /api/v1/crm/pipeline/summary` |
| Агрегация для ленты активности | `GET /api/v1/projects/{id}/activity?page=1`; `GET /api/v1/crm/deals/{id}/activity?page=1`; `GET /api/v1/crm/deals/{id}/history` |

Отчёт: JSON + таблица (тип запроса, n, p50, p95, max, норматив, «недопустимо»); код выхода 1,
если p95 превышает норматив (без `--no-thresholds`).

## 8. Риски

- **R-1. Локальный `.venv` на Python 3.14.** Возможны расхождения с эталоном 3.12; T01
  пересоздаёт окружение (`python3.12 -m venv --clear .venv`).
- **R-2. Ложная зелень из-за отката транзакций в тестах.** Забытая фиксация не видна в
  тестах с откатом. Митигация: фикстура `committed` для сквозных тестов и инфраструктурный
  прогон стека (AC-23 — смена пароля и повторный вход в реальном стеке).
- **R-3. AC-40 «TLS 1.1 отклонено».** Современные OpenSSL-клиенты могут сами не поддерживать
  TLS 1.1, и тест прошёл бы тривиально. Митигация: тест дополнительно проверяет
  `nginx -T` на `ssl_protocols TLSv1.2 TLSv1.3` и успешное соединение по TLS 1.2.
- **R-4. Порты 80/443 заняты на машине оператора** (NFR-3, 10 минут). Митигация: `HTTP_PORT`,
  `HTTPS_PORT` в `.env`; README описывает.
- **R-5. Предупреждение браузера о самоподписанном сертификате** (ADR-0004) — README ru/en.
- **R-6. Нагрузочная таблица `domain_event`** (~250 000 строк) и лента ≤ 2 с: частичные
  индексы §4.3, пагинация без COUNT. Проверяется в R1.4 до приёмки.
- **R-7. FastAPI тянет `opentelemetry-api`.** Без SDK вызовов нет; тест «нет SDK/экспортёров»
  в T19 (NFR-4).
- **R-8. Слабые исполнители и порядок проверок.** Нарушение порядка 403/404 — частая
  ошибка; сквозные тесты `test_route_guards.py` и `test_not_found_vs_forbidden.py`.
- **R-9. Блокировка входа как DoS** (ADR-0004) — принято для пилота.
- **R-10. Защищённые от исполнителя тесты фронтенда** — только в `frontend/tests/**` и
  `frontend/e2e/**` (хук `block-test-edits.py` не защищает `*.test.tsx` в `src/`).

### 10.2. Протокол блокировок R1.1

Порядок всегда один и тот же — без обратных зависимостей и, значит, без взаимоблокировок;
превышение `lock_timeout` — 503 (D-40):

1. **Изменение проекта** (правка полей, архив, владелец, участники, удаление, восстановление,
   окончательное удаление проекта): строка `project` — `FOR NO KEY UPDATE` сразу после гейтов.
2. **Изменение содержимого** (задачи, подзадачи, комментарии, вложения, метки задачи,
   восстановление и окончательное удаление объектов внутри проекта): строка `project` —
   `FOR SHARE` (сериализует с п.1: архивирование и исключение участника не проходят между
   проверкой и записью).
3. **Получатель** (участник, исполнитель, владелец): строки `app_user` и `workspace_member`
   получателя — `FOR SHARE` (сериализует с блокировкой и сменой роли, которые берут
   `FOR NO KEY UPDATE`, §4.6).
4. **Колонки доски**: `positions.lock_columns` — `pg_advisory_xact_lock(hashtext(project_id || ':' || status))`,
   одноключевая форма (не пересекается с двухключевой `_ACCOUNT_LOCK_NAMESPACE`), статусы в
   отсортированном порядке.
5. Строки задач, комментариев, вложений, упоминаний.

- `SearchTask {id, title, status, project: ProjectRef}`, `SearchProject {id, name, status}`.

### 10.6. Корзина R1.1 (уточнение §4.10)

| Тип | Право удалить = восстановить = окончательно удалить | 422 при восстановлении | 409 (архив, D-50) |
|---|---|---|---|
| project | `can_manage_project` (любой БА — фича 002, 002/FR-8; до неё — БА-владелец или СМ) | — | нет |
| task (и подзадача) | `can_delete_task` | проект удалён → `project_deleted`; родитель удалён → `parent_task_deleted` | да |
| comment | `can_delete_comment` (и участник) | задача удалена → `parent_task_deleted`; проект удалён → `project_deleted` | да |
| attachment | `can_delete_attachment` (и участник) | то же | да |

- Права оцениваются по текущим роли и членству (FR-67, FR-68) на фактах удалённого объекта;
  `actor_has_task` считает только неудалённые задачи (FR-19).
- Восстановление: строки с тем же `deleted_batch_id` (D-25); задача верхнего уровня —
  `place_after`, если позиция в колонке занята неудалённой задачей (AC-118); восстановление
  пишет `task.restored` только для задачи-корня пакета.
- `GET /trash` строится одним `UNION ALL` по типам с SQL-предикатами прав, эквивалентными
  функциям `policy` (тест: множество строк корзины = множество объектов, для которых
  `restore` разрешён, по всем ролям). Объект виден, пока строка существует (и после 30 дней —
  до запуска обслуживания).
- Окончательное удаление: `purge` удаляет строки (каскады FK, D-26), возвращает ключи файлов
  до `DELETE`; `domain_event` не трогается (AC-66). Снятие связи со сделкой при удалении
  проекта — R1.3 (§4.10 п.1, AC-91).

### 11.1. Цель и рамки

Решение владельца продукта (2026-10-15, строка под Q-8 §10.8): максимально ускорить прототип
таск-трекера для показа заказчику; CRM (R1.3) — в следующую версию продукта; MVP без
оверинжиниринга. Цель — **≤ 25 задач до демо** (получилось 25, из них 1 — синхронизация spec,

**Входит в MVP:** всё R1.0 (готово); проекты (создание, правка названия/описания, участники,

пометками [ВОПРОС ВЛАДЕЛЬЦУ] заменяет spec-writer по SC-22, SC-23 (§11.9); исполнители работают по
этому разделу.

#### 11.12.1. Подход

- `app_user.login` — **ключ** (нормализованный вид: ASCII, строчные). Вход
  (`normalize_login` → `reserve_attempt(where=AppUser.login == key)`), уникальность
  (`uq_app_user_login`, `ON CONFLICT (login)`), поиск `GET /users?q=` (`ILIKE` по ключу),
  сортировка `ORDER BY login, id` и счётчик FR-61 **не меняются**.
- Новый столбец `app_user.login_display` — написание, введённое при создании. Его читают **все**
  выборки, которые отдают логин наружу (§11.12.4).
- Имена полей API не меняются: `login` в `UserRef`, `DirectoryUser`, `AdminUser`,
  `SessionUser`/`LoginResponse`, `Me`, `AuditActor` содержит отображаемый логин. `docs/api/openapi.json`
  и `frontend/src/shared/api/schema.d.ts` **не меняются** (ограничение R-M6 к T93–T99 не
  применяется; `cli/test_openapi.py` и `infra/test_frontend_api_types.py` должны остаться
  зелёными без перегенерации).
- Логин неизменяем, как и раньше: ни один `UPDATE` не трогает `login`/`login_display`.

#### 11.12.2. Схема БД (изменение `app_user`)

| Столбец | Тип | NULL | Ограничения |
|---|---|---|---|
| `login` (без изменений) | varchar(64) | нет | `uq_app_user_login` UNIQUE (уже есть, миграция 0001 — проверено); `ck_app_user_login_format`: `login ~ '^[a-z0-9][a-z0-9._-]{2,63}$'` (без изменений) |
| `login_display` (новый) | varchar(64) | нет | `ck_app_user_login_display_lower`: `lower(login_display COLLATE "C") = login` |

Почему одного CHECK достаточно: `lower(… COLLATE "C")` меняет только `A–Z` → `a–z` и оставляет
прочие символы как есть. Значит, `login_display` совпадает с `login` с точностью до регистра
латинских букв; вместе с `ck_app_user_login_format` это гарантирует ASCII и шаблон FR-73 без
учёта регистра. Знак Кельвина, кириллица, пробелы — нарушение CHECK (U+212A не приводится к `k`).
Отдельный UNIQUE на `login_display` не нужен: равные `login_display` дают равные `login`.
Индекс на `login_display` не нужен: по нему не ищут и не сортируют.

#### 11.12.3. Миграция `0005_login_display.py`

```python
revision = "0005"; down_revision = "0004"
_CHECK = "ck_app_user_login_display_lower"

def upgrade() -> None:
    op.add_column("app_user", sa.Column("login_display", sa.String(length=64), nullable=True))
    op.execute("UPDATE app_user SET login_display = login")          # backfill: как до обновления
    op.alter_column("app_user", "login_display", existing_type=sa.String(length=64), nullable=False)
    op.create_check_constraint(op.f(_CHECK), "app_user", 'lower(login_display COLLATE "C") = login')

def downgrade() -> None:
    op.drop_constraint(op.f(_CHECK), "app_user", type_="check")
    op.drop_column("app_user", "login_display")                      # написание теряется (R-M10)
```

Блокировки: `ADD COLUMN` без `DEFAULT` — только каталог; `UPDATE`, `SET NOT NULL` и `ADD
CONSTRAINT CHECK` сканируют `app_user` под `ACCESS EXCLUSIVE` — единицы–десятки строк
(пилот: 13 пользователей демо), миллисекунды. Миграции выполняет `gostracker bootstrap` до
старта API под advisory-блокировкой (§4.7, §4.12), `env.py` ставит `lock_timeout = 0`. Схема
`NOT VALID` + `VALIDATE` и пакетный backfill отвергнуты: выигрыша на таком объёме нет, а шагов
и точек отказа больше. Оператору ничего делать не нужно (FR-73a): обновление образа →
`bootstrap` → `upgrade head`.

#### 11.12.4. Модель и интерфейсы

```python
# app/domain/users/models.py
def _login_display_default(context: DefaultExecutionContext) -> str:
    """Не передан — равен ключу (демо-логины, фабрики тестов): строка как до v0.17 (FR-73a)."""
    return str(context.get_current_parameters()["login"])
```

#### 11.12.5. Уникальность и параллельное создание

- Проверка «занят» и вставка идут по ключу: `Ivanov.Petr`, `ivanov.petr`, `IVANOV.PETR` → ключ
  `ivanov.petr`.
- Одно пространство: `create_user` после хеширования берёт `pg_advisory_xact_lock` пространства
  (`_lock_for_account_change`) — создания идут по очереди; второе выполняет
  `INSERT … ON CONFLICT (login) DO NOTHING` после фиксации первого, видит конфликт по
  `uq_app_user_login` → `RETURNING` пуст → 422 `login_taken`, события нет.
- Разные пространства (логин глобален, advisory-ключи разные): второй `INSERT` ждёт фиксации
  первой транзакции на уникальном индексе; фиксация первой → `DO NOTHING` → 422 `login_taken`;
  откат первой → вставка проходит. Новые блокировки и индексы не нужны.
- Предварительная проверка «занят» (до хеширования) — только быстрый путь; источник истины —
  уникальный индекс.
