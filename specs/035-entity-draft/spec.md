# Spec: черновик сущностей из текста (`propose_entities`)

- **ID:** 035-entity-draft
- **Статус:** DRAFT
- **Дата:** 2026-11-16
- **Кастдев:** CD-06, 2026-11-16
- **ADR:** 0031 (атрибуция); миграции нет
- **Связано:** спека 022 (CD-05), ADR-0018

## 1. Контекст и цель
ПМ размечает сущности из текста вручную. Агент уже в MCP: нужен инструмент, который
из текста предлагает задачи / инциденты / заметки и пишет в БД только по явному
`commit=true`. Без commit записей нет. Ошибка разбора не создаёт задач.

## 2. Пользовательские сценарии
- Как агент, я хочу передать текст и получить черновик сущностей, не меняя трекер.
- Как ПМ, я хочу, чтобы запись появилась только после `commit=true`.
- Как ПМ, я хочу, чтобы битый текст не оставлял частичных задач.

## 3. Функциональные требования
- **FR-1:** MCP-инструмент `propose_entities` (запись). Аргументы: `text` (1–20000),
  `commit` (по умолчанию `false`), `project_id` (необязательный UUID проекта по умолчанию).
- **FR-2 (разбор):** `text` — JSON-массив объектов или строки вида
  `task: …` / `incident: …` / `note: …`. Элемент: `type` (`task`|`incident`|`note`),
  `title` (1–255), опционально `project_id`, `existing_task_id`.
  После `|` в строке допустимы `project_id=<uuid>` и `existing_task_id=<uuid>`.
- **FR-3:** Без `commit=true` ответ содержит `drafts` и пустой `committed`;
  **0** новых строк в `task` и `comment`.
- **FR-4:** С `commit=true` для каждого элемента: `task` и `incident` — `create_task`
  (описание = название, срок = сегодня MSK); `incident` плюс комментарий «блокер»
  (поля `blocked` в этом срезе нет). `note` с `existing_task_id` — `add_comment`
  с телом = название; без него — `create_task`. Проект: у элемента или аргумент
  `project_id`. Поле `blocked` не трогать.
- **FR-5:** Ошибка разбора или нет ни одной сущности — 422 `entity_parse_error`,
  ни одной записи. При `commit` сначала проверяются все элементы, затем запись
  в одной транзакции вызова MCP.
- **FR-6:** События создания несут `client_name` токена (ADR-0018).

## 4. Нефункциональные требования
- **NFR-1:** без миграции, без LLM на сервере: детерминированный разбор.
- **NFR-2:** описание инструмента ≤ 100 символов (MCP / ruff).

## 5. Критерии приёмки
- **AC-1:** Given валидный текст When `commit` отсутствует или `false` Then `drafts` непусты,
  `committed` пуст, `count(*)` задач проекта не меняется.
- **AC-2:** Given `task: Новая` и `project_id` When `commit=true` Then создана задача с этим
  названием; событие `task.created` с `client_name` токена.
- **AC-3:** Given мусорный текст When вызов Then 422 `entity_parse_error` и 0 новых задач,
  в том числе при `commit=true`.
- **AC-4:** Given `incident: Падение` When `commit=true` Then задача и комментарий «блокер».
- **AC-5:** Given `note: Уточнить` и `existing_task_id` When `commit=true` Then новый
  комментарий у этой задачи, новой задачи нет.

## 6. Вне рамок
- LLM на сервере; ingest Telegram (CD-02); поле `blocked` (CD-03); шаблон DoD.

## 7. Допущения
- Права как у `create_task` / `add_comment`.
- Колонки `task.blocked*` в этом срезе нет: инцидент = задача + комментарий «блокер».
