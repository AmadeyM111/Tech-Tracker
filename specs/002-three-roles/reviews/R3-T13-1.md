# Ревью R3-T13, попытка 1 — CHANGES_REQUESTED (только тесты)

Код миграции `0006_three_roles.py` и модели дословно соответствует plan §4.5/§4.6 и корректен по spec (FR-2, FR-13…FR-17, AC-2, AC-20…AC-22, AC-29). Продуктовый код менять не нужно.

Прогоны (только `*_test`, без полного набора): 4 db-файла задачи 176 passed; 32 файла миграций/ролей 1499 passed; `alembic check` (с `-x dburl` на `tracker_test`) чисто; ruff, format, mypy чисто. Туда-обратно на пустой отдельной БД (`downgrade base` → `upgrade head` → `downgrade -1` → `upgrade head` → `check`) чисто. Проба AC-29 в копии: без триггера rc=0; с триггером на version/event сбой срабатывает после снятия ролей и записи журнала (13 записей, mixed=0), после отката версия 0005, роли mixed на месте, журнал прежний; повтор после снятия сбоя даёт результат AC-20. `env.py` не менялся, всё идёт одной транзакцией, `bootstrap` использует тот же `env.py`. Рабочая БД и контейнеры не затрагивались; `tracker_test` на ревизии 0006.

## Мутации (копия, отдельная тестовая БД)
Убиты: без `NOT is_blocked`; «активный ТА» глобально; без INSERT в журнал; `actor_id` не NULL; CHECK раньше UPDATE; заблокированным СМ давать tech_admin; tech_admin незаблокированным СМ при наличии активного ТА; заблокированный ТА считается активным; ТА с одноразовым паролем считается неактивным; СМ с одноразовым паролем не получает ТА; перестановка removed/changed; `role_from` NULL; `in_audit` false; другой `entity_type`; `ORDER BY login DESC`; `clock_timestamp()`; чужой `workspace_id`; downgrade оставляет 3 значения / возвращает mixed в данные.
**Выжили:** (е) без `updated_at = now()`; `updated_at` у всех строк `workspace_member`; UPDATE только по `user_id` без `workspace_id` (нет случая «один пользователь в двух пространствах»); без `ON COMMIT DROP` (эквивалентная мутация: сессия alembic закрывается, таблица исчезает при любом коде); без `LOCK TABLE` (однопоточным тестом не проверяется — ожидаемо).

## BLOCKING (test-writer, только тесты)
1. `upgrade002_support.py:~408-426` (`data_fingerprint` исключает `updated_at` у всех строк `workspace_member`), `test_three_roles_upgrade.py:~131-154` (`_assert_ac20_result`) и AC-22 тесты (~368-447): ни один тест не проверяет `workspace_member.updated_at` (plan §4.5: миграция трогает только `role`, `updated_at` у бывших СМ и `domain_event`; `set_role` обновляет `updated_at`). Проверить: у бывших СМ `updated_at == occurred_at` новых записей журнала (одно `now()` транзакции — точное сравнение); у остальных строк `updated_at` не изменился (включить его в отпечаток для строк, которые не были `mixed`).

## NON-BLOCKING
1. `fr16_per_workspace` (~482-512): добавить пользователя с `business_admin` в ws1 и `mixed` в ws2 (D-5) и проверить, что роль в ws1 не изменилась (мутация «UPDATE без `workspace_id`»).
2. `test_..._no_temp_table_left` (~243-267): проверка временной таблицы проходит при любом коде — убрать из названия/docstring или пометить как формальную защиту на будущее.
3. `upgrade002_support.py:~437-439` и plan D-8: триггер `AFTER INSERT … FOR EACH ROW` срабатывает после всех вставок (13 записей), а не «посреди записи журнала»; поправить формулировку или взять `BEFORE INSERT`.
4. Блокировки (R-9/D-9): порядок миграции `ACCESS EXCLUSIVE` на `workspace_member`, затем `SHARE` на `app_user`; циклов с путями входа/`get_actor` не найдено; миграция откатывается целиком при дедлоке (FR-17). Остаточный риск: при ручном запуске на живом API с `lock_timeout = 0` миграция ждёт без ограничения, новые запросы встают за ней в очередь — описать в ADR-0013.
5. Остальная кодовая база: `mixed` в `backend/app` больше нет, «СМ» осталось только в docstring шести файлов R3-T12; docstring `roles.py:18` снова верен; ревизия 0005 нигде не зашита в код, упоминания — README:211/568 и docstring `bootstrap.py:269` (R3-T17).

## Для владельца: что сделать перед обновлением рабочего стека (в README/ADR-0013, R3-T16/T17)
1. Резервная копия: `pg_dump` из `gostracker-db-1` (и из `gostracker-web-db-1`, если обновляется второй стек); тома не трогать.
2. Заранее записать, у кого роль `mixed` и есть ли активный ТА (`SELECT … WHERE role='mixed'`): видно, кто станет «без роли», а кто получит ТА по FR-16.
3. Обновлять только `docker compose up -d --build` одним выпуском R3-T11…T13; промежуточные образы не разворачивать, `uvicorn` без `bootstrap` не запускать.
4. После обновления проверить: `alembic_version` = 0006; по записи `user.role_removed`/`user.role_changed` с `actor_id IS NULL` на каждого бывшего СМ; у бывших СМ роль `NULL` или `tech_admin`; вход ТА работает.
5. При сбое контейнер API не стартует, БД остаётся на 0005 (AC-29); повторный запуск безопасен.
6. Откат (`downgrade 0005` или восстановление копии) роли `mixed` не возвращает: ТА восстанавливает вручную по журналу (spec §7). При восстановлении копии 001 на код 002 перезапустить api.
