# Spec: Роли БД и защита журнала

- **ID:** 010-db-roles
- **Статус:** APPROVED (ответы владельца на §8 — 2026-11-08)
- **Дата:** 2026-11-08
- **Пакет:** R2 T-02 (R2-34, R2-35, R2-37). Основание: `r2-dev-task-list.md` (T-02), решения владельца
  2026-11-08 (состав R2).

## 1. Контекст и цель
Сейчас API работает под ролью `POSTGRES_USER` — в образе `postgres:16` это суперпользователь и
владелец всех таблиц. Триггеры `domain_event` (миграция 0002) запрещают UPDATE/DELETE/TRUNCATE, но
владелец или суперпользователь может их отключить (plan 001 D-8). Пакет переводит работающий API на
отдельную роль без привилегий, чтобы взлом приложения не давал переписать журнал аудита.

## 2. Пользовательские сценарии
- Как ИБ заказчика, я хочу, чтобы процесс API не мог изменить или удалить записи журнала аудита.
- Как оператор, я обновляю стек обычным `up -d`: роль и её пароль создаются сами, без ручных шагов.

## 3. Функциональные требования
- **FR-1 (рабочая роль, R2-34):** `gtrack bootstrap` ДОЛЖЕН создавать (или приводить к нужному
  виду) роль `DB_APP_ROLE` (по умолчанию `gtrack_app`): `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
  NOREPLICATION NOBYPASSRLS`, без владения объектами.
- **FR-2 (права):** роль ДОЛЖНА получать `USAGE` на схему `public`; `SELECT, INSERT, UPDATE, DELETE` на
  таблицы, кроме `domain_event` (только `SELECT, INSERT`) и `alembic_version` (только `SELECT`);
  `USAGE, SELECT` на последовательности. `TRUNCATE`, `CREATE` в схеме и `REFERENCES`/`TRIGGER` — нет.
  Права выдаются заново при каждом bootstrap (новые таблицы из новых миграций получают права).
- **FR-3 (владелец миграций, R2-34):** миграции и bootstrap ДОЛЖНЫ выполняться под ролью из
  `DATABASE_URL` (владелец схемы); API (uvicorn) ДОЛЖЕН подключаться под `DB_APP_ROLE`.
- **FR-4 (пароль, R2-35):** пароль рабочей роли ДОЛЖЕН генерироваться при первом bootstrap (≥ 32
  случайных байт, base64url) и храниться в `DATA_DIR/secrets/db_app_password` (0600); в
  `.env.example` его нет. На сервер БД пароль ДОЛЖЕН передаваться только как SCRAM-SHA-256-верификатор
  (открытый текст не попадает в журнал PostgreSQL).
- **FR-5 (переход, R2-35):** на действующей установке обновление образа и перезапуск api ДОЛЖНЫ
  выполнить переход сами (роль, пароль, права); ручных SQL-шагов нет. Порядок описан в README.
- **FR-6 (журнал):** триггеры 0002 ДОЛЖНЫ остаться; под рабочей ролью `UPDATE`, `DELETE`, `TRUNCATE`
  `domain_event` и `ALTER TABLE domain_event DISABLE TRIGGER` ДОЛЖНЫ отклоняться.
- **FR-7 (отключение):** `DB_APP_ROLE=""` ДОЛЖНО оставлять прежнее поведение (API под `DATABASE_URL`) —
  для разработки; в `ENV=production` пустое значение ДОЛЖНО ронять старт API с понятной ошибкой.

## 4. Нефункциональные требования
- **NFR-1:** миграций схемы нет (роли — объекты кластера, создаются bootstrap); R2 NFR-07 соблюдён.
- **NFR-2:** простой при переходе — один перезапуск api (секунды).
- **NFR-3:** пароль роли не попадает в stdout, stderr, лог приложения, argv и тексты исключений.

## 5. Критерии приёмки
- **AC-1** (FR-1): Given bootstrap на `*_test` When читаем `pg_roles` Then у роли нет SUPERUSER,
  CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS; `pg_class` не содержит объектов с её владением.
- **AC-2** (FR-6): Given соединение под рабочей ролью When `UPDATE/DELETE/TRUNCATE domain_event` и
  `ALTER TABLE domain_event DISABLE TRIGGER ALL` Then ошибка прав (42501) или «must be owner».
- **AC-3** (FR-2): Given рабочая роль When `INSERT`/`SELECT domain_event`, CRUD `task` Then успех;
  `CREATE TABLE public.x` и `TRUNCATE task` Then отказ.
- **AC-4** (FR-3): Given приложение со стандартными настройками When вход, создание проекта и задачи по
  HTTP Then успех, а `current_user` соединений API = `DB_APP_ROLE`.
- **AC-5** (FR-2, повтор): Given новая таблица после bootstrap When bootstrap повторно Then у роли права на неё.
- **AC-6** (FR-4): Given первый bootstrap Then файл `db_app_password` 0600; второй bootstrap пароль не меняет;
  `pg_authid` хранит `SCRAM-SHA-256$…`; в выводе bootstrap пароля нет.
- **AC-7** (FR-7): Given `ENV=production` и `DB_APP_ROLE=""` When старт API Then ошибка запуска.
- **AC-8** (FR-5): Given стек на коде до 010 When обновление по README Then API работает под новой ролью,
  данные целы (ручная проверка на стенде, `docs/acceptance/mvp-demo.md`).

## 6. Вне рамок
`pg_trgm` (T-08, R3) — создаст миграция под владельцем, когда понадобится; RLS; отдельный
не-суперпользователь-владелец вместо `POSTGRES_USER`; ротация пароля по расписанию.

## 7. Допущения
- `POSTGRES_USER` остаётся владельцем схемы; `gtrack backup`, `restore`, `export`, `import`,
  `maintenance` работают под ним (команды оператора, не процесс API).
- MCP-эндпоинт работает в процессе API и получает ту же рабочую роль.

## 8. Решения по вопросам (владелец, 2026-11-08)
- Q-1: владелец схемы — суперпользователь `POSTGRES_USER`, только для CLI оператора; для R2 достаточно.
- Q-2: имя роли — `gtrack_app`.
- Q-3: выкатывается вместе с 009 одним перезапуском api.
