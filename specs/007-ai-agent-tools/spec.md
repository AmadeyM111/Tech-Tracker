## 0. Нумерация, термины, исходное состояние

- Нумерация своя: `FR-n`, `NFR-n`, `AC-n`, `Q-n` (вопросы владельцу), `D-n` (допущения
  аналитика). Ссылки на другие спецификации — с префиксом: `001/FR-18`, `002/FR-9`,
  `006/FR-23`. Номера после утверждения не меняются.
- **Агент** — внешняя программа на базе языковой модели (например, Claude Code). Она работает
  с трекером через программный интерфейс, а не через браузер.
- **Учётная запись агента** — учётная запись в рабочем пространстве, под которой работает
  агент (FR-1): без пароля и входа в браузер, работает только по ключу (Q-1, вариант а).
- **Ключ доступа (ключ)** — секретная строка. Она выдаётся учётной записи агента и
  аутентифицирует запросы без пароля и cookie-сессии (FR-5…FR-16).
- **Операции агента** — закрытый перечень действий FR-18…FR-27, доступных по ключу (FR-17).
- **Инструменты агента** — те же операции, оформленные для подключения агента по протоколу MCP
  (FR-35).
- **Обычный API** — существующие маршруты `/api/v1` с cookie-сессией `gt_session` (001).
- **Статусы** (001/FR-18a): `todo` — «К выполнению», `in_progress` — «В работе», `review` — «На
  проверке», `done` — «Выполнена». **Закрыть задачу** — перевести её в `done`. Отдельного поля
  «закрыта» в системе нет (001/FR-18a).
- **Сегодня** — календарная дата по Europe/Moscow (001/FR-18, ADR-0007).

**Исходное состояние (проверено по коду на `f7f19cf`):**
- Аутентификация есть только по cookie-сессии. Ключей API, сервисных учётных записей,
  заголовка авторизации и MCP нет (context.md).
- Переходы между статусами не ограничены: разрешён любой из четырёх статусов в любой.
  Значение вне набора — 422.
- Комментарии к задачам есть (001/FR-23): чтение, создание, правка своего, удаление. Длина
  текста 1–10 000 символов, HTML вырезается.
- В хранилище событий пишутся только действия с учётными записями и передача владения
  проектом. Создание, изменение и удаление задач и комментариев событий НЕ пишут ни для
  каких авторов. Типы `task.created`, `task.updated`, `comment.created`, `comment.deleted`
  объявлены в каталоге событий, но не используются. Отсутствие таких событий у демо-данных
  проверяет тест `test_d55_no_project_or_task_events`. В spec 001 отложена лента активности
  проекта (001/SC-8, FR-38, ADR-0012), то есть показ событий, а не их запись. Не писать
  события задач и комментариев решил plan 001 (001 plan D-55: без ленты их некому читать).
  Требованием spec 001 это не является. Ленты в интерфейсе и API нет.
- События задач и комментариев к журналу аудита не относятся и в нём не показываются (D-4).
- **Изменение в дельте 007** (решение владельца 2026-10-30): задачи и комментарии начинают
  писать события в хранилище для всех авторов, людей и агентов (FR-42). Это новое поведение,
  а не существующее. Ленты в интерфейсе и API по-прежнему нет (раздел 6).
- В журнал аудита пишутся действия с учётными записями: создание, блокировка, сброс пароля,
  завершение сессий, роли.
- Логи маскируют значения ключей `password|secret|token|cookie|authorization` (001/FR-57).
- Ограничения частоты запросов нет. Есть только блокировка входа после 5 неудачных попыток
  (ADR-0004).

## 1. Контекст и цель

Сейчас трекером пользуются только люди через браузер. Пользователь хочет, чтобы ИИ-агент
(например, Claude) вёл в трекере свою работу: заводил задачи, брал их в работу, отправлял на
проверку, закрывал и оставлял результат в комментарии. Тогда человек видит работу агента в той
же доске и списках, что и работу коллег. Нужен программный доступ без браузера, пароля и
cookie. Учётные данные агента должны отзываться в любой момент. Каждое действие агента должно
быть видно как действие агента. Права агента не шире прав выданной ему роли (002), правила
обязательных полей (006) действуют и для него. Существующие интерфейс и API не должны
сломаться.

## 2. Пользовательские сценарии

- Как агент, я хочу создать в проекте задачу на свою работу, чтобы человек видел, чем я занят.
- Как агент, я хочу получить список задач, где я исполнитель, и задачи проекта, чтобы выбрать
  следующую работу и не делать её дважды.
- Как агент, я хочу перевести задачу «К выполнению» → «В работе» → «На проверке» →
  «Выполнена», чтобы статус на доске отражал реальный ход работы.
- Как агент, я хочу оставить в задаче комментарий с результатом: что сделано, ссылки,
  ограничения.
- Как агент, я хочу при ошибке получить понятный ответ («нет описания», «срок в прошлом»,
  «нет прав»), чтобы исправить запрос без помощи человека.
- Как техадминистратор, я хочу завести учётную запись агента, выдать ей ключ и отозвать его,
  если ключ утёк или агент больше не нужен.
- Как бизнес-администратор, я хочу добавить агента в проект и ставить ему задачи, как
  сотруднику.
- Как участник проекта, я хочу видеть, какие задачи и комментарии сделал агент, а не человек.

## 3. Функциональные требования

### 3.1. Учётная запись агента

- **FR-1 (учётная запись агента).** Агент ДОЛЖЕН работать под собственной учётной записью
  рабочего пространства с признаком «агент». Отдельной роли «Агент» нет: права берутся из
  ролей 002 (FR-2, FR-3).
  - ТА создаёт учётную запись агента так же, как обычную (001/FR-4, 002/FR-3): логин, роль,
    признак «агент».
  - Признак задаётся только при создании и потом не меняется.
  - Пароля у учётной записи агента нет. Вход по логину и паролю ДОЛЖЕН отклоняться тем же
    ответом, что неверный пароль (401 `invalid_credentials`, ADR-0004).
  - Одноразового пароля и требования сменить его (001/FR-55) у учётной записи агента нет.
    Сбросить ей пароль нельзя: попытка ТА — 422.
  - Во всём остальном учётная запись агента — обычный пользователь:
    - её можно добавить в проект (002/FR-8);
    - её можно назначить исполнителем (001/FR-20, FR-70);
    - она бывает автором задач и комментариев;
    - она видна в справочнике пользователей и в «Учётных записях».
- **FR-2 (роль агента).** Учётная запись агента ДОЛЖНА иметь роль «Пользователь» или
  «Бизнес-администратор» либо быть без роли (001/FR-66). Назначить ей роль ТА при создании или
  сменой роли нельзя: 422, роль не меняется, запись в журнал не пишется. Причина: роль ТА не
  даёт доступа к задачам (002/FR-4), а ключ с правами администрирования учётных записей
  противоречит FR-17.
- **FR-3 (права не шире роли).** По ключу агент ДОЛЖЕН иметь ровно права своей роли по
  действующей матрице 002, раздел 5.2, с правилами 001/FR-19…FR-23 и 006. Если человек с той же
  ролью и тем же членством не может выполнить операцию через обычный API, агент её тоже не
  выполнит. Доступ к содержимому проекта агент получает только через участие в проекте
  (001/FR-17, 002/FR-10). FR-17 дополнительно сужает набор доступных операций.
- **FR-4 (блокировка и роль).**
  - Блокировка учётной записи агента (001/FR-5) ДОЛЖНА сразу отзывать все её ключи. Следующий
    запрос по любому из них получает 401.
  - Разблокировка отозванные ключи не восстанавливает.
  - Смена и снятие роли действуют со следующего запроса по ключу (001/FR-67). Ключи при этом
    не отзываются. Без роли агент получает 403 `no_role` на все операции агента.

### 3.2. Ключи доступа

- **FR-5 (выпуск).** ТА ДОЛЖЕН мочь выпустить ключ для учётной записи агента. Выпускает и
  отзывает ключи (FR-8) только ТА.
  - При выпуске задаются название (1–100 символов, без NUL) и, по желанию, срок действия.
    Если срок не задан, применяется срок по умолчанию (FR-9).
  - Выпуск ключа для учётной записи без признака «агент» ДОЛЖЕН отклоняться с 422.
  - Выпуск для заблокированной учётной записи ДОЛЖЕН отклоняться с 422.
  - Попытка БА, «Пользователя», учётной записи без роли или агента по ключу ДОЛЖНА
    отклоняться с 403. Ключ не создаётся.
- **FR-6 (секрет показывается один раз).**
  - Секрет ключа ДОЛЖЕН возвращаться только в ответе на выпуск.
  - Получить его повторно НЕ ДОЛЖНО быть возможно никому: ни через API, ни в интерфейсе, ни
    ТА, ни оператору.
  - Система ДОЛЖНА хранить ключ только в виде, из которого секрет нельзя восстановить.
- **FR-7 (перечень ключей).** ТА ДОЛЖЕН видеть ключи учётной записи агента. По каждому ключу
  показываются:
  - идентификатор и название;
  - кто и когда выпустил;
  - срок действия;
  - время последнего использования (FR-16) или «не использовался»;
  - состояние: «действует», «истёк» или «отозван» (с временем отзыва).

  Секрета и любой его части в перечне нет.
- **FR-8 (отзыв).** ТА ДОЛЖЕН мочь отозвать любой ключ учётной записи агента.
  - После отзыва любой запрос по этому ключу получает 401 (FR-13).
  - Отзыв необратим.
  - Отзыв уже отозванного или истёкшего ключа — успешный ответ без изменений и без новой
    записи в журнале (D-5).
- **FR-9 (срок действия).** У каждого ключа ДОЛЖЕН быть срок действия: по умолчанию 90 суток,
  не больше 365 суток с момента выпуска. Бессрочных ключей нет.
  - Срок в прошлом, нулевой или больше максимума — 422, ключ не создаётся.
  - С момента окончания срока любой запрос по ключу получает 401.
  - Продлить срок нельзя: выпускается новый ключ.
- **FR-10 (число ключей).** У учётной записи агента ДОЛЖНО быть не больше 5 действующих
  ключей. Выпуск шестого — 422, ключ не создаётся. Отозванные и истёкшие ключи в лимит не
  входят.
- **FR-11 (журнал аудита).** Выпуск и отзыв ключа ДОЛЖНЫ записываться в журнал аудита
  (001/FR-41), по одной записи на действие. В записи:
  - действие;
  - автор (ТА);
  - затронутая учётная запись агента;
  - идентификатор и название ключа;
  - время (UTC).

  Секрета в журнале нет. Окончание срока записей не создаёт. При блокировке (FR-4) пишется
  одна запись о блокировке по 001/FR-41, отдельные записи об отзыве ключей не пишутся.
  Журнал только дописывается.

### 3.3. Аутентификация по ключу

- **FR-12 (субъект запроса).** Запрос с действующим ключом ДОЛЖЕН выполняться от имени
  учётной записи агента, владеющей ключом, в её рабочем пространстве. Пароль, cookie и
  предварительный вход не нужны.
  - Ключ передаётся в заголовке запроса.
  - Ключ в адресе запроса (путь, параметры) запрос не аутентифицирует: ответ 401.
- **FR-13 (единый отказ).** Запрос по ключу ДОЛЖЕН получать 401 с телом
  `{"detail": "Требуется вход в систему", "code": "not_authenticated"}`, одинаковым во всех
  случаях:
  - ключ пустой, не по формату или неизвестен;
  - ключ отозван или истёк;
  - учётная запись заблокирована или не состоит в рабочем пространстве.

  По ответу нельзя определить причину отказа. Если в запросе есть и ключ, и cookie-сессия,
  запрос аутентифицируется только по ключу. При недействительном ключе ответ 401 даже при
  действующей cookie-сессии.
- **FR-14 (гейты).** К запросам по ключу ДОЛЖНЫ применяться те же гейты, что к сессии
  (001/FR-66, FR-67, 002/FR-3):
  - без роли — 403 `no_role`;
  - объектные права — по FR-3.

  Роль, блокировка и членство читаются на каждый запрос.
- **FR-15 (без сессии).** Запрос по ключу НЕ ДОЛЖЕН создавать, продлевать или завершать
  cookie-сессии и НЕ ДОЛЖЕН устанавливать cookie в ответе.
- **FR-16 (последнее использование).** Время последнего успешного запроса по ключу ДОЛЖНО
  отражаться в перечне FR-7 с точностью не хуже 5 минут.

### 3.4. Операции агента

- **FR-17 (объём доступа по ключу).** По ключу ДОЛЖНЫ быть доступны только операции
  FR-18…FR-27, даже если роль учётной записи агента разрешает больше. Любой другой запрос API
  по ключу ДОЛЖЕН получать 403 `forbidden`, данные не меняются. Это касается, в том числе:
  - удаления задач и подзадач;
  - правки и удаления комментариев;
  - управления проектами и участниками, передачи владения;
  - переноса карточки по доске с указанием соседей;
  - учётных записей, ролей, ключей и журнала аудита;
  - выхода и смены пароля.
- **FR-18 (кто я).** Агент ДОЛЖЕН мочь получить сведения о своей учётной записи:
  идентификатор, логин, роль, признак «агент».
- **FR-19 (проекты).** Агент ДОЛЖЕН мочь получить список проектов, где его учётная запись —
  участник: идентификатор, название, владелец. Проектов, где он не участник, в списке нет, в
  том числе у агента-БА. Каждый ключ действует во всех проектах, где учётная запись агента —
  участник. Область действия ключа задаётся только членством: БА добавляет агента в проект
  или исключает из него (002/FR-8). Ограничить отдельный ключ списком проектов нельзя.
- **FR-20 (мои задачи).** Агент ДОЛЖЕН мочь получить постраничный список задач и подзадач
  всех своих проектов, где он исполнитель. Порядок и состав — по 001/FR-26.
- **FR-21 (задачи проекта).** Агент ДОЛЖЕН мочь получить постраничный список задач и
  подзадач проекта с фильтрами по статусу и исполнителю (001/FR-27).
  - Проект, где агент не участник, — 403.
  - Несуществующий или удалённый проект — 404.
- **FR-22 (карточка задачи).** Агент ДОЛЖЕН мочь получить карточку задачи проекта, где он
  участник. В карточке:
  - все поля задачи, автор, исполнитель;
  - подзадачи и прогресс (001/FR-22);
  - ссылка на родителя у подзадачи (006);
  - права агента на эту задачу: правка, смена статуса, смена исполнителя, создание
    подзадачи. Состав прав тот же, что в карточке обычного API.
- **FR-23 (создание задачи).** Агент ДОЛЖЕН мочь создать задачу верхнего уровня в проекте,
  где он участник, по правилам 001/FR-18, FR-18a, FR-20 и 006:
  - название 1–255 символов;
  - описание обязательно и не пусто после обрезки пробелов, до 10 000 символов;
  - срок обязателен, `YYYY-MM-DD`, не раньше «сегодня»;
  - исполнитель по умолчанию — сам агент;
  - приоритет `low`, `medium` или `high`, по умолчанию `medium`;
  - статус новой задачи — `todo`.

  Назначить другого исполнителя может только агент с ролью БА (001/FR-19a, 002/FR-9), и
  исполнитель должен быть участником проекта (001/FR-20).
- **FR-24 (создание подзадачи).** Агент ДОЛЖЕН мочь создать подзадачу по 001/FR-19b, FR-21 и
  006: достаточно названия, вложенность — один уровень. Права — как у его роли.
- **FR-25 (смена статуса и закрытие).** Агент ДОЛЖЕН мочь перевести задачу или подзадачу в
  любой из четырёх статусов, если его роль это разрешает (001/FR-19b):
  - агент-«Пользователь» — свою задачу или задачу, где он исполнитель;
  - агент-БА — любую задачу проекта, где он участник.

  Правила:
  - Переходы не ограничены, как сейчас: из любого статуса в любой, включая возврат из
    `done`.
  - Закрытие — перевод в `done`.
  - Значение вне набора — 422 `validation_error`, статус не меняется.
  - Установка текущего статуса — успешный ответ без изменений и без нового события.
  - Смена статуса задачи верхнего уровня, у которой срок уже в прошлом или описание пусто
    (данные до 006), ДОЛЖНА выполняться: проверяются только меняющиеся поля (006/FR-23).
  - Задача верхнего уровня после смены статуса оказывается в колонке нового статуса на доске
    по тем же правилам, что при смене статуса в карточке через обычный API.
- **FR-26 (изменение полей).** Агент ДОЛЖЕН мочь изменить название, описание, срок, приоритет
  и исполнителя задачи или подзадачи в пределах прав роли:
  - полная правка — 001/FR-19;
  - смена исполнителя — только БА, 001/FR-19a;
  - для задачи верхнего уровня — правила 006/FR-23: нельзя снять исполнителя или срок,
    очистить описание, поставить срок раньше «сегодня».

  Меняются только переданные поля, всё или ничего (как в обычном API).
- **FR-27 (комментарии и результат).** Агент ДОЛЖЕН мочь:
  - прочитать комментарии задачи проекта, где он участник (001/FR-23, удалённые — заглушкой);
  - добавить комментарий к такой задаче: текст 1–10 000 символов, HTML вырезается.

  Результат работы агент оставляет комментарием. Отдельного поля «результат» нет.
- **FR-28 (ответы и ошибки).** Ответы операций агента ДОЛЖНЫ быть в формате обычного API
  того же действия. Ошибки — в едином формате `{"detail", "code"}` (001/FR-45) с теми же
  статусами и кодами: 400, 401, 403, 404, 422 (включая `validation_error`,
  `due_date_in_past`, `not_project_member`, `recipient_wrong_role`, `subtask_depth_exceeded`),
  503 `service_busy` с `Retry-After`. Дополнительно — 429 `too_many_requests` с `Retry-After`
  при превышении лимита частоты (FR-33). Мягко удалённые объекты — 404 (001/FR-25).

### 3.5. Авторство и следы действий агента

- **FR-29 (автор).** У задачи и подзадачи, созданных агентом, автор ДОЛЖЕН быть учётной
  записью агента. У комментария агента автор — учётная запись агента. Это видно в карточке
  задачи и в списке комментариев обычного API и интерфейса.
- **FR-30 (события).** Каждое изменение по ключу ДОЛЖНО записываться в хранилище событий так
  же, как такое же изменение человеком по FR-42: тот же тип события, те же изменённые поля. Автор
  события — учётная запись агента. Вдобавок в событии ДОЛЖЕН сохраняться идентификатор ключа,
  по которому выполнен запрос, без секрета. У событий от действий людей идентификатора ключа
  нет. Показ событий в ленте проекта не входит в рамки (001/FR-38 отложена).
- **FR-31 (пометка «ИИ»).** Признак «агент» ДОЛЖЕН передаваться в API в каждой ссылке на
  пользователя: автор, исполнитель, автор комментария, участник, справочник, учётные записи.
  Интерфейс ДОЛЖЕН показывать рядом с именем учётной записи агента метку «ИИ»:
  - в карточке задачи (автор, исполнитель);
  - в комментариях;
  - на доске и в списках задач (исполнитель);
  - в «Учётных записях».

  Рядом с именами людей метки нет.

### 3.6. Безопасность

- **FR-32 (секрет не утекает).** Значение ключа НЕ ДОЛЖНО попадать:
  - в логи приложения и access-лог;
  - в трассировки ошибок;
  - в тела ответов, кроме ответа на выпуск (FR-6);
  - в журнал аудита, хранилище событий и описание API;
  - в вывод и логи инструментов агента (FR-35).

  Это действует при успехе, при отказе 401/403/422/429, при неверном формате ключа и при
  внутренней ошибке 500.
- **FR-33 (лимит частоты).** По одному ключу ДОЛЖНО выполняться не больше 120 запросов в
  минуту.
  - Запрос сверх лимита получает 429 `too_many_requests` с заголовком `Retry-After`.
    Данные по нему не меняются.
  - Лимит одного ключа не влияет на другие ключи и на cookie-сессии людей.
- **FR-34 (изоляция пространства).** Ключ ДОЛЖЕН действовать только в рабочем пространстве
  своей учётной записи. Обращение к объекту другого пространства по идентификатору — 404,
  как в обычном API.

### 3.7. Подключение агента (MCP)

Внешнее требование пользователя — работа с агентом вида Claude. Claude Code подключает
внешние инструменты по протоколу MCP, поэтому протокол — часть контракта. Транспорт выбран
владельцем (Q-9, вариант а): инструменты агента работают локальным процессом на машине
агента, который подключается по stdio и обращается к API трекера по ключу. Точки MCP в
составе сервера трекера нет. Остальное устройство решает plan.

- **FR-35 (инструменты).** Агент, поддерживающий MCP (проверяется на Claude Code), ДОЛЖЕН
  мочь подключиться к трекеру с ключом и получить по одному инструменту на каждую операцию
  FR-18…FR-27. Других инструментов нет. Инструмент выполняет ровно соответствующую операцию с
  правами и правилами FR-3, FR-17…FR-28. Подключение — по stdio к локальному процессу
  инструментов, который выполняет операции через API трекера с ключом (FR-12).
- **FR-36 (описания для агента).** У каждого инструмента ДОЛЖНЫ быть:
  - описание назначения;
  - схема параметров с типами и признаком обязательности;
  - допустимые значения перечислений: статусы `todo`, `in_progress`, `review`, `done`;
    приоритеты `low`, `medium`, `high`;
  - формат срока `YYYY-MM-DD`.

  Для создания задачи описание называет обязательные поля и правило срока «не раньше
  сегодня по Europe/Moscow» (006). Для смены статуса описание говорит, что закрытие — это
  `done`.
- **FR-37 (ошибки инструментов).** При отказе операции инструмент ДОЛЖЕН возвращать агенту
  результат-ошибку с HTTP-статусом, кодом и текстом `detail` (FR-28). При 429 и 503
  результат указывает время, через которое можно повторить. Трассировки в результате нет.
  Подключение после ошибки не обрывается, следующие вызовы работают.
- **FR-38 (ключ вне параметров).** Ключ ДОЛЖЕН задаваться в конфигурации подключения агента,
  а не в параметрах инструментов. Он НЕ ДОЛЖЕН появляться в описаниях, параметрах и
  результатах инструментов. Без ключа или с недействительным ключом ни один инструмент не
  выполняет действий и возвращает ошибку аутентификации.
- **FR-39 (инструкция).** Документация проекта ДОЛЖНА содержать инструкцию на русском:
  - как ТА заводит учётную запись агента и выпускает ключ;
  - как подключить Claude Code к трекеру;
  - как отозвать ключ;
  - что ключ нельзя вставлять в текст запроса к модели, коммитить и пересылать.

### 3.8. Управление агентами в интерфейсе

- **FR-40 (интерфейс ТА).** В разделе «Учётные записи» ТА ДОЛЖЕН мочь:
  - создать учётную запись агента (признак «агент»);
  - увидеть её ключи (FR-7);
  - выпустить ключ с однократным показом секрета (FR-6) и кнопкой копирования;
  - отозвать ключ с подтверждением.

  После закрытия окна с секретом секрет больше не показывается. Те же действия доступны ТА
  через API (FR-5…FR-8).

### 3.9. Совместимость

- **FR-41 (обычный API и интерфейс не меняются).** Без изменений ДОЛЖНЫ работать:
  - вход, сессии, проверка Origin (001/FR-5, FR-57);
  - права и ответы обычного API для людей;
  - интерфейс (кроме FR-31, FR-40).

  Изменения контракта обычного API — только добавления (NFR-1).

### 3.10. События задач и комментариев

- **FR-42 (события для всех авторов).** Действия с задачами, подзадачами и комментариями
  ДОЛЖНЫ записываться в хранилище событий одинаково для всех авторов: для человека через
  обычный API и для агента по ключу (решение владельца 2026-10-30). На `f7f19cf` таких
  событий нет (раздел 0).
  - Создание задачи или подзадачи — одно событие `task.created`.
  - Изменение задачи или подзадачи — одно событие `task.updated` на запрос, если значение хотя
    бы одного поля изменилось. В событии — перечень изменённых полей: ровно те поля, значения
    которых изменились. Поле, переданное с прежним значением, в перечень не входит. Если не
    изменилось ни одно поле, события нет (как в AC-28).
  - В перечень изменённых полей входят: название, описание, срок, приоритет, исполнитель,
    статус. Приоритет — такое же поле, как остальные (Q-11, решение владельца 2026-10-30):
    - изменение только приоритета пишет `task.updated`, в перечне ровно приоритет;
    - при изменении приоритета вместе с другими полями приоритет входит в перечень наравне с
      ними;
    - приоритет, переданный с прежним значением, в перечень не входит и события не создаёт.
  - Перенос карточки задачи верхнего уровня по доске (001/FR-28a) в колонку другого статуса —
    одно событие `task.updated`, в перечне ровно статус. Это то же событие, что при такой же
    смене статуса в карточке задачи (Q-12, решение владельца 2026-10-30). Перенос внутри
    колонки, когда статус не меняется и меняется только порядок карточек, события не пишет.
    Порядок карточек на доске в перечень изменённых полей не входит. Перенос по доске доступен
    только людям (FR-17).
  - Создание комментария — одно событие `comment.created`.
  - Удаление комментария (мягкое, 001/FR-23) — одно событие `comment.deleted`, но только при
    прямом удалении этого комментария (Q-13, решение владельца 2026-10-30). Комментарии,
    удалённые вместе с задачей или подзадачей (каскад мягкого удаления, 001/FR-25), событий
    `comment.deleted` не дают. Это же правило действует, когда комментарии удаляются вместе с
    проектом. Повторное удаление уже удалённого комментария — отказ 404, событие не пишется.
  - В событии сохраняются автор (учётная запись, выполнившая действие), время, проект и
    объект события. Идентификатор ключа есть только у событий по ключу (FR-30).
  - Событие записывается тогда и только тогда, когда действие сохранено. При отказе (400,
    401, 403, 404, 422, 429, 503) событие не пишется.
  - Остальные действия событий не пишут, как на `f7f19cf`:
    - правка комментария;
    - удаление задачи или подзадачи, в том числе каскадное удаление её подзадач и
      комментариев;
    - перенос карточки по доске внутри колонки;
    - снятие исполнителя при исключении участника из проекта (001/FR-15a).
  - Задним числом события не создаются: у задач и комментариев, созданных до установки
    версии с 007, событий нет. Загрузка демо-данных событий задач и комментариев не пишет, как
    сейчас (тест `test_d55_no_project_or_task_events` остаётся в силе).
  - События задач и комментариев не показываются в журнале аудита (D-4), в интерфейсе и в
    API: ленты нет (001/FR-38 отложена, раздел 6). Ответы обычного API не меняются.

## 4. Нефункциональные требования

- **NFR-1 (совместимость API).** Существующие пути, методы, поля ответов и их типы не удаляются
  и не меняются. Новых обязательных полей во входных схемах существующих путей нет. Новое —
  только добавление: маршруты, поле признака «агент» в ссылках на пользователя (FR-31), коды
  ошибок. Описание API (`docs/api/openapi.json`) и типы клиента пересобираются (001/FR-44).
  Новый способ аутентификации дополняет ADR-0004. Решение оформляется новым ADR (NFR-7).
- **NFR-2 (производительность).** Операции агента по ключу укладываются в нормативы
  001/NFR-2 для тех же операций обычного API. Проверка ключа добавляет к времени ответа не
  больше 20 мс p95 по сравнению с тем же запросом по cookie-сессии. Методика: тестовая БД,
  фикстура раздела 5, 200 запросов карточки задачи по ключу и 200 по сессии после прогрева, 1
  клиент. Замер вне CI (как 001/NFR-2 в R1). В CI — только короткий прогон без проверки
  порога.
- **NFR-3 (стойкость ключа).** Секрет ключа содержит не меньше 256 бит случайности из
  криптографически стойкого источника. В поставляемой конфигурации ключ передаётся только по
  HTTPS (ADR-0004, «Транспорт»).
- **NFR-4 (проверяемость).** Каждый AC проверяется автотестом уровня API или БД, если у него
  нет пометки:
  - *ручной* — проверка человеком при приёмке;
  - *вне CI* — замер на стенде.

  Тесты:
  - используют фиксированные часы и фиксированный seed генераторов, как в 001;
  - не ходят в интернет;
  - не вызывают языковую модель: инструменты MCP проверяются тестовым MCP-клиентом,
    запущенным в тесте.

  Ослаблять существующие тесты нельзя (CLAUDE.md).
- **NFR-5 (ML).** Неприменимо: в фиче нет обучения моделей и метрик качества. Языковая
  модель — внешний клиент, в составе трекера её нет.
- **NFR-6 (автономность).** Трекер и инструменты агента не делают внешних вызовов и не
  отправляют телеметрию (001/NFR-4, AGENTS.md). Инструменты агента обращаются только к API
  трекера по адресу из конфигурации подключения. Внешний сетевой доступ нужен только самому
  агенту к его модели. Это за пределами трекера.
- **NFR-7 (документация).** Оформляются:
  - новый ADR (следующий свободный номер, ожидается 0020, см. ADR-0020): учётная запись агента, ключи,
    объём доступа, транспорт MCP, лимиты;
  - инструкция FR-39;
  - правки 001 при синхронизации: FR-4 (кто создаёт учётные записи и их виды), FR-41 (новые
    действия журнала), FR-57 (ключ — секрет наравне с паролем), модель данных (в том числе
    запись событий задач и комментариев по FR-42; лента FR-38 по-прежнему отложена).

## 5. Критерии приёмки

**Общая фикстура** (если в AC не сказано иное):
- одно рабочее пространство; часы зафиксированы на 2026-11-02 10:00 по Europe/Moscow
  (07:00 UTC), «сегодня» — 2026-11-02;
- ТА `ta1`;
- проект P: владелец и участник БА `ba1`, участники П `u1`, агент `agent.u` (роль П) и
  агент `agent.ba` (роль БА);
- проект P2: владелец и участник `ba1`, агентов в нём нет; в P2 задача T9;
- в P:

## 7. Допущения и зависимости

- **D-1.** В R1 одно рабочее пространство (001/FR-13). AC-16 проверяет изоляцию фикстурой
  уровня БД.
- **D-2.** Переходы статусов не ограничены, это проверено по коду (`_status` принимает любое
  значение набора). FR-25 сохраняет это поведение.
- **D-3.** Смена статуса задачи верхнего уровня через изменение задачи переносит её в колонку
  нового статуса по существующим правилам позиций. Агент использует ту же операцию.
- **D-4.** События задач и комментариев не входят в журнал аудита (каталог событий:
  `task.*`, `comment.*` — не аудит), и это не меняется. Авторство агента проверяется по
  автору задачи и комментария и по хранилищу событий (AC-35).
- **D-5.** Отзыв уже отозванного или истёкшего ключа — успешный ответ без записи в журнал
  (FR-8). Это предложение аналитика по аналогии с правилом «нет изменений — нет события» при
  изменении задачи (001, plan D-46). Владелец может поменять.
- **D-6.** Учётная запись агента не может получить роль ТА (FR-2). Это следует из 002/FR-4
  (ТА без бизнес-данных) и FR-17. Отдельного вопроса владельцу не выносится.
- **D-7.** Пакета для MCP нет в списке разрешённых зависимостей
  (`backend/tests/arch/test_dependencies_allowlist.py`). Новая зависимость или своя
  реализация протокола решается в plan.md и ADR (AGENTS.md: новая зависимость только по plan,
  проверка лицензии).
- **D-8.** Код 429 `too_many_requests` уже есть в общем обработчике ошибок. Ограничителя
  частоты в системе нет: его вводит эта фича (FR-33).
- **D-9.** Лимиты длины и формата полей задач и комментариев — по 001 и 006 без изменений.
  Постраничный вывод — до 100 элементов на страницу, как в обычном API.
- Зависимость: 006 реализована и принята (коммит `f7f19cf`), обязательные поля действуют.
- Зависимость: ADR-0004 (сессии, пароли, транспорт) дополняется новым ADR (NFR-7), а не
  заменяется.
