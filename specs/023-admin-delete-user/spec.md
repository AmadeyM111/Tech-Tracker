# Spec: Удаление пользователя техадминистратором (черновик)

- **ID:** 023-admin-delete-user
- **Статус:** DRAFT. Реализация не начата. Решения владельца не приняты (см. §8).
- **Дата:** 2026-11-08
- **Номер:** 022 предложен Orchestrator Agent под дельту M20; 023 взят как следующий свободный, без коллизий.
- **Связано:** ADR-0004 (сессии, блокировка), ADR-0006 (аудит), ADR-0010 (корзина и хранение), ADR-0013 (роли,
  «хотя бы один активный ТА»), ADR-0018 (блокировка отзывает токены `gtrk_`), ADR-0019 (регистрация, ПДн), spec 021
  (отложена; там предложено «отзыв согласия = удаление учётной записи до 30 дней»), 152-ФЗ (ст. 21 ч. 5 — уничтожение ПДн).

## 1. Контекст и цель
Владелец просит, чтобы техадминистратор (ТА) мог удалить пользователя. Сейчас это невозможно по решению, записанному
в `docs/data-model.md`: «Пользователи не удаляются: в интерфейсе и API нет операции удаления учётной записи,
внешние ключи на `app_user` — `RESTRICT`; вместо удаления используется блокировка (`app_user.is_blocked`)».
Эта фича меняет данное правило, поэтому без нового ADR её нельзя реализовать.

Нужна операция, которая:
- полностью убирает доступ пользователя (сессии, токены `gtrk_`, вход);
- уничтожает его персональные данные (фамилия, имя, email) по требованию 152-ФЗ;
- не ломает связанные данные (задачи, комментарии, ленту) и журнал аудита.

## 2. Пользовательские сценарии
- Как **ТА**, я хочу удалить учётную запись сотрудника, который ушёл из компании, чтобы он не мог войти и его
  данные не хранились.
- Как **ТА**, я хочу видеть предупреждение о последствиях и подтвердить действие, чтобы не удалить запись случайно.
- Как **пользователь**, отозвавший согласие (spec 021), я хочу, чтобы его учётная запись и ПДн были удалены по
  правилу, которое указано в тексте согласия.

## 3. Функциональные требования
- **FR-1:** ТА ДОЛЖЕН мочь удалить пользователя. Другие роли — не могут (ADR-0013).
- **FR-2:** Система НЕ ДОЛЖНА позволять ТА удалить себя.
- **FR-3:** Система НЕ ДОЛЖНА позволять удалить последнего активного ТА (ADR-0013: «хотя бы один активный ТА»).
  Проверка выполняется под той же блокировкой, что и остальные действия с учётными записями (ADR-0013).
- **FR-4:** Перед удалением система ДОЛЖНА показать последствия (связанные задачи, комментарии, сколько сессий и
  токенов будет отозвано) и потребовать подтверждение (§8, Q6).
- **FR-5:** При удалении система ДОЛЖНА: завершить все сессии пользователя (ADR-0004), отозвать все токены `gtrk_`
  (ADR-0018), запретить вход.
- **FR-6:** Связанные данные (§8, Q2): задачи, комментарии, авторство в ленте активности не должны ломаться.
  Варианты поведения ссылок на удалённого пользователя — в §8.
- **FR-7:** Персональные данные (фамилия, имя, email) ДОЛЖНЫ быть уничтожены или обезличены, сроки — §8, Q4.
- **FR-8:** Система ДОЛЖНА записать в журнал аудита событие `user_deleted` с учётной записью ТА и идентификатором
  удалённого пользователя, без фамилии, имени и email (ADR-0006: записи о удалённом объекте остаются).
- **FR-9:** Отличие от блокировки: блокировка обратима и сохраняет учётную запись и связи; удаление убирает учётную
  запись и ПДн, восстановление — §8, Q3.
- **FR-10:** Пользователь с удалённой учётной записью НЕ ДОЛЖЕН появляться в выборах исполнителя, в списках
  участников и поиске. Исторические ссылки — по FR-6.

## 4. Нефункциональные требования
- **NFR-1 (безопасность):** ПДн не попадают в логи, ответы API и аудит (тот же принцип, что spec 007, NFR-1).
- **NFR-2 (атомарность):** удаление выполняется в одной транзакции под блокировкой пространства (ADR-0013).
- **NFR-3 (миграции):** применённые миграции не правятся; FK на `app_user` меняются новой миграцией.

## 5. Критерии приёмки (черновик)
- **AC-1** (FR-1): Given пользователь без роли ТА When вызывает удаление Then 403.
- **AC-2** (FR-2): Given ТА When удаляет себя Then 422 с понятным кодом.
- **AC-3** (FR-3): Given единственный активный ТА When пытается удалить его Then 422, запись не меняется.
- **AC-4** (FR-5): Given пользователь с открытой сессией и токеном `gtrk_` When его удаляют Then сессия завершена,
  токен не принимается, вход невозможен.
- **AC-5** (FR-6): Given задачи и комментарии удалённого пользователя When открываем проект Then задачи и комментарии
  остаются, ссылка на автора — по выбранному варианту (§8, Q2).
- **AC-6** (FR-7): Given удаление выполнено When проверяем БД Then фамилия, имя и email уничтожены или обезличены.
- **AC-7** (FR-8, NFR-1): Given удаление When смотрим журнал и логи Then событие `user_deleted` есть, ПДн нет.

## 6. Вне рамок (Out of scope)
- Удаление задач, проектов и комментариев (уже есть в ADR-0010, корзина 30 дней).
- Удаление по CLI оператора (ADR-0010) — отдельная задача.
- Самоудаление пользователем (только ТА, FR-1; согласие — spec 021).
- Выгрузка данных удаляемого пользователя перед удалением (если понадобится — отдельно).

## 7. Допущения и зависимости
- Допущение: удаление — только по инициативе ТА. Отзыв согласия (spec 021) сейчас отложен; если понадобится, он будет
  вызывать ту же операцию.
- Зависимость: вопрос Q8 (менять ли правило «пользователи не удаляются» из `docs/data-model.md`). Владелец решил:
  ADR-0021 сейчас не заводить, спека остаётся черновиком, Q1–Q8 открыты, реализация не начата.
- Зависимость: ADR-0018 (токены), ADR-0004 (сессии), ADR-0013 (правила ТА), ADR-0006 (аудит).

## 8. Вопросы владельцу (ответы не подставлены)
| # | Вопрос | Варианты |
|---|--------|----------|
| Q1 | Жёсткое удаление или обезличивание учётной записи? | Жёсткое (строка удаляется) / обезличивание (строка остаётся, ПДн стёрты) |
| Q2 | Судьба задач, комментариев и авторства в ленте? | Оставить с пометкой «Удалённый пользователь» / передать другому ТА / удалить вместе с ним |
| Q3 | Можно ли восстановить удалённого? В каком окне? | Нет / в течение 30 дней (как в корзине, ADR-0010) / всегда через оператора |

| Q5 | Может ли ТА удалить другого ТА? | Да / нет / только при наличии двух активных ТА |
| Q6 | Подтверждение удаления | Повторный ввод логина / пароль ТА / оба |
| Q7 | Освобождается ли email для новой регистрации (spec 019)? | Да / нет |
| Q8 | Меняем правило «пользователи не удаляются» в `docs/data-model.md` и ADR-0013? | Да (новый ADR-0021) / нет (только блокировка) |
