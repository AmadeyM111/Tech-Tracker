## 5. Риски и неочевидные места

1. Экспорт/импорт универсален по `Base.metadata` (см. раздел 1): без явных исключений email и таблица токенов попадут в архив, а импорт отвергнет архивы при несовпадении колонок. Решение «email не экспортируется» требует изменения `archive.py`/`export.py`/`importer.py` и теста цикла export-import-export.
2. Нет эндпоинта редактирования учётной записи (FR-2 «изменить/очистить»), нет `deleted_at` у `app_user` (FR-1 «среди активных»; решить, что значит «активна» — вероятно, `is_blocked=false`; уникальность среди всех строк безопаснее и проще: partial unique index не нужен).
3. Уникальность email без регистра: хранить в нижнем регистре в колонке с `UNIQUE` (как `login`) либо функциональный уникальный индекс `lower(email)`; `alembic check` с функциональными индексами требует аккуратного объявления в модели. Спецификация: 409 `email_taken`, тогда как существующие конфликты идут как 422 (`login_taken`).
4. Единый ответ и время (FR-6, AC-4, NFR-2): в существующем коде вход имитирует время `dummy_verify` (`hasher.dummy_verify`, `auth/service.py:~190`); для request отправка письма должна идти после ответа (BackgroundTasks) либо через очередь, а работа с БД/хешем в обеих ветках выравниваться по времени. `get_db` коммитит ДО отправки ответа — письмо отправлять только после COMMIT (иначе токен может не сохраниться); исключение в фоновой отправке не должно ронять ответ и логировать токен/email (логи фильтрует `backend/app/core/logging.py` `redact_text`/`_is_secret_key`: новые секретные поля стоит проверить, что маскируются; AC-12).
5. Токен в фрагменте URL: ссылка строится из базового URL; в `Settings` нет `public_base_url` — нужен источник хоста для ссылки в письме (Origin-заголовок небезопасен: подмена Host/Origin). Решить в plan (новая переменная окружения, например `PUBLIC_BASE_URL`), не забыть `.env.example`, `docker-compose.yml`, `test_compose_static.py`.
6. Публичные POST проходят `check_origin` (CSRF) и попадают под обход маршрутов `test_route_guards.py`; `FR-9` требует ограничения по IP, а IP-логики нет (за nginx используется `X-Forwarded-For`, но приложение его не читает; прямой доступ к api в compose не опубликован — проверить).
7. Мультиарендность: `app_user` глобален; поиск по email для сброса выходит за один `workspace_id` — это допустимо только как исключение для публичного эндпоинта (в spec/plan отметить явно); аудит-запись требует workspace (берётся из `workspace_member`; у пользователя без членства события писать некуда — FR-15 выполнить нельзя; проверить, возможно ли такое состояние).
8. Событие и аудит: `record_event` валидирует белые списки; новые `EventAction` требуют правки `EVENT_CATALOG`, `EXPECTED` в `test_event_catalog.py`, возможно `AuditPage`/`ru.ts` (подписи действий) и CHECK/enum при необходимости миграции.
9. `ErrorCode` — каталог кодов 422; для 400/404/409 использовать собственные подклассы `AppError` с `code`; новые коды нужны в `ru.ts` и в `API_CODES` теста i18n.
10. Правила ruff (ratchet, `backend/pyproject.toml:41-48`): `max-complexity=16`, `max-branches=16`, `max-args=10`, `max-statements=34`; уже в `change_own_password` много аргументов — для сервиса сброса дробить функции. Прочее: `F401`, `F841`, `ARG`; в `tests/**` сложность не ограничена. mypy strict с pydantic-плагином.

AST-тесты: запрет `Depends(get_db)` вне `core/db.py`, запрет `.commit()` в `app/**` кроме `commit_durably` (разрешён только в `domain/auth/service.py` и `api/deps.py`) — `test_deps_gates.py`, `test_route_guards.py`; новый домен (`domain/auth/reset.py`?) не может вызвать `commit_durably`, если это не `service.py`.
