# Spec: Резервная копия и восстановление (`gtrack backup`, `gtrack restore`, предупреждение ТА)

- **ID:** 009-backup-restore
- **Статус:** APPROVED (ответы владельца на §8 — 2026-11-08)
- **Дата:** 2026-11-08
- **Пакет:** R2 T-01 (R2-25…R2-29, R2-36). Решения владельца: ежедневная копия, 14 штук, RPO ≤ 24 ч,
  RTO ≤ 60 мин, подтверждение учебным восстановлением; таймер на хосте вызывает CLI `gtrack`;
  предупреждение ТА в интерфейсе, если последней копии больше 26 ч; шифрования нет, копии локально,
  root/владелец 0600 (до письменного ответа ИБ, Q-4).

## 1. Контекст и цель
В R1 копия снимается вручную `scripts/backup.sh`; расписания, ротации, проверки после снятия и
статуса для ТА нет. На проде с 2026-11-08 работает временный таймер хоста (`deploy/backup/host/`).
Пакет делает копию командой приложения, проверяемой и видимой ТА, чтобы пилот (2026-11-09…12-21)
не терял больше суток работы и восстанавливался за час.

## 2. Пользовательские сценарии
- Как оператор, я ставлю таймер, который раз в сутки вызывает `gtrack backup`, и больше о копиях не думаю.
- Как оператор, я восстанавливаю стек на чистом сервере одной командой `gtrack restore`.
- Как ТА, я вижу предупреждение, если копий нет, последняя упала или старше 26 часов.
- Как БА или пользователь, я не вижу состояние копий.

## 3. Функциональные требования
- **FR-1 (снятие, R2-25):** `gtrack backup [--out DIR]` ДОЛЖНА без остановки системы создавать в
  `DIR` (по умолчанию `BACKUP_DIR`, `/backups`) один файл `gtrack-backup-<UTC YYYYmmddTHHMMSSZ>.tar`
  (режим 0600) с членами: `db.dump` (`pg_dump -Fc`), `appdata.tar` (содержимое `DATA_DIR`, кроме
  `exports/`), `manifest.json` (формат, время UTC, ревизия alembic, версия приложения, размер и
  sha256 каждого члена).
- **FR-2 (проверка, R2-27):** До появления файла под итоговым именем команда ДОЛЖНА проверить:
  sha256 членов совпадают с манифестом, `pg_restore --list` читает дамп, `appdata.tar` читается.
  Неудача — код 1, незавершённый файл удалён.
- **FR-3 (ротация, R2-26):** После успешной проверки команда ДОЛЖНА оставить в `DIR` `BACKUP_KEEP`
  (по умолчанию 14) самых новых файлов `gtrack-backup-*.tar` и удалить остальные такие файлы.
  Другие файлы каталога не трогаются. При неудаче ничего не удаляется.
- **FR-4 (журнал запусков, R2-27):** Каждый запуск, при доступной БД, ДОЛЖЕН записывать строку
  `backup_run`: начало, конец, результат (`ok`/`failed`), размер, ревизия схемы, имя файла (без пути),
  код ошибки. Содержимого и секретов в строке нет.
- **FR-5 (тот же диск, R2-26):** Если `DIR` и `DATA_DIR` на одном устройстве, команда ДОЛЖНА печатать
  предупреждение (stdout `same_device=1` и лог) и продолжать.
- **FR-6 (статус для ТА, R2-27):** `GET /api/v1/admin/system/backup` ДОЛЖЕН отдавать ТА (возможность
  `manage_accounts`): время и размер последней успешной копии, время и результат последнего запуска,
  признак `stale` и порог 26 ч. Прочим ролям — 403, без сессии — 401. Пути и содержимое не отдаются.
- **FR-7 (предупреждение в интерфейсе):** На экранах ТА ДОЛЖНА показываться плашка, когда `stale`:
  нет успешных копий; последняя успешная старше 26 ч; последний запуск неудачен (тексты — Q-2).
- **FR-8 (восстановление, R2-28):** `gtrack restore ARCHIVE --yes` ДОЛЖНА проверить sha256 и формат,
  отказать (код 2), если в БД есть таблицы в схеме `public` или `DATA_DIR` не пуст, иначе развернуть
  дамп (`pg_restore --no-owner --exit-on-error`) и `appdata.tar`. Без `--yes` — код 2, без изменений.
- **FR-9 (перед миграцией, R2-29):** `gtrack bootstrap` ДОЛЖЕН печатать в stderr предупреждение, если
  есть неприменённые миграции и последней успешной копии нет или она старше 24 ч. Не блокирует.
- **FR-10 (одна команда, F8):** Шаг «резервная копия» чек-листа обновления (ADR-0013, README) ДОЛЖЕН
  ссылаться на `docker compose exec -T api gtrack backup`.

## 4. Нефункциональные требования
- **NFR-1 (RPO/RTO, R2-36):** копия раз в сутки (RPO ≤ 24 ч); восстановление по инструкции на чистом
  стенде ≤ 60 мин — подтверждается протоколом учения.
- **NFR-2 (секреты, R2-44):** пароль БД передаётся `pg_dump`/`pg_restore` только через окружение
  процесса (`PGPASSWORD`), не в argv и не в лог; содержимое дампа и архива в лог не пишется.
- **NFR-3 (без внешних вызовов):** исходящих соединений, кроме БД, нет.
- **NFR-4 (совместимость):** клиент PostgreSQL в образе API — той же major-версии, что сервер (16).

## 5. Критерии приёмки
- **AC-1** (FR-1, FR-2): Given БД с данными и файлом в `DATA_DIR` When `gtrack backup --out D` Then
  код 0, в `D` один `gtrack-backup-*.tar` 0600 с тремя членами; sha256 в манифесте верны.
- **AC-2** (FR-1): Given `DATA_DIR/exports/x.tar` When копия Then `exports/` в `appdata.tar` нет.
- **AC-3** (FR-2): Given `pg_dump` завершился ошибкой When копия Then код 1, в `D` нет файлов, `backup_run.status='failed'`.
- **AC-4** (FR-3): Given 15 копий и чужой файл в `D` When успешная копия с `BACKUP_KEEP=14` Then 14
  копий (самые новые), чужой файл на месте; при неудаче копии — 15 и файл на месте.
- **AC-5** (FR-4): Given успешная копия Then строка `backup_run` `ok` с размером и ревизией.
- **AC-6** (FR-5): Given `D` на том же устройстве, что `DATA_DIR` Then stdout содержит `same_device=1`.
- **AC-7** (FR-6): Given ТА When `GET /admin/system/backup` Then 200 и поля; БА, пользователь — 403; без сессии — 401.
- **AC-8** (FR-6, граница): Given последняя успешная копия 25 ч 59 мин и 26 ч 01 мин назад Then `stale` false/true;
  нет копий — `stale=true`; последний запуск `failed` — `stale=true`.
- **AC-9** (FR-8): Given копия AC-1 и чистая БД `*_test` When `gtrack restore --yes` Then `gtrack export`
  до и после даёт одинаковый `data.json`, файлы `DATA_DIR` совпадают по sha256.
- **AC-10** (FR-8): Given непустая БД или непустой `DATA_DIR`, либо испорченный sha256 When restore Then
  код 2 (испорчен — 1), БД и каталог не изменены; без `--yes` — код 2.
- **AC-11** (FR-9): Given неприменённые миграции и копия старше 24 ч When bootstrap Then предупреждение в stderr, код 0.
- **AC-12** (FR-7): Given `stale=true` When ТА открывает «Пользователи» Then плашка видна; `stale=false` — нет.
- **AC-13** (NFR-2): Given запуск копии и восстановления When перехвачены argv подпроцессов и лог Then пароля БД в них нет.
- **AC-14** (NFR-1): протокол учения восстановления на чистом стенде ≤ 60 мин — `docs/acceptance/backup-restore-drill.md` (вручную).

## 6. Вне рамок
Шифрование копий и внешнее хранилище (ответ ИБ, Q-4); оповещения почтой/мессенджером; копия по кнопке
из интерфейса; восстановление поверх работающей системы (для этого `scripts/restore.sh`); PITR/WAL.

## 7. Допущения и зависимости
- Таймер хоста (systemd или cron) вызывает `docker compose -p <проект> exec -T api gtrack backup`;
  каталог хоста примонтирован в api как `/backups`, владелец uid 10001, режим 0700.
- Вложения (T-04) хранятся в `DATA_DIR/attachments` и попадают в копию без изменений этой спеки.

## 8. Решения по вопросам (владелец, 2026-11-08)
- Q-1: ежедневный запуск в 02:30 МСК.
- Q-2: тексты плашки утверждены: «Резервных копий нет.», «Последняя резервная копия старше 26 часов: <дата>.»,
  «Последняя резервная копия не удалась: <дата>.»
- Q-3: плашка — на всех экранах ТА.
- Q-4: после выкатки 009 таймер хоста переводится на `docker exec <проект>-api-1 gtrack backup`; описание
  таймера в конфиге NixOS хоста делается один раз, уже с этой командой. До выкатки работает временный
  скрипт хоста.
- Порядок слияния: первой вливается 019 (миграция `0010`); перед слиянием 009 `down_revision` миграции
  `0011` меняется на `"0010"`.
