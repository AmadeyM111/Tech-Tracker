## Исходные решения владельца (запрос 2026-10-17)

Запрос владельца дословно: «зачем нам Главное меню? лучше убрать его и главным экраном сделать
Проекты».

Решения переданы оркестратором; ниже изложение по передаче. При расхождении действует текст
владельца.

1. Страница «Главная» (маршрут `/`) удаляется вместе со ссылкой «На главную».
2. После входа и после принудительной смены пароля пользователь с возможностью
   `business_access` (роли «Бизнес-админ» и «Пользователь») попадает на «Проекты»
   (`/projects`). «Тех-админ» (у него нет `business_access`) попадает на «Учётные записи»
   (`/admin/users`). Пользователь без роли остаётся на `/no-role`. `/` и неизвестные пути
   перенаправляют по тому же правилу.
3. «Выйти» и «Сменить пароль» размещаются внизу бокового меню на всех экранах, где есть
   боковое меню. Оговорка владельца: «Сменить пароль» — только если добровольная смена пароля
   сейчас существует в интерфейсе. По 001/FR-56 (v0.17) в интерфейсе есть только
   принудительная смена, добровольной нет. **Поэтому в боковое меню добавляется только
   «Выйти». Ссылка или кнопка «Сменить пароль» не добавляется** (FR-12).
4. После смены пароля фокус ставится на заголовок целевой страницы, а не на `body`.

- **Роли и сокращения.** ТА — роль `tech_admin`, в интерфейсе подпись «Тех-админ». БА — роль

- **Профиль сессии** — ответ существующего запроса профиля `GET /api/v1/me`: роль, флаг

- **Стартовый экран** — экран, на который система ведёт пользователя по правилу FR-3.
- **Боковое меню** — левая панель экрана: сверху пункты разделов по возможностям (001/FR-10),

  - экраны отказа в доступе на любом из этих путей (FR-14).
- **Экраны без бокового меню** (не меняются): вход (`/login`), окно принудительной смены
  пароля (`/change-password`), «Роль не назначена» (`/no-role`), индикатор проверки сессии,
  экран ошибки проверки сессии с кнопкой «Повторить».
- Тексты заголовков в словаре сейчас такие: «Список проектов», «Учётные записи»,
  «Журнал аудита», «Роль не назначена». Кнопка выхода — «Выйти». Навигация по страницам списков
  называется «Постраничная навигация».

## 1. Контекст и цель

Сейчас после входа пользователь попадает на страницу «Главная» (`/`). На ней только заголовок
«Главная» и боковая панель с пунктами разделов и кнопкой «Выйти» внизу, то есть это лишний
промежуточный шаг. На всех остальных экранах с ролью над содержимым стоит ссылка-кнопка
«На главную»: на экранах ТА она единственный элемент навигации (бокового меню там нет), а на
бизнес-экранах боковое меню есть, но кнопки «Выйти» в нём нет. Чтобы выйти, нужно сначала
вернуться на «Главную». Владелец решил убрать «Главную»: бизнес-пользователи сразу попадают на
«Проекты», ТА — на «Учётные записи». Боковое меню с «Выйти» должно быть на каждом экране с
ролью, включая экраны ТА. Изменение затрагивает только интерфейс: права проверяет сервер
(001/FR-10), и серверная часть не меняется.

## 2. Пользовательские сценарии

- Как БА или «Пользователь», я хочу после входа сразу видеть список проектов, чтобы не делать
  лишний переход.
- Как ТА, я хочу после входа сразу видеть «Учётные записи» и переходить в «Журнал аудита» через
  боковое меню, чтобы сразу заняться своей задачей.
- Как любой пользователь с ролью, я хочу выйти из системы с любого экрана с боковым меню, не
  возвращаясь на промежуточную страницу.
- Как новый пользователь с одноразовым паролем, я хочу после смены пароля оказаться на своём
  стартовом экране с фокусом на заголовке, чтобы продолжить работу с клавиатуры.
- Как пользователь со старой закладкой на `/` или на несуществующий адрес, я хочу попасть на
  свой стартовый экран, а не на пустую или ошибочную страницу.

## 3. Функциональные требования

### 3.1. Удаление «Главной»

- **FR-1:** В интерфейсе НЕ ДОЛЖНО быть страницы «Главная». Маршрут `/` не показывает
  собственного содержимого: он только перенаправляет пользователя (FR-6). Заголовок «Главная»
  не показывается ни на одном экране.
- **FR-2:** В интерфейсе НЕ ДОЛЖНО быть ссылки «На главную» и вообще ссылок, ведущих на `/`,
  ни на одном экране: ни на экранах ТА, ни на бизнес-экранах, ни на экранах отказа в доступе
  (FR-14).

### 3.2. Стартовый экран и перенаправления

- **FR-3 (правило стартового экрана):** Стартовый экран определяется по профилю сессии в таком
  порядке (решение владельца (2), Q-3 б):
  1. у профиля установлен флаг принудительной смены пароля → `/change-password`, как сейчас
     (001/FR-55);
  2. у пользователя нет роли → `/no-role`, как сейчас (001/FR-66);
  3. у профиля есть `business_access` → «Проекты» (`/projects`);
  4. иначе есть `manage_accounts` → «Учётные записи» (`/admin/users`);
  5. иначе есть `view_audit` → «Журнал аудита» (`/admin/audit`);
  6. иначе → `/admin/users`, где показывается отказ в доступе по FR-14.

  Для трёх ролей текущей матрицы результат совпадает с решением владельца (2): БА и
  «Пользователь» → `/projects`, ТА → `/admin/users`. Пункты 5–6 касаются только нетипичных
  наборов возможностей.
- **FR-4 (после входа):** После успешного входа система ДОЛЖНА вести пользователя на его
  стартовый экран по FR-3. Данные предыдущего пользователя на клиенте при этом не используются,
  как сейчас.
- **FR-5 (после принудительной смены пароля):** После успешной принудительной смены пароля
  система ДОЛЖНА заново получить профиль сессии с сервера и вести пользователя на стартовый
  экран по FR-3 (п. 2–6). Пользователь без роли попадает на `/no-role`.
- **FR-6 (`/` и неизвестные пути):** Для любых путей ниже система ДОЛЖНА выполнять
  перенаправление по FR-3 и ничего не показывать по самому исходному пути, кроме индикатора
  проверки сессии:
  - `/`;
  - любой путь, для которого в интерфейсе нет экрана;
  - `/login` при действующей сессии;
  - `/change-password` у пользователя, которому смена пароля не требуется.

  Если сессии нет (401), система ДОЛЖНА вести на `/login`, как сейчас.
- **FR-7 (ошибка проверки сессии):** Если проверка сессии на пути из FR-6 завершилась ошибкой,
  которая не является перенаправлением (5xx, сбой сети), система ДОЛЖНА, как сейчас, показать
  сообщение об ошибке и кнопку «Повторить». Адрес при этом не меняется. После успешного
  повтора система ДОЛЖНА выполнить перенаправление по FR-3.
- **FR-8 (история браузера):** Перенаправления по FR-4…FR-7 ДОЛЖНЫ заменять текущую запись
  истории, а не добавлять новую. После прихода на стартовый экран кнопка «Назад» браузера НЕ
  ДОЛЖНА возвращать на `/`, на неизвестный путь, на `/login` или на `/change-password`.
- **FR-9 (без лишних запросов):** При перенаправлении на стартовый экран интерфейс НЕ ДОЛЖЕН
  запрашивать данные разделов, недоступных пользователю. Например, у ТА нет запросов списка
  проектов и «моих задач», у БА и «Пользователя» — запросов учётных записей и журнала аудита.

### 3.3. Боковое меню и «Выйти»

- **FR-10 (состав бокового меню):** На каждом экране с боковым меню (раздел 0) боковое меню
  ДОЛЖНО содержать:
  - сверху — пункты разделов по возможностям профиля, как сейчас (001/FR-10): «Проекты» и
    «Мои задачи» при `business_access`, «Учётные записи» при `manage_accounts`,
    «Журнал аудита» при `view_audit`;
  - внизу — кнопку «Выйти». Она стоит после последнего пункта меню (и в порядке документа, и
    визуально) и оформлена так же, как сейчас на «Главной»: светлая кнопка-таблетка с
    декоративной иконкой слева, прижатая к низу панели на широком экране.

  Кнопку «Задача» в этом же меню добавляет 004 (004/FR-5, FR-6). 003 её не вводит.
- **FR-11 (экраны ТА):** Экраны «Учётные записи» и «Журнал аудита» ДОЛЖНЫ получить боковое
  меню по FR-10 вместо удаляемой ссылки «На главную» (решение владельца, Q-1 а). Через это
  меню ТА переходит между своими разделами и выходит из системы.
- **FR-12 (без «Сменить пароль»):** Ни в боковом меню, ни где-либо ещё в интерфейсе НЕ ДОЛЖНО
  появляться ссылки или кнопки добровольной смены пароля и ссылок на `/change-password`.
  Основание — 001/FR-56, 001/FR-66, OI-6, OI-75 (v0.17). Решение владельца (3) в части
  «Сменить пароль» не применяется, потому что добровольной смены пароля в интерфейсе нет.
- **FR-13 (поведение «Выйти»):** Нажатие «Выйти» в боковом меню ДОЛЖНО работать так же, как
  существующий выход:
  - удаляется сессия на сервере (001/FR-60);
  - на клиенте очищаются данные предыдущего пользователя;
  - пользователь переходит на `/login`.

  Ответ 401 на запрос выхода считается успешным выходом. При другой ошибке система
  показывает сообщение из словаря, остаётся на экране, и кнопка снова становится доступна.
  Пока запрос выхода выполняется, кнопка недоступна, и повторное нажатие нового запроса не
  отправляет.

### 3.4. Отказ в доступе

- **FR-14:** Если у пользователя нет возможности, нужной для открытого раздела (например, ТА
  открыл `/projects` или БА открыл `/admin/users`), система ДОЛЖНА, как сейчас:
  - оставить адрес без изменений;
  - показать сообщение «нет прав» из словаря;
  - не запрашивать данные раздела.

  Вместо удалённой ссылки «На главную» ДОЛЖНО показываться боковое меню по FR-10 с пунктами
  разделов, доступных пользователю, и кнопкой «Выйти» (решение владельца, Q-2 а). Если
  доступных разделов нет (FR-3, п. 6), в меню только «Выйти».

### 3.5. Фокус

- **FR-15 (фокус после смены пароля):** После успешной принудительной смены пароля, когда
  целевой экран показан, фокус клавиатуры ДОЛЖЕН находиться на заголовке первого уровня
  целевого экрана, а не на `body`:
  - «Список проектов» — для БА и «Пользователя»;
  - «Учётные записи» — для ТА;
  - «Роль не назначена» — для пользователя без роли.

  Заголовок получает фокус программно и НЕ ДОЛЖЕН становиться остановкой при обходе клавишей
  Tab.
- **FR-16 (фокус после входа):** То же правило ДОЛЖНО действовать после обычного входа (решение
  владельца, Q-4 а): когда стартовый экран показан, фокус находится на его заголовке первого
  уровня («Список проектов» для БА и «Пользователя», «Учётные записи» для ТА), а не на `body`.
  Заголовок не становится остановкой при обходе клавишей Tab.

### 3.6. Что не меняется

- **FR-17:** Экраны «Роль не назначена» и окно принудительной смены пароля ДОЛЖНЫ остаться без
  изменений. На них нет бокового меню, а кнопка «Выйти» есть, как сейчас. Подложка под окном
  принудительной смены пароля по-прежнему пустая и скрыта от вспомогательных технологий.

## 4. Нефункциональные требования

- **NFR-1 (бэкенд не меняется):** Серверная часть, API и OpenAPI-схема НЕ ДОЛЖНЫ меняться.
  Стартовый экран выбирается по уже существующему профилю сессии. Ответ на вход возможностей не
  содержит, поэтому выбор по возможностям делается только по профилю сессии.
- **NFR-2 (локализация, 001/NFR-6, 001/AC-98):** Все строки, которые добавляются, берутся из
  словаря. Строки «Главная» и «На главную» ДОЛЖНЫ быть удалены из словаря и не показываться в
  интерфейсе. Новая строка — имя навигации бокового меню «Меню».
- **NFR-3 (доступность, 001/NFR-7):**
  - Боковое меню ДОЛЖНО быть ориентиром навигации (landmark `navigation`) с доступным именем
    «Меню» из словаря (решение владельца, Q-5 а). Это имя отличается от имени навигации по
    страницам («Постраничная навигация»).
  - «Выйти» ДОЛЖНА быть кнопкой (роль `button`, доступное имя «Выйти»), а не ссылкой.
    Она активируется клавишами Enter и Space и имеет видимый фокус.
  - Порядок обхода клавишей Tab на экране с боковым меню: пункты меню в видимом порядке, затем
    «Выйти», затем содержимое экрана.
  - Контраст — по WCAG AA, как сейчас.
- **NFR-4 (совместимость и сборка):** Новых зависимостей нет. Проверки фронтенда
  (`cd frontend && npm run lint && npm run typecheck && npm test`) и полная проверка
  `bash scripts/check.sh` проходят.
- **NFR-5 (тесты):** Тесты, которые проверяли удаляемое поведение («Главная», «На главную»,
  переход на `/` после входа или смены пароля), ДОЛЖНЫ быть заменены тестами критериев этой
  спецификации, а не просто удалены. Ослаблять проверки не допускается (CLAUDE.md). Перечень
  затрагиваемых тестов — раздел 9.

Требований к ML-моделям нет: в фиче нет DS/ML-кода, метрик и случайности.

## 7. Допущения и зависимости

- Состав возможностей ролей — по 001/BR-11 и 002 (раздел 5). Роли не пересекаются по
  `business_access` и `manage_accounts`. Цепочка FR-3 даёт для трёх ролей результат решения
  владельца (2) и определена для любых наборов возможностей.
- Ответ на вход содержит роль и флаг смены пароля, но не возможности. Поэтому стартовый экран
  после входа выбирается по профилю сессии (NFR-1).
- Экран «Список проектов» уже сам ставит фокус на свой заголовок при открытии. Экраны
  «Учётные записи» и «Журнал аудита» сейчас этого не делают. FR-15 и FR-16 требуют фокус на
  заголовке стартового экрана.
- В приложении содержимое уже находится внутри ориентира `main`. Ориентир `navigation` бокового
  меню находится внутри него, как сейчас. Перестройка ориентиров страницы — вне рамок.
- **Порядок реализации:** 003, затем 004 (решение владельца, 004/Q-7). 004 добавляет в боковое
  меню кнопку «Задача» между пунктами разделов и «Выйти» и дополняет AC-19, AC-27, AC-28,
  AC-30 этой спецификации своими критериями (004, раздел 11). Требования 003 от этого не
  меняются.
- Фикстуры AC — моки сети в тестах фронтенда. Реальные данные и GPU не нужны.

## 10. Сверка со spec 001 и 002: противоречия и нужные правки

Spec 001 и 002 этой фичей не правятся. Ниже — что сверено и что потребует правки отдельно.

**Противоречий в требованиях нет:**

1. **001/FR-10.** Меню по возможностям, скрытие не считается защитой. Согласовано: стартовый
   экран — удобство интерфейса, проверки остаются на сервере. Правка не нужна.
2. **001/FR-55, 001/FR-56, 001/FR-66, OI-6, OI-75 (v0.17).** В интерфейсе только
   принудительная смена пароля. Согласовано через FR-12: «Сменить пароль» не добавляется, и
   условная часть решения владельца (3) не применяется. Правка не нужна.
3. **001/AC-75 и 001/AC-113.** Это проверки уровня API: вход, смена одноразового пароля,
   выход, 403 без роли. От «Главной» не зависят, экран `/no-role` не меняется (FR-17). Правка
   не нужна.
4. **001/AC-98, 001/NFR-6.** Словарь строк. Удаление «Главная» и «На главную» согласовано
   (NFR-2). `docs/acceptance/mvp-demo.md` «Главную» не упоминает.

   клавиатурной проверки меняется: ТА начинает с «Учётных записей», БА — с «Проектов».
   Правка текста не обязательна. Ручная проверка по AC-31.
6. **001/FR-11 (отказ в доступе).** По Q-2 а) путь сохраняется, данных раздела не
   запрашивается — как сейчас. Правка не нужна.
