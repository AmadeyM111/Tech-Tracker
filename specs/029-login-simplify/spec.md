# Spec: Упрощённый вход (email или логин, «Запомнить меня», magic link, Яндекс ID / VK ID / Google)

- **ID:** 029-login-simplify
- **Статус:** APPROVED (2026-11-14: владелец принял все рекомендации Q-1…Q-10 раздела 8)
- **Дата:** 2026-11-13
- **Связанные:** ADR-0026 (принято), спеки 005 (экран входа), 019 (самостоятельная регистрация, генерация логина), 007 (сброс пароля, токены и лимиты), 027 (личные проекты).

## 1. Контекст и цель
Сейчас вход только по логину и паролю (`normalize_login` в `domain/auth/provider.py`). Владелец хочет, чтобы вход был проще: одно поле для email или логина, вход без пароля по ссылке из письма, вход через российские и иностранный аккаунты, длинная сессия по желанию. Пароль остаётся, но перестаёт быть единственным способом.

Нерешённая часть текущей модели: `app_user.password_hash` имеет `NOT NULL`, поэтому учётка, созданная через провайдера, потребует либо nullable-колонку, либо отдельный признак «без пароля» (миграция, см. раздел 7).

## 2. Пользовательские сценарии
- Как пользователь, я ввожу email или логин в одно поле и пароль, чтобы войти.
- Как пользователь, я ставлю «Запомнить меня», чтобы не входить неделями на своём компьютере.
- Как пользователь без пароля, я ввожу email, получаю письмо со ссылкой и вхожу одним кликом.
- Как пользователь, я вхожу через Яндекс ID, VK ID или Google, и если у меня ещё нет учётки, она создаётся сама (роль «Пользователь»).
- Как пользователь с учёткой по паролю, я привязываю внешний аккаунт из профиля и могу отвязать, если останется другой способ входа.

## 3. Функциональные требования

### 3.1 Вход по email или логину (пункт 1)
- **FR-1.** Поле «Email или логин» ДОЛЖНО принимать оба варианта. Значение, содержащее «@», трактуется как email (нижний регистр, как у `email_lower` в 007/PR-1), иное — как логин (нижний регистр, FR-73). Требуется проверить по текущему шаблону логина, что «@» в логине недопустим; иначе разбор неоднозначен.
- **FR-2.** Ответ на неверные данные ДОЛЖЕН быть одинаковым для «неизвестный email», «неизвестный логин» и «неверный пароль» (без перечисления учётных записей, как сейчас).
- **FR-3.** Блокировка по неверному паролю (5 неудач, 15 минут, `login_max_failures` / `login_lock_duration`) ДОЛЖНА действовать на учётку независимо от того, введён email или логин.

### 3.2 «Запомнить меня» (пункт 2)
- **FR-4.** Флажок «Запомнить меня» по умолчанию выключен. Без него действуют текущие сроки сессии: простой 8 ч, абсолютный срок 7 дней (`session_idle_timeout`, `session_absolute_timeout`).
- **FR-5.** С флажком сессия ДОЛЖНА жить дольше: простой и абсолютный срок — 30 дней (значение — вопрос Q-4). Признак хранится в строке сессии.
- **FR-6.** Смена пароля, блокировка учётки и отзыв сессий ДОЛЖНЫ завершать длинные сессии так же, как обычные (сейчас — по FR-62, AC-39).

### 3.3 Вход по ссылке из письма — magic link (пункт 3)
- **FR-7.** Пользователь вводит email и получает письмо со ссылкой. Ответ на запрос ДОЛЖЕН быть одинаковым, есть ли такой адрес (как при сбросе пароля, 007).
- **FR-8.** Ссылка ДОЛЖНА содержать одноразовый токен, действовать 15 минут (Q-5), после использования — недействительна. В БД хранится только хэш токена (как `password_reset_token`).
- **FR-9.** Переход по ссылке ДОЛЖЕН открывать страницу подтверждения, и вход происходит по POST с кнопкой «Войти» (защита от сканеров почты, которые открывают ссылки GET-запросом и сжигают токен).
- **FR-10.** Лимиты: не больше 5 запросов на один email в час и 20 на один IP в час (по образцу `reset_limits.py`). Лимит не раскрывает существование адреса.
- **FR-11.** Magic link не требует пароля и не увеличивает счётчик неверных паролей; учётка в блокировке не входит ни по какой ссылке.

### 3.4 Вход через внешних провайдеров (пункт 4)
- **FR-12.** Провайдеры: Яндекс ID, VK ID, Google (OAuth 2.0 / OpenID Connect; мы — клиент). Провайдеры включаются отдельными флажками конфигурации; по умолчанию выключены до одобрения владельца и проверки по 152-ФЗ (Q-1).
- **FR-13.** Авторизация ДОЛЖНА использовать PKCE (`code_challenge_method=S256`), `state` длиной не меньше 32 символов и проверку `state` при обратном вызове. Состояние и `code_verifier` хранятся в БД с TTL 10 минут и одноразово (см. раздел 7).
- **FR-14.** Ключ идентичности — стабильный идентификатор провайдера (`sub` у Google, `id` или `psuid` у Яндекса, `user_id` у VK ID), а не email. Email может смениться у провайдера.
- **FR-15.** При первом входе, если учётки с этим идентификатором нет и связанного адреса нет, учётка создаётся: роль «Пользователь», логин генерируется по правилам 019 (`login_generation.py`), пароля нет. Создание открыто только при включённой самостоятельной регистрации 019 (Q-3).
- **FR-16.** Автоматическая привязка к существующей учётке по email ДОПУСТИМА ТОЛЬКО если провайдер подтверждает email (Google: `email_verified = true`). У Яндекса и VK ID признака подтверждения, по официальной документации, нет, поэтому для них автопривязки по email НЕТ (Q-2).
- **FR-17.** Если автопривязка запрещена, а учётка с таким email уже есть, вход через провайдера ДОЛЖЕН отказывать с понятным текстом и предлагать войти по паролю или ссылке, а затем привязать провайдера в профиле. Раскрывать, что учётка существует, нельзя без доказательства владения адресом (FR-2).
- **FR-18.** Привязка из профиля ДОЛЖНА требовать текущую сессию (уже вошедший пользователь) и явное подтверждение.
- **FR-19.** Отвязка из профиля ДОЛЖНА быть запрещена, если это последний способ входа (нет пароля, нет подтверждённого email для ссылки, нет другого провайдера).
- **FR-20.** Заблокированная учётка не входит ни через один провайдер (ответ как у блокировки по паролю).
- **FR-21.** Провайдерские access- и refresh-токены ДОЛЖНЫ отбрасываться после получения идентичности; в БД не хранятся (нужен только факт входа).

### 3.5 Сессии, аудит, лимиты (сквозные)
- **FR-22.** Все способы входа создают сессию тем же механизмом (`sessions.py`), в строке сессии сохраняется `auth_method` (`password`, `magic_link`, `yandex`, `vk`, `google`) и признак «Запомнить меня».
- **FR-23.** Аудит: успешный и неуспешный вход по каждому способу, отправка magic link, использование ссылки, привязка и отвязка внешнего аккаунта, создание учётки через провайдера. Адрес в журнале — хэш, как в 007 и 027 (Q-7).
- **FR-24.** 2FA в этой спеке НЕ вводится (решение владельца). Вход по ссылке в почту сам является одним фактором, поэтому безопасность почты пользователя — граница риска (раздел 6).

## 4. Нефункциональные требования
- **NFR-1 (безопасность).** Все внешние вызовы — по HTTPS; `redirect_uri` совпадает побайтно с зарегистрированным; `client_secret` (если нужен) — только из переменных окружения, не в репозитории и не в чате.
- **NFR-2 (приватность).** Запрашиваем у провайдеров только email (и идентификатор). Имя, аватар, телефон, дату рождения не запрашиваем в этой спеке.
- **NFR-3 (совместимость).** Вход по паролю и логину работает как раньше; существующие сессии и тесты 005/007/019 не меняют поведения, кроме явно перечисленного.

## 5. Критерии приёмки (черновые)
- **AC-1** (FR-1, FR-2): Given учётка с логином `ivanov` и email `i@example.ru` When вход по `I@example.ru` и паролем Then успех; When по `unknown@x.ru` Then тот же ответ, что при неверном пароле.
- **AC-2** (FR-3): Given 5 неверных паролей по email Then учётка блокируется и по логину тоже.
- **AC-3** (FR-4, FR-5): Given «Запомнить меня» выключено When сессия простаивает 8 ч Then она истекла; Given включено When простой 8 ч Then сессия жива.
- **AC-4** (FR-7…FR-9): Given magic link When открыт GET Then токен не расходуется; When POST Then вход, ссылка больше не работает.
- **AC-5** (FR-10): Given 6-й запрос ссылки на один email за час Then ответ как при успехе, письмо не отправляется.
- **AC-6** (FR-15): Given Google с `email_verified=true` и новым `sub` When первый вход Then создаётся учётка «Пользователь», логин по правилам 019, без пароля.
- **AC-7** (FR-16): Given Яндекс с email существующей учётки When вход Then автопривязки нет, предложено войти и привязать в профиле.
- **AC-8** (FR-19): Given учётка без пароля и с одним провайдером When отвязка Then отказ, последний способ входа сохранён.
- **AC-9** (FR-20): Given заблокированная учётка When вход через любой провайдер Then отказ.
- **AC-10** (FR-13): Given неверный `state` при обратном вызове Then отказ, сессия не создаётся, состояние сжигается.

## 6. Риски
| Риск | Что случится | Смягчение |
|---|---|---|
| Захват учётки через непроверенный email у Яндекса и VK ID | Злоумышленник регистрирует у провайдера адрес жертвы (если провайдер не проверяет) и получает учётку | FR-16: без автопривязки по email; привязка только из сессии |

| Смена email у провайдера | Чужой адрес у старой учётки | FR-14: ключ — стабильный идентификатор |

| 152-ФЗ, передача данных | См. ниже | Вопрос Q-1 и отдельная юридическая оценка |
| Доставляемость писем (magic link) | Ссылка не доходит | Зависит от DNS почты `leggent.ru` (SPF, DKIM), пункт 15 из `report-password-reset-followups.md` сейчас ОТЛОЖЕН; включать magic link только после исправления (Q-8) |
| Длинная сессия на чужом компьютере | Доступ сохраняется | FR-4 по умолчанию выключено; отзыв сессий в профиле |

### 6.1 152-ФЗ (оценка, не юридическое заключение)
- **Яндекс ID и VK ID** — российские сервисы. Передача email и идентификатора происходит в рамках входа, который инициирует пользователь. Что именно хранит провайдер и где — нужно уточнить у провайдера; мы этого не проверяли.
- **Google** — иностранный провайдер. Мы передаём Google только `client_id`, `redirect_uri`, PKCE и `state`; от Google получаем email и `sub`. Сама передача браузера пользователя на сервер Google и логи Google — вне нашего контроля. По ст. 12 152-ФЗ трансграничная передача требует оценки, входит ли страна получателя в перечень адекватной защиты РКН. Текст ст. 12 доступен на rulaws.ru; по данным юридических обзоров, в 2026 году редакция ст. 12 менялась (ФЗ от 26.07.2026 № 265-ФЗ). Точная редакция и перечень РКН требуют проверки юристом.
- **Magic link и почта** — письма уходят через наш SMTP. Если почтовый сервис иностранный, это тоже трансграничная передача email (вопрос Q-8).
- **Минимизация:** в этой спеке храним email, стабильный идентификатор провайдера и дату привязки. Имя и аватар не храним.

## 7. Миграция и изменения данных
Миграция: `0016` для внешних идентичностей (`0014` — OAuth, `0015` — «Запомнить меня», ветка `feat/029a-login-remember`):
1. `app_user.password_hash` — `NULL` допустим; признак «нет пароля» = `NULL`. Проверка: любой путь, читающий хэш, обрабатывает `NULL` (FR-19, вход по паролю без хэша — отказ).
2. Таблица `external_identity`: `id`, `user_id` (FK `app_user`, `ON DELETE RESTRICT`), `provider` (CHECK: `yandex`, `vk`, `google`), `provider_subject` (строка до 255), `email_at_link` (lower, nullable), `email_verified_by_provider` (bool), `linked_at`, `last_used_at`, `unlinked_at` (soft). Уникальность: `(provider, provider_subject)` где `unlinked_at IS NULL`; индекс по `user_id`.
3. Таблица `oauth_login_state`: `state_hash`, `verifier` (шифруется или хранится короткоживущим), `provider`, `purpose` (`login` / `link`), `user_id` (для привязки), `expires_at` (+10 мин), `used_at`.
4. Таблица `magic_link_token`: `token_hash`, `email_lower`, `user_id` (nullable: если адреса нет — ссылки не создаётся), `expires_at` (+15 мин), `used_at`.
5. Колонки `session.auth_method` (text, CHECK) и `session.remember` (bool, по умолчанию `false`).
6. Все таблицы — с `workspace_id` там, где сущность привязана к пространству; внешние идентичности у R1 — в единственном пространстве, колонка `workspace_id` добавляется для единообразия (уточнить).

Существующие данные не меняются: у всех учёток есть пароль, `session.auth_method` для старых сессий — `password`.

### 8.1 Что регистрировать в консолях провайдеров (черновик, пути проверить)
- **Яндекс ID:** приложение в https://oauth.yandex.ru/client/new, платформа «Веб-сервисы», Redirect URI `https://task-tracker.aiqarus.ru/api/v1/auth/external/yandex/callback` (путь предложен), доступ к email. По официальной документации при PKCE `client_secret` не обязателен (см. раздел 11, источник Яндекс ID).
- **VK ID:** кабинет VK ID для бизнеса (https://id.vk.com/about/business), приложение, доверенный redirect URL (предложен тот же путь с `/vk/`), scope `email`. Тип приложения (публичный или конфиденциальный) влияет на обмен кода: для публичного — PKCE без `service_token`.
- **Google:** Google Cloud Console → OAuth consent screen (внешний тип, scopes `openid`, `email`) → OAuth client типа «Web application», Authorized redirect URI `https://task-tracker.aiqarus.ru/api/v1/auth/external/google/callback`. Для веб-клиента Google обычно требует `client_secret` даже с PKCE — проверить.

## 10. Вне рамок
- 2FA и TOTP.
- Вход через Apple, Mail.ru, GitHub и другие провайдеры.
- Использование провайдерских API, кроме входа (контакты, аватары).
- Единый вход для нескольких пространств (в R1 одно пространство).

- Google OpenID Connect (`email`, `email_verified`, `sub`, S256, точный `redirect_uri`, эндпоинты, discovery): https://developers.google.com/identity/openid-connect/openid-connect
- 152-ФЗ, ст. 12 (текст на сайте-агрегаторе; сверить с официальным порталом): https://rulaws.ru/laws/Federalnyy-zakon-ot-27.07.2006-N-152-FZ/Statya-12/

**Не удалось проверить:** официальные страницы VK ID о регистрации приложения и о структуре id_token (домен `id.vk.com` против `id.vk.ru` и смысл `verified` — открыть вручную); актуальная редакция ст. 12 после ФЗ от 26.07.2026 № 265-ФЗ; перечень адекватной защиты РКН; требования Google к `client_secret` для веб-клиента с PKCE.
