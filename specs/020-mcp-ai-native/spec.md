# Spec: AI Native — подключение агентов через MCP

- **ID:** 020-mcp-ai-native
- **Статус:** APPROVED (контрольная точка 1 пройдена 2026-11-07; решения — ADR-0018)
- **Дата:** 2026-11-07

## 1. Контекст и цель
Трекер должен быть доступен не только через веб-интерфейс, но и из AI-агентов: кодовых
(Claude Code, Codex CLI, Cursor и др.) и чат-ассистентов. Для этого трекер выступает MCP-сервером
(Model Context Protocol) и отдаёт инструменты для работы с проектами и задачами. Агент действует
от имени пользователя и видит и меняет только то, что разрешено его роли. Цель — сделать
трекер «AI Native»: работа с задачами возможна из диалога с агентом, без переключения в UI.

## 2. Пользовательские сценарии
- Как пользователь, я хочу создать токен доступа для агента в настройках, чтобы подключить
  Claude Code к трекеру и попросить его показать мои задачи на сегодня.
- Как пользователь, я хочу отозвать токен, чтобы агент потерял доступ сразу.
- Как бизнес-пользователь, я хочу, чтобы агент не смог создать задачу другому человеку, так же
  как это запрещено в веб-интерфейсе.
- Как техадминистратор, я хочу, чтобы блокировка учётной записи отзывала её токены.
- Как пользователь, я хочу, чтобы в ленте проекта было видно, что изменение сделано через
  агента, а не вручную.

## 3. Функциональные требования
- **FR-1:** Система ДОЛЖНА выдавать пользователю персональный токен доступа (PAT). Токен
  показывается один раз; в БД хранится только хеш.
- **FR-2:** Система ДОЛЖНА принимать токен в заголовке `Authorization: Bearer` на эндпоинте
  MCP и проверять его при каждом запросе (как `get_actor` для cookie).
- **FR-3:** Система ДОЛЖНА отзывать токен по запросу пользователя; блокировка учётной записи
  ДОЛЖНА отзывать все её токены (по аналогии с ADR-0004 для сессий).
- **FR-4:** Система ДОЛЖНА предоставлять MCP-инструменты для чтения и изменения проектов,
  задач, подзадач и комментариев. Инструменты вызывают те же доменные сервисы, что и REST API;
  правила прав не дублируются.
- **FR-5:** Когда агент вызывает инструмент, на который у пользователя нет права, система
  ДОЛЖНА вернуть ошибку с тем же `code`, что и REST API (например `forbidden`), а не выполнять
  действие.
- **FR-6:** Система ДОЛЖНА возвращать в `tools/list` только инструменты, доступные роли
  владельца токена.
- **FR-7:** Система ДОЛЖНА записывать в активность изменения, сделанные через MCP, с указанием
  клиента (имя токена), например «Иван через «Claude Code на ноутбуке».
- **FR-8:** Система ДОЛЖНА предоставлять команду `gtrack mcp` (stdio), которую локальные
  агенты запускают как процесс. Команда пересылает вызовы в API по токену; бизнес-логики в
  ней нет.
- **FR-9:** Система ДОЛЖНА проверять заголовок `Origin` на HTTP-эндпоинте MCP (защита от DNS
  rebinding, требование спецификации MCP).
- **FR-10:** В документации ДОЛЖНЫ быть готовые фрагменты настройки для Claude Code и
  Codex CLI и описание ограничений для облачных клиентов (см. OI-1).

## 4. Нефункциональные требования
- **NFR-1 (безопасность):** токены хранятся как хеш (SHA-256 от случайных 256 бит); сравнение
  constant-time; токен не попадает в логи и ответы, кроме однократного показа при создании.
- **NFR-2 (изоляция):** каждый запрос MCP фильтруется по `workspace_id` токена.
- **NFR-3 (без внешних вызовов):** новых исходящих запросов и телеметрии нет.
- **NFR-4 (производительность):** вызов инструмента чтения — в пределах норматива REST
  «открытие списка задач» (300 мс p95 на объёме ТЗ §5).
- **NFR-5 (совместимость):** протокол MCP версии, поддерживаемой официальным SDK, зафиксированной
  в `plan.md`.

## 5. Критерии приёмки
- **AC-1** (FR-1): Given вход пользователя When создан токен Then токен показан один раз, в БД
  только хеш, повторный просмотр токена невозможен.
- **AC-2** (FR-2, граничный): Given запрос к MCP без токена или с неверным токеном When вызов
  Then 401 в формате `{"detail","code"}`.
- **AC-3** (FR-3): Given активный токен When пользователь его отзывает Then следующий запрос с
  ним даёт 401.
- **AC-4** (FR-3): Given пользователь с токеном When техадмин блокирует его Then токен отвергается.
- **AC-5** (FR-4, FR-5): Given роль «Пользователь» When агент вызывает создание задачи другому
  Then 403 `forbidden`, задача не создана (ТЗ §4, проверка 6).
- **AC-6** (FR-6): Given роль «Техадмин» When `tools/list` Then нет инструментов задач и проектов.
- **AC-7** (FR-4): Given бизнес-пользователь When агент создаёт задачу и меняет статус Then
  изменения видны в REST API и в веб-интерфейсе.
- **AC-8** (FR-7): Given изменение через MCP When открыта лента проекта Then запись содержит
  имя токена.
- **AC-9** (FR-8): Given `gtrack mcp` и токен в окружении When Claude Code подключён по
  инструкции Then он перечисляет задачи пользователя. _Ручная проверка._
- **AC-10** (FR-9, граничный): Given запрос с чужим `Origin` When обращение к HTTP-эндпоинту MCP
  Then 403.
- **AC-11** (NFR-3): Given сборка When `scripts/check.sh` Then нет новых исходящих адресов в коде.
- **AC-12** (FR-10): Given `docs/` When открыт файл интеграций Then есть рабочие фрагменты
  конфигурации для Claude Code и Codex CLI.

## 6. Вне рамок (Out of scope)
- Встроенные LLM-функции трекера (суммаризация, автогенерация задач). Это отдельная фича.
- Инструменты CRM: раздел не реализован (ADR-0012, R1.3).
- OAuth-поток для MCP-клиентов. В R1 — только персональные токены.
- Подключение облачных клиентов (ChatGPT и др.) по публичному адресу — см. OI-1.
- Изменение ролей, учётных записей, аудита и экспорта через MCP.

## 7. Допущения и зависимости
- Допущение: официальный Python SDK MCP подходит по лицензии (MIT) и весу; проверить в plan.
- Зависимость от `backend/app/domain/tasks` и `projects` — сервисы уже есть.
- Новая таблица токенов и миграция Alembic (AGENTS.md: миграция в том же коммите).
- Новый ADR нужен до плана: токены (ADR-0004 описывает только сессии) и решение по OI-1.
