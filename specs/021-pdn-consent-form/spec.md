# Spec: Согласие на обработку персональных данных (спека 021, v2)

- **ID:** 021-pdn-consent-form
- **Статус:** APPROVED (владелец возобновил спеку и принял решения 2026-11-15; решения приоритетнее черновика v1). Реализация: ветка `feat/021-pdn-consent`, PR #56, миграция `0017`.
- **Версия:** 2 (v1 — черновик 2026-11-08, ветка `docs/backlog-specs-2026-11-08`; заменяется этим файлом)
- **Связано:** ADR-0019 (ИБ одобрила ввод ПДн для MVP), ADR-0026 (вход через провайдеров), ADR-0027 (эта спека), спека 019 (регистрация),
  спека 029 (вход, провайдеры; ветка `feat/029-providers`, PR #55), `docs/data-model.md`
- **Макеты:** `Shared/Design/pdn-consent/` и `Shared/Design/gtrack-pdn-consent/pdn-consent-design.md` (Design Agent). Расхождения с решениями владельца: блок оператора с ИП/ИНН до флажка, блок согласия и диалог отзыва в профиле, оглавление `/privacy`, экран ТА — не реализованы (реквизиты — заглушки, отзыв вручную, §6, §10).

  Рекламную шапку и дисклеймер консультанта в страницы не переносим.

## 1. Цель
При регистрации (в том числе через Яндекс ID и Google) пользователь отмечает обязательный флажок согласия на обработку ПДн и
принятия Политики конфиденциальности. Факт и версия согласия пишутся в БД. Уже существующие пользователи один раз подтверждают
согласие при следующем входе. Тексты Политики и Согласия публично доступны без входа.

## 2. Решения владельца (2026-11-15)
1. Обязательный флажок на `/register`: «Я согласен на обработку персональных данных и принимаю Политику конфиденциальности», со
   ссылками на `/consent` и `/privacy`. Без флажка регистрация и вход через Яндекс/Google недоступны.
2. Факт и версия согласия — в БД (миграция `0017`). Существующим пользователям экран согласия показывается при следующем входе.
3. Тексты — из шаблонов юр. консультанта.
4. Публичные страницы без входа: `/privacy` (политика) и `/consent` (согласие). Тексты лежат в репозитории как данные с версией
   (дата), не в вёрстке.
5. Email для обращений по данным (п. 4.1–4.2 политики): `support@leggent.ru`.
6. Реквизиты оператора: ИП работает онлайн, почтового адреса нет (2026-11-15). Заполнены наименование (ИП Суриков Антон Евгеньевич),
   ОГРНИП 324774600650295, ИНН 771975146252; адрес для обращений — электронная почта `support@leggent.ru`, сведения об ИП — в ЕГРИП
   по ИНН. Реквизиты лежат в одном месте (`requisites.json`). Достаточно ли этого для Политики по 152-ФЗ, решает юрист (пометка
   «[предложение, подтвердить у юриста]» в текстах); заглушка `[ЗАПОЛНИТЬ]` остаётся защитой, если поле реквизитов снова опустеет (§7).

## 3. Функциональные требования
- **FR-1 (данные).** Тексты Политики и Согласия — файлы данных `backend/app/domain/legal/documents/{privacy,consent}.json` с
  полем `version` (дата `ГГГГ-ММ-ДД`) и разделами. Версия обоих документов одна (`CURRENT_VERSION`); тест следит за совпадением.
  Реквизиты и email для обращений — единственный файл `backend/app/domain/legal/documents/requisites.json`; в текстах — подстановки
  `{operator_name}`, `{operator_ogrn}`, `{operator_inn}`, `{contact_email}`; почтовый адрес оператора необязателен (`operator_postal_address`, в тексте только если задан).
- **FR-2 (публичные тексты).** `GET /api/v1/legal` и `GET /api/v1/legal/{kind}` (`kind` = `privacy` | `consent`) доступны без входа.
  Страницы фронта `/privacy` и `/consent` показывают тексты; шапка и дисклеймер консультанта не переносятся.
- **FR-3 (регистрация по email).** `POST /api/v1/auth/registration/request` принимает `pdn_consent` и `pdn_consent_version`. Без
  `pdn_consent: true` и с версией, не равной текущей, заявка отклоняется 422 (`pdn_consent_required`,
  `pdn_consent_version_mismatch`) до всякой другой обработки данных формы. Факт и версия сохраняются в заявке и при подтверждении
  email копируются в `app_user`.
- **FR-4 (вход через провайдера).** `GET /api/v1/auth/external/{provider}/start` принимает `consent=true` и `consent_version`. Без
  них при включённой функции старт отклоняется редиректом на `/login?external_error=pdn_consent_required`. Если провайдер вернул
  пользователя, которого нет в системе, учётная запись создаётся сразу с согласием из состояния входа. Этот пункт реализуется
  после слияния PR #55 (§7; сделано в этом же PR после ребейза).
  Существующий пользователь, вошедший через провайдера с флажком на `/login`, получает согласие записанным (событие
  `user.pdn_consent_given` один раз на версию; решение оркестратора 2026-11-15).
- **FR-5 (экран подтверждения).** Пользователь без согласия текущей версии (в том числе существующие) получает на все
  маршруты, кроме выхода, смены пароля и `POST /api/v1/me/pdn-consent`, 403 `pdn_consent_pending`. Фронт ведёт на `/pdn-consent`
  («Подтвердите согласие»). Принятие: `POST /api/v1/me/pdn-consent` (204). Выход доступен всегда.
- **FR-6 (новая версия текста).** При выходе новой версии (`CURRENT_VERSION` изменилась) все пользователи с прежней версией
  проходят FR-5 заново.
- **FR-7 (аудит).** Принятие пишет событие `user.pdn_consent_given` (актор и объект — пользователь, `details.version`) без ПДн.
- **FR-8 (флаг).** `PDN_CONSENT_ENABLED` (по умолчанию `false`). При `false`: флажок не показывается, FR-3…FR-6 не действуют,
  `GET /legal/{kind}` отвечает 404 `feature_disabled`, `GET /legal` отдаёт `enabled: false`.
- **FR-9 (гейт реквизитов).** Если `PDN_CONSENT_ENABLED=true` и `ENV=production`, а в текстах или реквизитах остался `[ЗАПОЛНИТЬ]`,
  приложение не стартует (Fail Fast). Скрипт `scripts/check_legal_requisites.py` проверяет то же вручную и в деплое.

## 4. Контракт (имена, фиксируются первым коммитом)
| Что | Имя |
|---|---|
| Настройка | `PDN_CONSENT_ENABLED` |
| Колонки `app_user` | `pdn_consent_version text NULL`, `pdn_consented_at timestamptz NULL` |
| Колонки `registration_request` | `pdn_consent_version text NULL`, `pdn_consent_at timestamptz NULL` |
| Колонка состояния входа провайдера (`oauth_login_state`, спека 029) | `pdn_consent_version text NULL` (добавляет миграция 0017) |
| Поля тела регистрации | `pdn_consent: bool` (по умолчанию `false`), `pdn_consent_version: str \| null` |
| Параметры старта провайдера | `consent: bool = false`, `consent_version: str \| null` |
| Ошибка 422 (поле `pdn_consent`) | `pdn_consent_required` |
| Ошибка 422 (поле `pdn_consent`) | `pdn_consent_version_mismatch` |
| Ошибка 403 гейта | `pdn_consent_pending` |
| Ошибка редиректа входа провайдера | `external_error=pdn_consent_required` |
| Публичное API | `GET /api/v1/legal` → `{enabled, version}`; `GET /api/v1/legal/{kind}` → `{kind, title, version, effective_date, sections: [{heading, paragraphs}]}` |
| Принятие | `POST /api/v1/me/pdn-consent` `{pdn_consent: true, pdn_consent_version}` → 204 |
| Событие аудита | `user.pdn_consent_given` |
| Маршруты фронта | `/privacy`, `/consent` (публичные), `/pdn-consent` (экран подтверждения, нужна сессия), флажок `pdn_consent` на `/register` и над кнопками провайдеров на `/login` |

## 5. Данные и цели (из `docs/data-model.md`, спек 019 и 029; перечень не расширяем)
- **Обрабатываем:** email, имя, фамилия, логин, пароль (только хеш Argon2id), роль, IP-адрес и cookie сессии, журнал аудита;
  для входа через Яндекс/Google — идентификатор у провайдера и email.
- **Цели:** создание и ведение учётной записи; вход и защита от подбора пароля; разграничение прав по ролям; учёт действий в
  журнале аудита; отправка писем подтверждения регистрации и сброса пароля.
- **Вход через провайдера = передача данных провайдеру** (Яндекс — РФ; Google — иностранный, спека 029 §6.1, Q-1): в текстах
  отмечено отдельным абзацем.
- **Действия с данными и сроки хранения** — предложение, подтвердить у юриста: пометка `[предложение, подтвердить у юриста]` в
  текстах. Предложены: сбор, запись, хранение, использование, уточнение, передача провайдеру входа и почтовому сервису, блокирование,
  удаление; хранение — пока существует учётная запись и до отзыва согласия; после отзыва — прекращение обработки и уничтожение
  в срок до 30 дней, если иное не требует закон (152-ФЗ, ст. 21 ч. 5).

## 6. Отзыв согласия
Выбран путь без нового кода: обращение на `support@leggent.ru` (п. 4.1–4.2 политики), обработка вручную техадминистратором.
Автоматического удаления нет (спека 023 отложена, правило «пользователи не удаляются»). Решение за владельцем и оркестратором.
Что реально делать техадмину при отзыве (блокировка учётной записи, обезличивание полей, удаление), — вне этой спеки.

## 7. Выкатка и порядок слияния
- Миграция `0017` цепляется после `0016` (PR #55, спека 029; слит 2026-11-15, ветка перебазирована на `main`, `down_revision = 0016`).
- Миграция останавливает автодеплой: выкатка вручную (`ALLOW_MIGRATIONS=1`).
- `PDN_CONSENT_ENABLED` в проде включается только когда `requisites.json` заполнен (FR-9) и владелец одобрил тексты.

## 8. Нефункциональные требования
- **NFR-1.** ПДн не попадают в логи и в аудит (только версия текста).
- **NFR-2.** Новых зависимостей нет. Применённые миграции не правятся.
- **NFR-3.** Интерфейс и тексты — на русском; публичные страницы работают без входа и проходят проверку Design Agent.

## 9. Критерии приёмки
- **AC-1.** Регистрация без `pdn_consent` и с устаревшей версией — 422 с кодами из §4; с флажком — заявка сохранена с версией.
- **AC-2.** После подтверждения email у пользователя `pdn_consent_version` = текущая, `pdn_consented_at` заполнено.
- **AC-3.** Пользователь без согласия: любой маршрут кроме перечисленных — 403 `pdn_consent_pending`; после `POST /me/pdn-consent` — доступ.
- **AC-4.** `GET /legal/privacy` и `/legal/consent` без cookie — 200; тексты без рекламной шапки и дисклеймера.
- **AC-5.** `PDN_CONSENT_ENABLED=false`: поведение как до спеки (регистрация без флажка, гейта нет).
- **AC-6.** Запуск в `production` с флагом и `[ЗАПОЛНИТЬ]` — отказ старта; `scripts/check_legal_requisites.py` возвращает ненулевой код.
- **AC-7.** События `user.pdn_consent_given` в журнале; в `details` только версия.
- **AC-8 (провайдеры, после #55).** Старт без `consent` — редирект с `pdn_consent_required`; новый пользователь через провайдера создан с согласием.

## 10. Вне рамок
Автоматический отзыв и удаление учётной записи; экспорт и просмотр согласий техадмином; согласия контрагентов; PDF; согласие на
иные ПДн (паспорт, СНИЛС, ИНН и пр.); трансграничная оценка по ст. 12 152-ФЗ (спека 029, Q-1).
