# Проект: правила для агентов (SDD)

## Процесс
Работаем по Spec-Driven Development. Любая нетривиальная фича проходит этапы:
spec → plan → tasks → (tests → code → review) по каждой задаче → финальная приёмка.
Запуск цикла: `/sdd <описание фичи>`.

## Артефакты
Все артефакты фичи лежат в `specs/<NNN-feature-slug>/`:
- `context.md`  — обзор кодовой базы (scout)
- `spec.md`     — ЧТО и ЗАЧЕМ: требования и критерии приёмки (spec-writer)
- `plan.md`     — КАК: архитектура, интерфейсы, решения (architect)
- `tasks.md`    — упорядоченные задачи со статусами (architect, статусы ведёт оркестратор)
- `reviews/`    — вердикты ревьюера по задачам (reviewer отвечает, оркестратор сохраняет)

Источник истины — `spec.md`. Код, противоречащий spec, — ошибка кода или повод
вернуться к spec, но никогда не повод молча менять spec.

## Окружение (заполните под свой проект)
- Python: <версия>, окружение: <uv / conda / venv>, команда активации: `<...>`
- Тесты: `<pytest -q ...>`
- Линтер/типы: `<ruff check . && mypy src>`
- Данные: `<путь>` — ТОЛЬКО ЧТЕНИЕ. Никогда не изменять и не удалять исходные данные.
- GPU: перед запуском проверять `nvidia-smi`; не занимать чужие карты.

## Правила для DS/ML-кода
- Никаких полных обучений внутри цикла. Для проверки — smoke-запуск:
  маленький сабсет данных, `--max-steps`/`--limit`, фиксированный seed.
- Seed фиксируется явно во всех экспериментах и тестах.
- Ноутбуки: логику выносить в `.py`-модули, ноутбук только вызывает их.
  Если правите `.ipynb` — не коммитить выводы ячеек.
- Большие логи и выводы не вставлять в контекст целиком: сначала сжать (scout).
- Новые зависимости — только если это указано в plan.md.

## Общие запреты
- Не делать `git push`, не менять удалённые ветки, не трогать CI-секреты.
- Не удалять тесты и не ослаблять assert-ы, чтобы «позеленить» прогон.
- Не выходить за файлы, перечисленные в задаче, без явной причины в отчёте.
