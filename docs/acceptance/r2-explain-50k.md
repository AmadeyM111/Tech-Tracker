# Замер запросов «Сводки» и счётчика уведомлений на 50 000 задач (R2, локально)

- **Дата:** 2026-11-10 · **Автор:** GTrack R2 · **Основание:** ревью 008 (EXPLAIN на 50 000 задач), ревью 012.
- **Стенд:** локальный Docker PostgreSQL 16.15 на ноутбуке разработчика (не стенд пилота 3 vCPU / 6 ГБ), `shared_buffers` по умолчанию. Данные синтетические.
- **Данные:** 1 пространство, 21 пользователь, 50 проектов, **50 000 задач** (45 000 верхнего уровня + 5 000 подзадач; 20 % без срока; сроки ±45 дней; статусы и приоритеты случайно), **50 000 уведомлений** (20 000 у одного пользователя, 60 % прочитано, возраст до 200 дней).
- **Акторы:** `perf.all` — участник всех 50 проектов (худший случай: видны все 50 000 задач); `perf.some` — участник 10 проектов.
- **Как повторить:** `scripts/explain_r2_queries.py` (только БД `*_test`; инструкция в начале файла). Сырой вывод `EXPLAIN (ANALYZE, BUFFERS)` — `r2-explain-50k.output.txt` (первый запуск: нагрузка на машину не измерялась, по временам — спокойная) и `r2-explain-50k.loaded-run.txt` (та же БД, машина занята посторонней нагрузкой, load average ≈ 7,5).
- **Цель:** p95 ≤ 500 мс (008/NFR-1, R2 NFR-09). Это замер самих запросов (функция домена, без HTTP, сериализации и сети), поэтому он оценка нижней границы; нагрузочный замер по API — спека 016 (T-10, ведёт TechTracker).

## Выводы

1. **Индекс не нужен.** В первом запуске все запросы «Сводки» укладываются в 50 мс (худший — последняя страница без фильтров на 50 000 задач, ≈ 47 мс); счётчик уведомлений — единицы миллисекунд. Это на порядок ниже порога 500 мс.
2. **Планы.** Все запросы «Сводки» читают таблицу `task` последовательным проходом по 50 000 строк (`Seq Scan on task` + `Hash Join` с проектами по членству), затем `top-N heapsort` под `ORDER BY due_date NULLS LAST, id LIMIT 51`. Индекс `(workspace_id, due_date, id) WHERE deleted_at IS NULL` позволил бы идти по порядку сортировки, но не отменяет полный подсчёт для плиток и `total` (`COUNT` всё равно проходит все видимые задачи), поэтому выигрыш был бы только у самого списка и только до сотен тысяч задач. Миграцию R2 не предлагаю.
3. **Счётчик уведомлений** (`unread_count`) идёт по индексу `ix_notification_recipient_id_read_at_created_at` (Bitmap Index Scan) и затем соединяется с задачами и проектами по первичному ключу; список — по `ix_notification_created_at` с досрочной остановкой. Для пользователя с 20 000 уведомлений за 90 дней видимых ≈ 9 000 (оценка плана): 5–8 мс в первом запуске.
4. **Оговорка про нагрузку.** Запросы упираются в CPU, поэтому при посторонней нагрузке на машину (load ≈ 7,5) те же запросы замедлились в 10–25 раз, а худшие (список без фильтров, плитки) оказались на 360–510 мс, у самого порога 500 мс. Стенд пилота (3 vCPU) выделен под GTrack, но замер на нём нужен: **действие — T-10 (спека 016) на стенде пилота**; если там p95 списка окажется выше 300 мс, первыми кандидатами будут индекс под сортировку списка и/или кэширование плиток (решение — после замера, миграцию согласует оркестратор).
5. **Глубокая пагинация.** Страница 800 из 1000 (`OFFSET 39 950`) делает внешнюю сортировку на диск (`external merge`, ≈ 8 МБ) — 47 мс в первом запуске; в интерфейсе «Сводки» такая страница недостижима (кнопки «вперёд/назад», 50 строк).
