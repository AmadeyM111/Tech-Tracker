# Чек-лист приёмки MVP-демо

Ручной чек-лист R1 (MVP, решение D-64 в `specs/001-pilot-r1/plan.md`, ADR-0012). Он закрывает
критерии, которые помечены в `specs/001-pilot-r1/spec.md` как *ручной*: AC-1, AC-5, AC-97 и
AC-98 и AC-132 (логины в написании при создании, раздел 5), а также сценарий демо UF-2…UF-6. AC-107 проверяется ручным вариантом (опрос сервера с порогом 15 с,
раздел 6); автоматизированный e2e отложен. Остальные критерии MVP закрыты автотестами (`bash scripts/check.sh`, трассировка -
plan §11.7). Состав MVP и отложенное описаны в [README](../../README.md) и
[ADR-0012](../adr/0012-mvp-task-tracker-first.md).

## Условия прогона

- Браузер: Chromium (актуальная стабильная версия). Для пунктов с двумя пользователями -
  два профиля браузера (или обычное окно и окно инкогнито).
- Чистая машина с Docker (Compose v2), порты 80 и 443 свободны, стек запущен по README
  («Быстрый старт»).
- Демо-данные загружены командой `docker compose exec api gostracker demo-data`; пароли -
  в `/data/secrets/demo-passwords.txt` (см. README).
- Результат фиксируйте в отметках `- [x]`; найденные дефекты записывайте отдельным списком в
  конце прогона (дата, версия `git rev-parse --short HEAD`, проверяющий).

## 1. Развёртывание и демо-данные (AC-1)

- [ ] AC-1: на чистой машине выполнены `git clone`, `cp .env.example .env`,
  `docker compose up -d --build --wait`, `docker compose exec api gostracker demo-data`; вход с
  демо-данными выполнен не позднее 10 минут от начала (время засечено, `date -u` в начале и в
  конце), код не правился.
- [ ] Команда `demo-data` напечатала путь к файлу паролей и счётчики (12 пользователей, 2 проекта,
  30 задач); паролей в выводе нет; в stderr есть ожидаемое предупреждение `ENV=production`
  (учётные записи `demo.*` общеизвестны; код возврата 0); файл `demo-passwords.txt` читается командой
  `docker compose exec api cat /data/secrets/demo-passwords.txt`.
- [ ] Первый вход демо-пользователя (например, `demo.ba1`) требует сменить пароль; после смены
  открывается интерфейс, а старый пароль больше не подходит.
- [ ] `https://localhost/healthz` отвечает 200 `ok`; браузер предупреждает о самоподписанном
  сертификате (ожидаемо, см. README).

## 2. Сценарий демо UF-2…UF-6

- [ ] UF-2: технический администратор (`admin` или `demo.ta`) на странице «Учётные записи»
  создаёт учётную запись, назначает роль и входит под ней; блокирует пользователя - тот больше не
  может войти; разблокирует - вход снова возможен.
- [ ] UF-3: бизнес-администратор (`demo.ba1`) создаёт проект, добавляет участников, ставит
  несколько задач со сроками и исполнителями; каждый исполнитель в списке «Мои задачи» видит
  ровно назначенные ему задачи.
- [ ] UF-3 (права): владелец передаёт владение проектом другому бизнес-администратору; запись о
  передаче видна техническому администратору в журнале аудита.
- [ ] UF-4: исполнитель открывает задачу, добавляет три подзадачи и закрывает их по одной;
  прогресс родителя растёт (33 %, 66 %, 100 % - округление вниз, FR-22); подзадача «На проверке» закрытой не считается.
- [ ] UF-5: участник на вкладке «Доска» переносит карточку в другую колонку; другой участник после
  опроса (не позднее 15 с) видит новый статус (AC-5).
- [ ] UF-6: участник на вкладке «Задачи» фильтрует список по исполнителю и по статусу, открывает
  карточку и добавляет комментарий; в поле комментария вводит `<b>жирный</b> <i>текст</i>` - после
  отправки виден текст «жирный текст» без тегов и без форматирования, скрипт не выполняется
  (HTML вырезается, D-60).
- [ ] UF-3 (права БА, FR-8, FR-9 фичи 002): `demo.ba2` (участник, не владелец проекта
  «Внедрение трекера», владелец - `demo.ba1`) открывает чужую задачу (автор - `demo.ba1`,
  исполнитель - другой пользователь) - правка, смена исполнителя и удаление задачи ему
  доступны без передачи владения (так же удаление чужого комментария); удаление проверяйте
  на задаче и комментарии, заведённых для проверки, демо-задачи не удалять. Владение проектом
  `demo.ba2` может принять от `demo.ba1` как участник с ролью «Бизнес-администратор»; передать
  владение любого проекта вправе любой Бизнес-администратор (получатель - участник проекта с
  этой ролью). Это осознанное правило, его показывают заказчику (ADR-0013).
- [ ] 002/AC-27 (три роли, ручной; FR-20, FR-21): пункт выполняется на двух стеках. Шаг 1
  обязателен для приёмки и выполняется на любом стеке, обновлённом по
  `docs/adr/0013-three-roles.md`, если в его журнале есть исторические записи со смешанной
  ролью (в журналах рабочих стеков такие записи есть) и записи миграции 0006 «снятие роли»;
  выполнять его именно на стеке, обновлённом с демо версии 001, не требуется. Приёмка
  выполняется на обновлённом стеке, чистая установка шаг 1 не заменяет (упразднённой роли в её
  журнале нет). Шаги 2-4 - на чистой установке с демо-данными, где есть `demo.ba4` и `demo.ba3` (демо-данные в непустую
  систему не загружаются, а `demo.ba4` в демо 001 нет). (1) Журнал: технический администратор
  открывает «Журнал аудита» - у исторических записей показано «Смешанная роль» (прежнее
  название упразднённой роли), латинского кода роли нигде нет. (2) Выбор роли: `demo.ta` на странице «Учётные записи»
  открывает выбор роли у учётной записи - предложены только «Техадминистратор»,
  «Бизнес-администратор», «Пользователь» и «Без роли». (3) БА - участник. Подготовка:
  `demo.ba1` (владелец) заводит в «Внедрение трекера» задачу T для проверки (исполнитель -
  `demo.user1`) и отдельный проект для проверки с участником `demo.ba4`; `demo.user1`
  оставляет к T комментарий. Затем `demo.ba4` (участник, не владелец проекта, не автор и не
  исполнитель T) выполняет по порядку, каждый раз без ответа 403. Проект «Внедрение
  трекера»: правка проекта (название и описание; после проверки вернуть прежние); участники
  (добавить не участника `demo.user5` и исключить именно его; действующих участников не
  исключать - у исключённого очищается исполнитель его задач, в том числе мягко удалённых);
  передача владения `demo.ba2` (участнику с ролью «Бизнес-администратор», не совпадающему с
  действующим владельцем `demo.ba1`), затем обратно `demo.ba1`. Чужая задача T: полная правка
  (все поля, включая статус); смена исполнителя; создание подзадачи другому участнику - в два
  шага, потому что форма подзадачи не выбирает исполнителя: сначала создать подзадачу, затем
  сменить исполнителя в её карточке; удаление чужого комментария `demo.user1`; удаление задачи T.
  Удаление проекта - только на проекте для проверки; демо-проекты не удалять. (4) БА - не
  участник: `demo.ba3` (не участник проекта «Внедрение трекера») открывает список проектов,
  открывает проект «Внедрение трекера» (карточка: название и владелец; задач и
  комментариев не видно; число задач показано только в списке проектов) и добавляет себя в
  участники; после этого содержимое проекта ему доступно; затем `demo.ba3` исключает себя из
  участников, чтобы шаг можно было повторить и демо осталось прежним.
- [ ] UF-6 (удаление): удалённая задача пропадает из списков и с доски, а её адрес показывает
  «не найдено»; восстановить задачу нельзя - корзины в MVP нет.

## 3. Доска: перетаскивание мышью (AC-5, AC-97 в объёме MVP)

Перечень ручной проверки из заметок ревью T86 (`specs/001-pilot-r1/tasks.md`, T83–T86).

- [ ] Мышью: карточка переносится в другую колонку; статус задачи в карточке задачи совпадает с
  колонкой после обновления страницы.
- [ ] Мышью: сброс между двумя карточками колонки, сброс на заголовок колонки и сброс в пустую
  колонку; порядок карточек после обновления страницы сохраняется.
- [ ] Высокая карточка (длинное название, срок, исполнитель, прогресс подзадач) переносится
  целиком, без обрезки и без «прыжков» списка.
- [ ] Enter на ссылке карточки открывает карточку задачи; перенос, начатый за текст ссылки, не
  уводит на `/tasks/<id>`.
- [ ] Опрос во время переноса не сбрасывает карточку: список замирает до сброса и обновляется
  после него.
- [ ] Медленная сеть (в DevTools - Slow 3G): повторный перенос во время выполнения предыдущего не
  теряет карточку, показывается сообщение; после ответа сервера доска соответствует его данным.
- [ ] Отказ сервера (перенос, на который у пользователя нет прав, - ответ 403) возвращает
  карточку на прежнее место и показывает сообщение на русском. Как воспроизвести: `demo.userN`
  из проекта «Внедрение трекера» переносит карточку задачи, где он и не исполнитель, и не
  автор.

## 4. Доска и сценарии с клавиатуры (AC-97)

- [ ] Клавиатура: Tab доводит фокус до карточки; Space берёт карточку; стрелки перемещают её
  внутри колонки и между колонками (в том числе в пустую колонку); Space опускает; Escape
  отменяет перенос, и карточка остаётся на прежнем месте.
- [ ] Клавиатура: Enter на ссылке карточки открывает карточку задачи; Tab/Shift+Tab обходит
  элементы в логичном порядке, ловушек фокуса нет.
- [ ] Скринридер (NVDA или VoiceOver): взятие, положение над колонкой или карточкой, сброс и
  отмена переноса объявляются по-русски; у колонок есть заголовки и подписи.
- [ ] AC-97: сценарии UF-2…UF-6 выполнены только с клавиатуры, включая перемещение карточки
  между колонками и внутри колонки клавиатурной заменой перетаскивания; каждый сценарий
  завершён; фокус виден на каждом интерактивном элементе; контраст текста соответствует WCAG AA.

## 5. Язык интерфейса (AC-98)

- [ ] AC-98: на всех экранах (вход, смена пароля, «Учётные записи», журнал аудита, «Проекты»,
  «Мои задачи», доска, список задач, карточка задачи, комментарии, участники) все видимые строки
  на русском; латинских строк интерфейса вне имён собственных и логинов нет.
- [ ] Сообщения об ошибках (неверный пароль, нет прав, не найдено, сервис занят) показываются
  по-русски, без технических кодов и текстов исключений.

- [ ] AC-132 (ручная проверка, FR-73a): технический администратор создаёт учётные записи
  `Ivanov.Petr` (бизнес-администратор, владелец проекта) и `Sidorova.Anna` (участник проекта,
  исполнитель задачи с её комментарием). В браузере открыть девять экранов: «Учётные записи»,
  профиль текущего пользователя, список и карточку проекта, участников, «Мои задачи», доску,
  карточку задачи с комментариями, выбор исполнителя и участника, журнал аудита. Ожидание: везде
  логины показаны как `Ivanov.Petr` и `Sidorova.Anna`, нигде не строчными. Вход по `ivanov.petr`
  без учёта регистра выполняется; создание `IVANOV.PETR` отклоняется как занятый логин.

## 6. Опрос сервера (AC-107, ручной вариант)

Автоматизированный e2e-вариант AC-107 отложен; в MVP опрос сервера проверяется вручную
(FR-29): второй пользователь видит чужое изменение без перезагрузки страницы не позднее чем
через 15 с плюс время ответа.

- [ ] Опрос ≤ 15 с, доска: первый переносит карточку, второй (экран не перезагружается) видит
  новый статус.
- [ ] Опрос ≤ 15 с, список задач проекта: первый создаёт задачу или меняет статус, второй видит
  изменение.
- [ ] Опрос ≤ 15 с, «Мои задачи»: первый назначает задачу второму, она появляется у второго.
- [ ] Опрос ≤ 15 с, карточка задачи с комментариями: первый добавляет комментарий или меняет
  поле, второй видит его.

## Отложено (не проверяется в MVP)

Следующее в MVP не входит и в этом чек-листе не проверяется (ADR-0012; реестр - раздел «Отложено
(следующая версия)» в `specs/001-pilot-r1/tasks.md`):

- CRM: клиенты, контакты, сделки, воронка, связь сделки с проектом (UF-7, UF-8);
- метки задач;
- вложения (файлы к задачам);
- упоминания и уведомления;
- корзина, восстановление, окончательное удаление и автоочистка (удаление мягкое, корзины нет);
- архив проекта и лента активности проекта (UF-9);
- поиск (UF-10);
- экспорт и импорт (UF-11), резервная копия (UF-12);
- фильтры по сроку и общий список задач по всем проектам (FR-27a);
- замеры производительности (NFR-2) и автоматизированный e2e-вариант AC-107.
