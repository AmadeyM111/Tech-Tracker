### CD-01 — Критерий готовности (DoD) на задаче

**Боль:** технари не ставят статусы; галка «готово» врёт (задача может быть сделана без неё); нейронки не понимают, закрыта ли работа. Нужен признак завершения, который агент не выдумает.

**Кто:** ПМ/БА на проекте 8–10 человек; исполнитель; агент по MCP.

**Сделать:**
- У задачи (и опционально у проекта как шаблон) список критериев готовности: текст, обязательный/нет, отмечен/нет, кто отметил.
- Статус `done` нельзя поставить, пока обязательные критерии не отмечены.
- Отметить критерий может исполнитель, автор, владелец проекта, БА-участник; агент по MCP — только если человек не запретил (флаг «закрывает только человек», по умолчанию включён для `done`).
- В карточке и в `get_task` видны: сколько критериев закрыто, какие открыты.
- MCP: чтение критериев; запись отметки — отдельный инструмент или поле `update_task`; перевод в `done` без критериев → ошибка с текстом открытых пунктов.

**Готово, когда:**
- Given у задачи 2 обязательных критерия, 1 открыт When PATCH статус `done` Then 422, задача не в «Готово».
- Given все обязательные отмечены When PATCH `done` Then 200.
- Given агент с обычным `mcp` When отмечает критерий Then аудит с `client_name`; When ставит `done` при флаге «только человек» Then 403.
- Подзадачи: родитель не `done`, пока открыт обязательный критерий родителя (подзадачи не подменяют DoD).

**Вне рамок:** авто-вывод готовности из git/логов; смена колонок доски; принудительные напоминания в UI.

### CD-02 — Карточка и статус из Telegram через агента

**Боль:** живой разговор и статус — в одной командной группе Telegram; созвоны 2 раза в неделю; переписка уже парсится во внешнюю карточку и уходит в Codex. Доска отстаёт. Команду не заставить вести трекер.

**Кто:** ПМ; агент в контуре (Codex/Claude) с токеном проекта.

**Сделать:**
- MCP-инструмент `ingest_message` (имя уточнить в спеке): проект, внешний id (chat+message), текст, опционально `task_id`.
- Если `task_id` нет — создать задачу в указанном проекте (или черновик «входящие») с источником `telegram`, ссылкой на сообщение, телом как описанием.
- Если `task_id` есть — добавить комментарий с тем же источником, без смены статуса.
- Идемпотентность по `(workspace_id, source, external_id)`.
- Права как у `create_task` / `add_comment`; удаление и состав проекта по-прежнему не через MCP.

**Готово, когда:**
- Given одно и то же `external_id` дважды When ingest Then одна задача/один комментарий.
- Given участник проекта When ingest в чужой проект Then 403/404 как у `create_task`.
- Given задача из Telegram When `get_task` Then видны источник и внешняя ссылка.
- Веб-бота Telegram в этом срезе нет: вход — агент, который уже читает группу.

**Вне рамок:** официальный Telegram Bot API внутри api; парсинг всего чата без агента; замена комментариев на чат (T-07).

### CD-03 — «Горит» = блокер/инцидент, не просроченный срок

**Боль:** внутренние дедлайны не главный риск; «горит» — ошибки, uptime, алерт. Сейчас `hot` = приоритет high + срок ≤ сегодня (спека 008 FR-8). Алерт «нет галки» ложно срабатывает.

**Кто:** ПМ перед утром и инцидентом; агент в сводке.

**Сделать:**
- Поле задачи `blocked` (или тип `incident`): причина (текст до N символов), кто поставил, когда.
- «Горит» на сводке и карточке: `blocked` или (прежнее правило 008 — оставить как «срок», подпись не путать).
- На доске метка «Блокер», не красный срок вчера.
- MCP: поставить/снять блокер; `list_project_tasks` фильтр `blocked=true`.
- Снятие блокера не закрывает задачу.

**Готово, когда:**
- Given `medium` без срока и `blocked=true` When сводка Then строка с меткой «Блокер», не «Горит» по правилу срока.
- Given `high`+срок сегодня без блокера When сводка Then прежняя метка срока (008 AC-8 не ломается).
- Given задача `done` When `blocked` Then либо 422, либо блокер снимается автоматически — зафиксировать в спеке.

**Вне рамок:** интеграция с мониторингом/алертами инфраструктуры; корневая причина инцидента.

### CD-04 — Сводка для агента: что застряло без галки команды

**Боль:** «нужен статус» пишут в Telegram, потому что доска врёт. ПМ не хочет ещё один командный экран; хочет нейроинтерфейс. Команда 8–10 не заполняет статусы.

**Кто:** ПМ через агента утром; не новый экран.

**Сделать:** MCP-инструмент (черновик имени `list_stuck_work`):
- задачи моих проектов не в `done`;
- давно без комментария/движения (порог в спеке, старт 48 ч);
- открытый DoD (CD-01) или `blocked` (CD-03);
- просроченный срок — отдельным полем, не единственный сигнал;
- на задачу: последнее событие, исполнитель (имя), проект, открытые критерии.
- Read-only; доступен при `mcp:read`.

**Готово, когда:**
- Given 10 задач, 2 без движения 48 ч, 1 `blocked`, 1 `done` When вызов Then в ответе две застрявших и блокер, `done` нет.
- Given read-only токен When вызов Then 200; When `update_task` Then по-прежнему forbidden.
- Веб-экран не обязателен; «Сводка» 008 не дублировать.

**Вне рамок:** чат-UI в продукте; always-on / `/goal`; письмо на каждое застревание (T-06).

### CD-05 — Агент как коллега

**Боль:** работу уже отдают Codex; в трекере не видно, что сделал ИИ. Спека 022 не написана. Доверие: закрытие и роли — за человеком (уже так в ADR-0018).

**Кто:** команда 8–10; ПМ в ленте.

**Сделать:** написать спеку 022 и срез:
- учётка/флаг `is_agent` или клиент MCP в карточке («ИИ», имя токена/клиента);
- исполнитель может быть агентской учёткой;
- в списке и карточке отличие от человека;
- удаление, роли, состав, `done` при CD-01 — только человек.

**Готово, когда:** спека 022 APPROVED + AC: задача, изменённая MCP, в UI помечена клиентом; человек и агент не путаются в фильтре исполнителя.

**Вне рамок:** свой Devin/харнесс; A2A; ключи `gtk_`.

**Связь:** P1.1 живой ChatGPT OAuth и отзыв `gtrk_` 12.11 — по-прежнему шаг владельца, не эта задача.

### CD-06 — Разметка сущностей из переписки

**Боль:** «хороший продукт определяет отношение сущности компаний за тебя»; сейчас ручные процедуры, агент видит не все ошибки, «всё сломалось». ПМ размечает сам.

**Кто:** ПМ; агент предлагает, человек подтверждает.

**Сделать:**
- MCP-инструмент: на вход текст (кусок TG/транскрипта), на выход черновик: тип (`task` / `incident` / `note`), заголовок, проект-кандидат, связь с существующей задачей (id или нет).
- Ничего не создаётся, пока человек (или явный флаг `commit=true` после превью) не подтвердил.
- Подтверждение создаёт задачу через те же правила, что CD-02, с полем «предложено агентом».

**Готово, когда:**
- Given текст без `commit` When вызов Then черновик, в БД задач 0.
- Given `commit=true` и валидный черновик When вызов Then задача/блокер созданы, аудит клиента.
- Ошибка модели не пишет задачу.

**Вне рамок:** обучение своей модели; граф компаний/CRM; разбор всех исторических чатов.
