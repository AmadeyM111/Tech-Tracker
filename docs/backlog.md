### CD-01 — Критерий готовности (DoD) на задаче

**Боль:** технари не ставят статусы; галка «готово» врёт (задача может быть сделана без неё); нейронки не понимают, закрыта ли работа. Нужен признак завершения, который агент не выдумает.

**Кто:** ПМ/БА на проекте 8–10 человек; исполнитель; агент по MCP.

**Сделать:**
- У задачи (и опционально у проекта как шаблон) список критериев готовности: текст, обязательный/нет, отмечен/нет, кто отметил.
- Статус `done` нельзя поставить, пока обязательные критерии не отмечены.
- Отметить критерий может исполнитель, автор, владелец проекта, БА-участник; агент по MCP — только если человек не запретил (флаг «закрывает только человек», по умолчанию включён для `done`).
- В карточке и в `get_task` видны: сколько критериев закрыто, какие открыты.
- MCP: чтение критериев; запись отметки — отдельный инструмент или поле `update_task`; перевод в `done` без критериев → ошибка с текстом открытых пунктов.

**Готово, когда:**
- Given у задачи 2 обязательных критерия, 1 открыт When PATCH статус `done` Then 422, задача не в «Готово».
- Given все обязательные отмечены When PATCH `done` Then 200.
- Given агент с обычным `mcp` When отмечает критерий Then аудит с `client_name`; When ставит `done` при флаге «только человек» Then 403.
- Подзадачи: родитель не `done`, пока открыт обязательный критерий родителя (подзадачи не подменяют DoD).

**Вне рамок:** авто-вывод готовности из git/логов (это CD-07); смена колонок доски; принудительные напоминания в UI.

### CD-02 — Карточка и статус из Telegram через агента

**Боль:** живой разговор и статус — в одной командной группе Telegram; созвоны 2 раза в неделю; переписка уже парсится во внешнюю карточку и уходит в Codex. Доска отстаёт. Команду не заставить вести трекер.

**Кто:** ПМ; агент в контуре (Codex/Claude) с токеном проекта.

**Сделать:**
- MCP-инструмент `ingest_message` (имя уточнить в спеке): проект, внешний id (chat+message), текст, опционально `task_id`.
- Если `task_id` нет — создать задачу в указанном проекте (или черновик «входящие») с источником `telegram`, ссылкой на сообщение, телом как описанием.
- Если `task_id` есть — добавить комментарий с тем же источником, без смены статуса.
- Идемпотентность по `(workspace_id, source, external_id)`.
- Права как у `create_task` / `add_comment`; удаление и состав проекта по-прежнему не через MCP.

**Готово, когда:**
- Given одно и то же `external_id` дважды When ingest Then одна задача/один комментарий.
- Given участник проекта When ingest в чужой проект Then 403/404 как у `create_task`.
- Given задача из Telegram When `get_task` Then видны источник и внешняя ссылка.
- Веб-бота Telegram в этом срезе нет: вход — агент, который уже читает группу.

**Вне рамок:** официальный Telegram Bot API внутри api; парсинг всего чата без агента; замена комментариев на чат (T-07).

### CD-03 — «Горит» = блокер/инцидент, не просроченный срок

**Боль:** внутренние дедлайны не главный риск; «горит» — ошибки, uptime, алерт. Сейчас `hot` = приоритет high + срок ≤ сегодня (спека 008 FR-8). Алерт «нет галки» ложно срабатывает.

**Кто:** ПМ перед утром и инцидентом; агент в сводке.

**Сделать:**
- Поле задачи `blocked` (или тип `incident`): причина (текст до N символов), кто поставил, когда.
- «Горит» на сводке и карточке: `blocked` или (прежнее правило 008 — оставить как «срок», подпись не путать).
- На доске метка «Блокер», не красный срок вчера.
- MCP: поставить/снять блокер; `list_project_tasks` фильтр `blocked=true`.
- Снятие блокера не закрывает задачу.

**Готово, когда:**
- Given `medium` без срока и `blocked=true` When сводка Then строка с меткой «Блокер», не «Горит» по правилу срока.
- Given `high`+срок сегодня без блокера When сводка Then прежняя метка срока (008 AC-8 не ломается).
- Given задача `done` When `blocked` Then либо 422, либо блокер снимается автоматически — зафиксировать в спеке.

**Вне рамок:** интеграция с мониторингом/алертами инфраструктуры; корневая причина инцидента.

### CD-04 — Сводка для агента: что застряло без галки команды

**Боль:** «нужен статус» пишут в Telegram, потому что доска врёт. ПМ не хочет ещё один командный экран; хочет нейроинтерфейс. Команда 8–10 не заполняет статусы.

**Кто:** ПМ через агента утром; не новый экран.

**Сделать:** MCP-инструмент (черновик имени `list_stuck_work`):
- задачи моих проектов не в `done`;
- давно без комментария/движения (порог в спеке, старт 48 ч);
- открытый DoD (CD-01) или `blocked` (CD-03);
- просроченный срок — отдельным полем, не единственный сигнал;
- на задачу: последнее событие, исполнитель (имя), проект, открытые критерии.
- Read-only; доступен при `mcp:read`.

**Готово, когда:**
- Given 10 задач, 2 без движения 48 ч, 1 `blocked`, 1 `done` When вызов Then в ответе две застрявших и блокер, `done` нет.
- Given read-only токен When вызов Then 200; When `update_task` Then по-прежнему forbidden.
- Веб-экран не обязателен; «Сводка» 008 не дублировать.

**Вне рамок:** чат-UI в продукте; always-on / `/goal`; письмо на каждое застревание (T-06).

### CD-06 — Разметка сущностей из переписки

**Боль:** «хороший продукт определяет отношение сущности компаний за тебя»; сейчас ручные процедуры, агент видит не все ошибки, «всё сломалось». ПМ размечает сам.

**Кто:** ПМ; агент предлагает, человек подтверждает.

**Сделать:**
- MCP-инструмент: на вход текст (кусок TG/транскрипта), на выход черновик: тип (`task` / `incident` / `note`), заголовок, проект-кандидат, связь с существующей задачей (id или нет).

**Готово, когда:**
- Given текст без `commit` When вызов Then черновик, в БД задач 0.
- Given `commit=true` и валидный черновик When вызов Then задача/блокер созданы, аудит клиента.

**Вне рамок:** обучение своей модели; граф компаний/CRM; разбор всех исторических чатов.

### CD-07 — Готово = артефакт, не галка

**Боль:** закрытие задачи = есть результат в системе (прогон данных, PR, отчёт). Галочка человека ничего не значит. CD-01 не пускает `done` без критериев, но не требует внешнего факта — это как раз «вне рамок» CD-01.

**Кто:** аналитик/исполнитель через агента; ПМ на приёмке.

**Сделать:**
- У критерия DoD тип `evidence`: ссылка или id артефакта (PR, отчёт, прогон), текст «что получилось».
- Обязательный `evidence` пуст → `done` 422, как открытый критерий CD-01.
- MCP: приложить evidence (отметить критерий), `done` по-прежнему только человек (`human_close_only`).
- В карточке и `get_task` видно, каких артефактов не хватает.

**Готово, когда:**
- Given обязательный evidence пуст When PATCH `done` Then 422.
- Given URL/id артефакта When агент отмечает критерий Then критерий закрыт, аудит `client_name`; When тот же агент ставит `done` Then 403.
- Given все evidence есть When человек ставит `done` Then 200.

**Вне рамок:** авторазбор GitHub Actions / пайплайна Яндекса; мониторинг инфраструктуры.

### CD-08 — Слои знаний: пространство выше проекта

**Боль:** проектов много, знание похожее. Урок из одного проекта не переносится в новый («как мартышка»). Глобальные факты среды («эти дата-центры лежат, иди в соседние») должны жить выше проекта, иначе умирают вместе с ним.

**Кто:** команда через агента; человек подтверждает запись в верхний слой.

**Сделать:**
- Сущность `knowledge_record`: `scope=space|project`, `project_id` nullable, тип, заголовок, тело, кто подтвердил.
- Проект видит свои записи + слой пространства. Чужой проект слой пространства видит, чужие project-записи — нет.
- MCP: `list_knowledge` / `get_knowledge` с фильтром слоя; агент читает space-слой до работы в проекте.
- Права записи в space — владелец пространства / БА по правилу спеки; агент без `commit` не пишет (CD-09).

**Готово, когда:**
- Given запись `scope=space` When участник второго проекта `list_knowledge` Then запись видна.
- Given запись `scope=project` A When участник только проекта B Then записи нет.
- Given не-участник When list Then 403/404 как у проекта.

**Вне рамок:** полный wiki; векторный поиск; автовытягивание из всех встреч (Viking).

### CD-09 — Запись, на которую можно опереться

**Боль:** синхронизация = знание командное. Настоящий тест — «можно ли опереться без перепроверки»: решения, причины, договорённости, не пересказ разговора. Агент, который пишет в базу как попало, воспроизводит свалку vault.

**Кто:** человек подтверждает; агент предлагает черновик (как CD-06).

**Сделать:**
- Типы записи: `decision` | `reason` | `agreement`. Свободная заметка без типа → 422.
- Обязательные поля: что решили / почему / кто подтвердил (и для agreement — с кем).
- MCP `upsert_knowledge`: без `commit=true` — 0 строк в БД; с commit — запись + аудит.
- Пересказ чата без полей решения — ошибка `knowledge_unstructured`.

**Готово, когда:**
- Given текст-пересказ без типа When upsert Then 422, в БД 0.
- Given `decision`+причина без `commit` When вызов Then черновик, в БД 0.
- Given `commit=true` человеком When вызов Then запись видна команде в слое CD-08.

**Вне рамок:** обучение модели; разбор всей истории чатов; граф компаний.

### CD-10 — Классификатор routine vs research

**Боль:** поток сам делит: рутина, где машине данных хватает, и research, где модель надо вести. Хочет ровно классификатор «данных достаточно — делай без меня». DoD машине не доверяет.

**Кто:** аналитик через агента; человек на research.

**Сделать:**
- У задачи `mode=routine|research` (ставит человек или классификатор).
- MCP `classify_task`: на вход задача/текст, на выход `mode` + каких полей не хватает (источник, полнота, проверка, evidence). Без `commit` ничего не пишет.
- `routine`: агент может исполнять, если DoD и обязательный evidence закрыты (CD-01/07) и есть попадание в слой знаний (CD-08).
- `research`: агент не стартует без DoD (CD-11); ведёт человек по чек-листу.

**Готово, когда:**
- Given «сравни нас с конкурентом» без источников When classify Then `research` + missing, в БД 0.
- Given routine с закрытым DoD и evidence When classify Then `routine`, `can_run_without_human=true`.
- Given research When агент `update_task` в `done` Then по-прежнему 403.

**Вне рамок:** раннер/харнесс агента; автозапуск без человека на research.

### CD-11 — Крупную задачу дробить до проверяемого куска

**Боль:** крупная задача валится не потому что модель глупая, а потому что нет DoD. «Сравни нас с конкурентом» — не задача, пока не задано, откуда данные, что такое полнота и как проверяем. Сверху остаётся приёмка по чек-листу, не переделка за джуном.

**Кто:** человек (приёмка); агент предлагает нарезку через CD-06.

**Сделать:**
- `create_task` / `propose_entities` для `research` без критериев (источник, полнота, проверка) → 422 `dod_required` и шаблон пунктов.
- Нарезка: подзадачи с проверяемым результатом (CD-07); родитель не `done`, пока обязательный DoD родителя открыт (уже CD-01).
- Приёмка родителя — человек, по чек-листу, не «переделай всё».

**Готово, когда:**
- Given research только с заголовком When create Then 422, задачи нет.
- Given три дочерние с закрытым evidence When человек закрывает родителя при открытом его DoD Then 422; When DoD родителя закрыт Then 200.
- Given `propose_entities` без `commit` Then 0 строк (CD-06 не ломается).

**Вне рамок:** автосплит моделью без подтверждения человека.

### Порядок внедрения (после CD-01…06)

1. CD-07 + CD-11 — «готово» и «это вообще задача» без них классификатор врёт.
2. CD-08 + CD-09 — слой правил над проектами; без схемы записи слой станет свалкой.
3. CD-10 — классификатор, когда есть DoD, evidence и знания.
