# ИИ-агенты: подключение к трекеру

Инструкция для технического администратора (ТА), оператора машины агента и самого агента
(spec 007, FR-39). Решение и его обоснование — `docs/adr/0015-agent-access.md`.

Агент (например, Claude Code) работает в трекере под своей **учётной записью агента** и
аутентифицируется **ключом доступа**. Ему доступны 10 операций обычного API (свои проекты и
задачи, создание задач и подзадач, смена статуса, правка полей, комментарии). Claude Code
получает их как 11 инструментов MCP. Инструменты — локальный процесс
`backend/app/agent_mcp.py` на машине агента: он подключается к Claude Code по stdio и ходит в
API трекера по HTTPS с ключом.

> **Ключ — секрет наравне с паролем.** Не вставляйте его в текст запроса к модели (в чат с
> агентом), не коммитьте в репозиторий и не пересылайте в мессенджерах и почте. Ключ задаётся
> только в конфигурации подключения (переменная `GOSTRACKER_API_KEY`). Если ключ мог утечь —
> сразу отзовите его и выпустите новый.

## 1. Технический администратор: учётная запись агента и ключ

### 1.1. Создать учётную запись агента
В интерфейсе: «Учётные записи» → форма «Новая учётная запись» → логин (например,
`agent.claude`) → флажок «Учётная запись ИИ-агента». Поле пароля исчезает, появляется выбор
роли: «Пользователь» (по умолчанию), «Бизнес-админ» или «Без роли». Роль «Тех-админ» агенту
назначить нельзя. Кнопка «Создать» → сообщение «Учётная запись агента создана», окна с паролем
нет. В списке рядом с логином агента — метка «ИИ».

Через API (cookie-сессия ТА, как у интерфейса): `POST /api/v1/admin/agents`, тело
`{"login": "agent.claude", "role": "user"}` (`role`: `user`, `business_admin` или `null` — «без
роли»; поле обязательно) → `201` с учётной записью (`is_agent: true`).

Ошибки: 403 — не ТА; 422 `agent_role_not_allowed` — роль `tech_admin`; 422 `login_taken`,
`login_invalid`, `validation_error` — логин.

Какую роль выбрать:
- **«Пользователь»** — агент ведёт свои задачи: создаёт их себе, меняет статус своих задач и
  задач, где он исполнитель, комментирует. Назначать задачи другим не может. Подходит почти
  всегда.
- **«Бизнес-админ»** — агент может менять любые задачи проектов, где он участник, и назначать
  исполнителем других участников. Управлять проектами и участниками по ключу он всё равно не
  может.

Чего у учётной записи агента нет: пароля и входа в браузер (вход отклоняется как неверный
пароль), сброса пароля («Сбросить пароль» в строке агента нет; API отвечает 422
`agent_password_not_allowed`). Признак «агент» задаётся только при создании и не меняется.

### 1.2. Дать агенту доступ к проекту
Агент видит только проекты, где он участник. Бизнес-администратор добавляет учётную запись
агента в проект на странице участников проекта, как сотрудника. Исключение из проекта сразу
закрывает агенту этот проект. Ограничить отдельный ключ списком проектов нельзя: область
действия задаёт только членство.

### 1.3. Выпустить ключ
В интерфейсе: «Учётные записи» → в строке агента кнопка «Ключи» → раздел «Ключи доступа:
<логин>» → форма «Новый ключ доступа»: «Название ключа» (1–100 символов, например
`claude-laptop` — по названию ключ потом опознаётся), «Срок действия» 30, 90 (по умолчанию),
180 или 365 суток → «Выпустить ключ». Откроется окно «Ключ «…» выпущен» с ключом, кнопкой
«Копировать» и предупреждением. **Ключ показывается один раз:** после «Закрыть» его не увидит
никто — ни ТА, ни оператор. Передайте ключ оператору машины агента защищённым способом
(например, через менеджер паролей) или сразу вставьте в его конфигурацию.

Через API: `POST /api/v1/admin/agents/{user_id}/api-keys`, тело
`{"name": "claude-laptop", "expires_in_days": 90}` (`expires_in_days` — целое число JSON от 1 до
365, по умолчанию 90; строка `"90"` отклоняется) → `201`
`{"key": {…}, "secret": "gtk_<ключ-выдаётся-один-раз>"}`, заголовок `Cache-Control: no-store`.
Тело ответа не сохраняйте в логах и истории.

Ограничения и ошибки выпуска:
- не больше 5 действующих ключей у агента — шестой: 422 `api_key_limit_reached` (отозванные и
  истёкшие не считаются);
- ключ выпускается только учётной записи агента (422 `not_an_agent`) и только
  незаблокированной (422 `user_blocked`);
- название пустое или длиннее 100 символов, срок вне 1…365 — 422 `validation_error`;
- выпускать, смотреть и отзывать ключи может только ТА: остальные получают 403.

Формат ключа: `gtk_` + 43 символа (латинские буквы, цифры, `-`, `_`), всего 47 символов.

### 1.4. Перечень ключей
Раздел «Ключи» показывает по каждому ключу: идентификатор, название, кто и когда выпустил,
срок («Действует до (МСК)»), «Последнее использование (МСК)» или «не использовался», состояние
«действует», «истёк» или «отозван <время>». Секрета и его частей в перечне нет. Через API:
`GET /api/v1/admin/agents/{user_id}/api-keys?page=1&page_size=50`.

### 1.5. Отозвать ключ, ротация, блокировка
- **Отзыв:** «Ключи» → «Отозвать» у действующего ключа → окно «Отозвать ключ?» →
  «Подтвердить». Через API: `POST /api/v1/admin/agents/{user_id}/api-keys/{key_id}/revoke` →
  `204`. Отзыв сразу и необратимо: следующий запрос по ключу получает 401. Повторный отзыв и
  отзыв истёкшего ключа — `204` без изменений.
- **Ротация** (плановая замена или подозрение на утечку): выпустите новый ключ, замените его в
  конфигурации агента, проверьте подключение (раздел 2.5), затем отзовите старый. Продлить срок
  ключа нельзя — только выпустить новый. Следите за сроком: после окончания срока запросы
  получают 401, напоминаний нет.
- **Блокировка** учётной записи агента («Заблокировать») сразу отзывает все её ключи.
  Разблокировка ключи не возвращает — после неё нужно выпустить новый ключ.
- **Смена или снятие роли** действует со следующего запроса; ключи не отзываются. Без роли
  агент получает 403 `no_role` на все операции.

Выпуск и отзыв ключа, создание учётной записи агента пишутся в журнал аудита: «Выпуск ключа
доступа», «Отзыв ключа доступа» (с названием ключа), «Создание учётной записи агента».
Окончание срока и отзыв при блокировке отдельных записей не создают (при блокировке — одна
запись о блокировке).

## 2. Оператор машины агента: подключение Claude Code

### 2.1. Что нужно
- Python 3.12 или новее (`python3 --version`).
- Файл `backend/app/agent_mcp.py` из клона репозитория. Модуль самодостаточен: только
  стандартная библиотека, устанавливать пакеты не нужно.
- Адрес трекера: `https://<сервер>` (или `https://<сервер>:<HTTPS_PORT>`, если порт
  нестандартный, README, «Порты»).
- Ключ агента (раздел 1.3).
- Если у стенда самоподписанный сертификат (по умолчанию) — файл этого сертификата (раздел
  2.3).

### 2.2. Переменные окружения
Инструменты читают конфигурацию только из окружения процесса:

| Переменная | Обязательна | Значение |
|---|---|---|
| `GOSTRACKER_URL` | да | адрес трекера без пути: `https://хост` или `https://хост:порт`. `http://` допускается только для `localhost`, `127.0.0.1` и `[::1]` (разработка) |
| `GOSTRACKER_API_KEY` | да | ключ агента. Пробелы и перевод строки по краям отбрасываются; внутри ключа допустимы только видимые ASCII-символы без пробелов |
| `GOSTRACKER_CA_FILE` | нет | путь к файлу сертификата (PEM), которому доверять при HTTPS; нужен при самоподписанном сертификате |

Поведение при ошибках конфигурации: без ключа (или с ключом недопустимого вида) любой вызов
инструмента сразу возвращает ошибку 401 `not_authenticated` без обращения к сети; неверный
адрес, нечитаемый файл сертификата или пустой `GOSTRACKER_URL` — ошибка `config_error`.
Список инструментов доступен всегда.

Важно: переадресации не выполняются. Адрес `http://<сервер>` поставляемого стека отвечает
переадресацией на HTTPS — инструмент вернёт `redirect_not_allowed`. Указывайте `https://`.
Системные прокси (`HTTPS_PROXY` и т. п.) не используются: запросы идут напрямую на адрес из
`GOSTRACKER_URL`. Таймаут ответа — 30 с.

### 2.3. Сертификат стенда
Самоподписанный сертификат поставки выдан на имя из `TLS_SERVER_NAME` (по умолчанию
`localhost`), а также `localhost` и `127.0.0.1` (README, «Самоподписанный сертификат»).
Адрес в `GOSTRACKER_URL` должен использовать одно из этих имён, иначе проверка сертификата не
пройдёт (ошибка `connection_error`). Получить файл сертификата (на сервере, в каталоге клона):

```bash
docker compose exec -T web cat /run/gostracker-tls/tls.crt > gostracker-ca.crt
```

Ключ `-T` отключает TTY, чтобы в файл не попали лишние символы перевода строки; стек под
другим именем Compose — `docker compose -p <имя> exec -T web …`. Перенесите файл на машину
агента и укажите путь в `GOSTRACKER_CA_FILE`. Если оператор стенда подключил свой сертификат от доверенного центра (каталог `deploy/tls`), `GOSTRACKER_CA_FILE` не
нужен. Отключать проверку сертификата инструменты не умеют.

### 2.4. Подключение
Ключ не должен попасть в репозиторий проекта, в котором работает агент. Два способа:

> Команды и форматы Claude Code в этом разделе и в разделе 2.5 (синтаксис
> `claude mcp add … --env … -- …`, область `local`, подстановка `${GOSTRACKER_API_KEY}` в
> `.mcp.json`, поле `"type": "stdio"`, команда `/mcp`) — внешний инструмент, его поведение
> проверяется при приёмке (`docs/acceptance/mvp-demo.md`, пункт 007/AC-46). При расхождении
> сверяйтесь с `claude mcp add --help` и документацией Claude Code.

**Способ 1 — локальная конфигурация Claude Code** (область по умолчанию `local`: хранится в
пользовательской конфигурации Claude Code в домашнем каталоге, в репозиторий не попадает).
Чтобы ключ не попал в историю оболочки, сначала прочитайте его в переменную без вывода на
экран, затем добавьте сервер:

```bash
# read the key without echo and without shell history
read -rs GOSTRACKER_API_KEY
claude mcp add gostracker \
  --env GOSTRACKER_URL=https://<сервер> \
  --env GOSTRACKER_API_KEY="$GOSTRACKER_API_KEY" \
  --env GOSTRACKER_CA_FILE=<абсолютный путь к gostracker-ca.crt> \
  -- python3 -I <абсолютный путь к клону>/backend/app/agent_mcp.py
unset GOSTRACKER_API_KEY
```

Ключ при этом хранится в конфигурации Claude Code открытым текстом: защитите домашний каталог
и не делитесь этим файлом. Кроме того, пока выполняется `claude mcp add`, ключ виден в
аргументах этого процесса (например, в выводе `ps` другого пользователя той же машины). На
общей машине используйте способ 2. Строку `--env GOSTRACKER_CA_FILE=…` опустите, если сертификат стенда
доверенный.

**Способ 2 — файл `.mcp.json` проекта** (общий для команды, можно коммитить): в нём только
ссылка на переменную окружения, само значение ключа — в окружении процесса `claude`
(например, из менеджера секретов):

```json
{
  "mcpServers": {
    "gostracker": {
      "type": "stdio",
      "command": "python3",
      "args": ["-I", "<абсолютный путь к клону>/backend/app/agent_mcp.py"],
      "env": {
        "GOSTRACKER_URL": "https://<сервер>",
        "GOSTRACKER_API_KEY": "${GOSTRACKER_API_KEY}",
        "GOSTRACKER_CA_FILE": "<абсолютный путь к gostracker-ca.crt>"
      }
    }
  }
}
```

Никогда не записывайте в `.mcp.json` само значение ключа.

**Команда `gostracker-mcp`.** Вместо `python3 -I …/agent_mcp.py` можно указать консольную
команду `gostracker-mcp`, но для неё нужно установить пакет бэкенда со всеми его зависимостями
(`pip install -e backend` в отдельном виртуальном окружении). Для машины агента проще и легче
запуск файла по пути.

### 2.5. Проверка подключения
1. В Claude Code выполните `/mcp`: сервер `gostracker` подключён, у него 11 инструментов.
2. Попросите агента: «вызови инструмент whoami трекера». Ожидается логин учётной записи агента,
   её роль и `is_agent: true`.
3. Без Claude Code (на машине агента, ключ — в переменной окружения, как в способе 1):

```bash
read -rs GOSTRACKER_API_KEY; export GOSTRACKER_API_KEY
export GOSTRACKER_URL=https://<сервер> GOSTRACKER_CA_FILE=<путь к gostracker-ca.crt>
printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"whoami","arguments":{}}}' \
  | python3 -I <путь к клону>/backend/app/agent_mcp.py
unset GOSTRACKER_API_KEY
```

В ответе `"isError": false` и сведения об учётной записи агента. `"isError": true` — смотрите
`code` (раздел 5).

## 3. Инструменты агента

| Инструмент | Что делает | Запрос API | Параметры (обязательные **жирным**) |
|---|---|---|---|
| `whoami` | сведения о своей учётной записи: id, логин, роль, признак «агент» | `GET /api/v1/me` | — |
| `list_projects` | проекты, где агент — участник: id, название, владелец | `GET /api/v1/projects` | `page`, `page_size` |
| `list_my_tasks` | задачи и подзадачи своих проектов, где агент — исполнитель | `GET /api/v1/me/tasks` | `page`, `page_size` |
| `list_project_tasks` | задачи и подзадачи проекта с фильтрами | `GET /api/v1/projects/{project_id}/tasks` | **`project_id`**, `status`, `assignee_id`, `page`, `page_size` |
| `get_task` | карточка: поля, автор, исполнитель, подзадачи и прогресс, родитель, права агента | `GET /api/v1/tasks/{task_id}` | **`task_id`** |
| `create_task` | создать задачу верхнего уровня | `POST /api/v1/projects/{project_id}/tasks` | **`project_id`**, **`title`**, **`description`**, **`due_date`**, `priority`, `assignee_id` |
| `create_subtask` | создать подзадачу (один уровень вложенности) | `POST /api/v1/tasks/{task_id}/subtasks` | **`task_id`** (родитель), **`title`**, `description`, `due_date`, `priority`, `assignee_id` |
| `set_task_status` | сменить статус; закрыть — `done` | `PATCH /api/v1/tasks/{task_id}` (только `status`) | **`task_id`**, **`status`** |
| `update_task` | изменить название, описание, срок, приоритет, исполнителя (статус — только через `set_task_status`) | `PATCH /api/v1/tasks/{task_id}` | **`task_id`**, `title`, `description`, `due_date` (дата или `null`), `priority`, `assignee_id` (UUID или `null`) |
| `list_comments` | комментарии задачи (удалённые — заглушкой) | `GET /api/v1/tasks/{task_id}/comments` | **`task_id`**, `page`, `page_size` |
| `add_comment` | добавить комментарий (результат работы) | `POST /api/v1/tasks/{task_id}/comments` | **`task_id`**, **`body`** |

Идентификаторы (`task_id`, `project_id`, `assignee_id`) — UUID. Успешный результат — тело
ответа API в формате обычного API (`structuredContent` и текстом JSON).

## 4. Правила работы (для агента)

**Статусы:** `todo` — «К выполнению», `in_progress` — «В работе», `review` — «На проверке»,
`done` — «Выполнена». **Закрыть задачу — перевести её в `done`** (`set_task_status`). Отдельного
поля «закрыта» нет. Переходы не ограничены: из любого статуса в любой, включая возврат из
`done`. Закрытие родителя не требует закрытия подзадач. Установка текущего статуса — успешный
ответ без изменений. Задача верхнего уровня после смены статуса оказывается в колонке этого
статуса на доске.

**Срок** — календарная дата `YYYY-MM-DD` без времени. «Сегодня» считается по Europe/Moscow, а не
по часам машины агента: например, в 22:30 UTC 2 ноября в Москве уже 3 ноября, и срок
`2026-11-02` будет в прошлом. Срок раньше «сегодня» — 422 `due_date_in_past`.

**Создание задачи** (`create_task`): обязательны название (1–255 символов), описание (не пустое
после обрезки пробелов, до 10 000 символов) и срок (не раньше «сегодня»). Приоритет `low`,
`medium` или `high`, по умолчанию `medium`. Исполнитель по умолчанию — сам агент; назначить
другого может только агент с ролью «Бизнес-админ», и исполнитель должен быть участником
проекта. Статус новой задачи — `todo`. **Подзадаче** (`create_subtask`) достаточно названия;
подзадача к подзадаче — 422 `subtask_depth_exceeded`.

**Изменение задачи** (`update_task`): меняются только переданные поля, всё или ничего. Передайте
хотя бы одно поле: вызов только с `task_id` ничего не меняет. У задачи верхнего уровня нельзя
снять исполнителя или срок, очистить описание, поставить срок раньше «сегодня»; `null` для срока
и исполнителя допустим только у подзадачи. Сменить исполнителя может только агент с ролью
«Бизнес-админ».

**Права** — как у человека с той же ролью и тем же участием (spec 002): агент-«Пользователь»
меняет статус своей задачи или задачи, где он исполнитель; агент-«Бизнес-админ» — любой задачи
проекта, где он участник. Что разрешено по конкретной задаче, показывает `permissions` в
карточке (`get_task`): `edit`, `change_status`, `change_assignee`, `create_subtask`; `delete` по
ключу всегда `false`.

**Результат работы** оставляйте комментарием (`add_comment`): текст 1–10 000 символов, HTML
вырезается. Отдельного поля «результат» нет.

**Списки** постраничные: `page` с 1, `page_size` от 1 до 100 (по умолчанию 50); в ответе
`items`, `page`, `page_size`, `has_next`.

**Повторы.** Защиты от дублей нет: если создание оборвалось по сети, сначала проверьте список
задач, а потом создавайте заново.

**Лимит:** не больше 120 запросов в минуту на ключ (считаются все запросы по ключу). Сверх
лимита — ошибка 429 с временем повтора.

## 5. Ошибки

При отказе инструмент возвращает результат-ошибку (`"isError": true`) с объектом
`structuredContent.error`: `status` (HTTP-статус или `null` для локальных ошибок), `code`,
`detail` (текст или перечень ошибок полей), `retry_after_seconds` (для 429 и 503). Трассировок
нет; подключение после ошибки не обрывается.

| Статус и код | Причина | Что делать |
|---|---|---|
| 400 `bad_request` | синтаксически неверное тело запроса | исправить запрос |
| 401 `not_authenticated` | ключа нет, он не по формату, неизвестен, отозван или истёк; учётная запись заблокирована. Тело всегда одинаковое | обратиться к ТА за новым ключом |
| 403 `no_role` | у учётной записи агента нет роли | обратиться к ТА |
| 403 `forbidden` | роль или участие не разрешают действие; проект, где агент не участник | не повторять; спросить человека |
| 404 `not_found` | объекта нет, он удалён или в другом рабочем пространстве | проверить идентификатор |
| 422 `validation_error` | поле отсутствует, пустое, неверного формата или вне допустимых значений | исправить параметры по `detail` |
| 422 `due_date_in_past` | срок раньше «сегодня» по Europe/Moscow | указать сегодняшнюю или более позднюю дату |
| 422 `not_project_member` | исполнитель не участник проекта | выбрать участника |
| 422 `recipient_wrong_role` | исполнителю с его ролью задачу назначить нельзя (например, ТА) | выбрать другого участника |
| 422 `subtask_depth_exceeded` | подзадача к подзадаче | создать подзадачу к задаче верхнего уровня |
| 429 `too_many_requests` | превышен лимит 120 запросов в минуту | подождать `retry_after_seconds` (заголовок `Retry-After`) и повторить |
| 503 `service_busy` | сервер занят (блокировка в БД) | подождать `retry_after_seconds` и повторить |
| `invalid_arguments` (`status: null`) | неизвестный параметр, аргументы не объект, `task_id`/`project_id` не UUID | исправить аргументы |
| `config_error` | неверный `GOSTRACKER_URL`, пустой адрес или нечитаемый `GOSTRACKER_CA_FILE` | исправить конфигурацию подключения |
| `connection_error` | трекер недоступен, таймаут, ошибка проверки сертификата | проверить адрес, сеть, имя в сертификате, `GOSTRACKER_CA_FILE` |
| `redirect_not_allowed` | API ответил переадресацией (обычно `http://` вместо `https://` или не тот порт) | указать `https://` и порт HTTPS |
| `invalid_response` | ответ не JSON или больше 8 МиБ | проверить, что адрес ведёт на трекер |
| `http_error` | ответ с ошибкой без кода в теле (например, HTML 502 от прокси) | повторить позже; сообщить оператору |

Вызов неизвестного инструмента — ошибка протокола JSON-RPC `-32602`.

## 6. Чего агент не может

По ключу доступны только 10 операций из раздела 3. Остальное получает 403 `forbidden`, даже если
роль разрешает больше:
- удалять задачи и подзадачи;
- править и удалять комментарии (в том числе свои);
- управлять проектами: создавать, менять, удалять, смотреть карточку проекта и доску;
- смотреть и менять участников, передавать владение; добавить себя в проект;
- переносить карточки по доске (статус меняется через `set_task_status`);
- работать с учётными записями, ролями, ключами, журналом аудита, справочником пользователей;
- входить по паролю, выходить, менять пароль;
- видеть проекты, где агент не участник (403), и объекты другого рабочего пространства (404).

`whoami` возвращает и поле `capabilities` — возможности роли. У агента-«Бизнес-админа» там есть
управление проектами, но по ключу оно закрыто (открытый вопрос владельцу, ADR-0015).
Ориентируйтесь на перечень выше и на `permissions` в карточке задачи.

## 7. Безопасность ключа
- Ключ передаётся только в заголовке `Authorization` по HTTPS; инструменты не отправляют его по
  `http://` (кроме `localhost`), не следуют переадресациям и не используют прокси.
- Ключа нет в описаниях, параметрах и результатах инструментов; в журнал (stderr) инструменты
  пишут только имя инструмента и статус. Сервер трекера хранит только SHA-256 ключа и маскирует
  ключ в своих журналах.
- **Нельзя:** вставлять ключ в текст запроса к модели, в задачи и комментарии трекера; коммитить
  его (в `.mcp.json` — только `${GOSTRACKER_API_KEY}`); пересылать в чатах и почте; передавать в
  адресе запроса (`?key=…`) — так ключ не работает и может попасть в журналы web-сервера.
- Один ключ — одна машина или одно место применения; названия ключей — по месту применения
  (`claude-laptop`, `ci-runner`), чтобы отзывать точечно.
- Срок — не больше нужного: по умолчанию 90 суток.
- После копирования ключа очистите буфер обмена, если включена его история.
- При подозрении на утечку — отзыв (раздел 1.5), затем новый ключ.

## 8. Как увидеть действия агента
- **В интерфейсе** (участники проекта): рядом с логином учётной записи агента — метка «ИИ» в
  карточке задачи (автор — строка «Автор» — и исполнитель), в комментариях, на доске и в списках
  задач.
  Задачи агента видны в общих доске и списках проекта.
- **ТА:** «Учётные записи» — метка «ИИ», перечень ключей с временем последнего использования;
  «Журнал аудита» — создание учётной записи агента, выпуск и отзыв ключей. Задачи и комментарии
  ТА не видит (002).
- **Хранилище событий** (оператор БД): каждое создание и изменение задачи, создание и прямое
  удаление комментария пишется в `domain_event`; у действий по ключу заполнен `api_key_id`. Ленты
  активности в интерфейсе и API нет. Запрос оператора (в каталоге клона на сервере) — последние
  50 действий, выполненных **по ключу** (с названием ключа); действия людей
  (`api_key_id IS NULL`) он не показывает:

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT d.occurred_at, u.login_display, k.name AS api_key, d.action, d.entity_id, d.changed_fields
FROM domain_event d
JOIN app_user u ON u.id = d.actor_id
JOIN api_key k ON k.id = d.api_key_id
ORDER BY d.id DESC
LIMIT 50;
SQL
```
