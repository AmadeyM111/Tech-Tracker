# ТЗ: Open Source трекер команды (пилот)

Версия 1.0 от 2026-10-13. Кладётся в `docs/brief/vision.md` и далее не редактируется.
Все уточнения — в `specs/*/spec.md`, изменения решений — через новый файл в `docs/adr/`.

---

## 1. Задача

Создать open source трекер для работы команды внутри крупной компании: проекты и задачи
сотрудников, воронка продаж и база клиентов в одной системе, со сквозной связью
«клиент → сделка → проект → задача».

**Сейчас делаем:** localhost-пилот для команды 10–12 человек.
**Закладываем на будущее:** мультикомандность (`workspace_id` у каждой сущности),
внешний провайдер аутентификации за интерфейсом. В пилоте это не реализуется.

## 2. Объём пилота (R1)

### Входит
- **Проекты:** название, описание, участники, владелец.
- **Задачи:** название, описание, исполнитель, срок, приоритет, статус, метки.
  Подзадачи на один уровень вложенности. Комментарии. Вложения (файлы).
- **Представления:** список с фильтрами (по исполнителю, статусу, сроку, проекту)
  и канбан-доска с перетаскиванием между колонками.
- **CRM** (отдельный раздел интерфейса того же приложения): клиенты, контакты,
  сделки (сумма, валюта, стадия, ответственный), воронка с настраиваемыми стадиями,
  связь сделки с проектом, история изменений сделки.
- **Пользователи:** учётные записи создаёт технический администратор. 4 роли (раздел 4).
- **Общее:** лента активности по проекту и по сделке, базовый поиск по названиям,
  экспорт и импорт данных в JSON.

### Следующий релиз (R2), не делать сейчас
Учёт потраченного времени, повторяющиеся задачи, обращения клиентов через веб-форму
и email, базовые отчёты и дашборды.

### Вне рамок
Диаграмма Ганта, зависимости задач, маршруты согласования, каналы Telegram, VK и
телефония, SSO, цели команды (OKR), мобильное приложение, встроенный мессенджер.

Обоснование по каналам: Telegram, VK и телефония требуют внешнего адреса или интеграции
с АТС, что несовместимо с localhost-пилотом.

## 3. Принятые решения

Менять только через новый ADR.

| Тема | Решение | Почему |
|---|---|---|
| Аутентификация | Локальные учётные записи, создаёт техадминистратор. Пароль хранится как Argon2id. Вход по логину и паролю | SSO удлиняет пилот и требует корпоративного IdP, которого на localhost нет |
| Готовность к SSO | Проверка учётных данных вынесена за интерфейс провайдера; добавление OIDC не затрагивает остальной код | Переход в корпоративный контур без переписывания |
| Рабочие пространства | В пилоте одно, но `workspace_id` есть у каждой сущности и участвует в каждом запросе | Позже не переделывать модель и запросы |
| Вложения | Файловая система (том Docker), в БД только метаданные. Лимит 10 МБ на файл | Иначе бэкап и восстановление становятся неподъёмными |
| Обновление данных | Опрос раз в 15 секунд. WebSocket вне пилота | Простота; для 12 человек достаточно |
| Время | В БД и API только UTC, ISO 8601. Отображение — Europe/Moscow | Избегаем класса ошибок с часовыми поясами |
| Деньги | Целое число копеек + код валюты. В пилоте только RUB | Никаких float в деньгах |
| Удаление | Мягкое (`deleted_at`) для задач, проектов, сделок | Восстановление без бэкапа |
| Лицензия | Apache License 2.0 | Разрешает коммерческое использование, закрывает патентные риски, принимается корпорациями |
| Данные в пилоте | Только синтетические клиенты и сотрудники; реальные ПДн не загружаются | Снимает требования 152-ФЗ на время пилота |

## 4. Роли и права

Роль назначается в рамках рабочего пространства.

| Действие | Техадмин | Бизнес-админ | Смешанная | Пользователь |
|---|---|---|---|---|
| Системные настройки | да | нет | да | нет |
| Создание и блокировка учётных записей | да | нет | да | нет |
| Назначение роли бизнес-администратора | да | нет | да | нет |
| Просмотр журнала аудита | да | нет | да | нет |
| Создание проекта | нет | да | да | нет |
| Добавление участников в проект | нет | да | да | нет |
| Удаление проекта | нет | только свой | да | нет |
| Создание задачи себе | нет | да | да | да |
| Создание задачи другому | нет | да | да | **нет** |
| Изменение своей задачи | нет | да | да | да |
| Изменение чужой задачи в своём проекте | нет | да | да | нет |
| Чтение задач проектов, где участвует | нет | да | да | да |
| Чтение задач чужих проектов | нет | нет | нет | нет |
| CRM: чтение | **нет** | да | да | **нет** |
| CRM: создание и изменение | нет | да | да | нет |

Технический администратор не имеет доступа к бизнес-данным: это разделение обязанностей,
обязательное для корпоративного внедрения. Все проверки прав выполняются на бэкенде:
скрытой кнопки на фронтенде недостаточно.

## 5. Нефункциональные требования

**Нагрузка:** 12 пользователей, до 5 одновременно активных. Объём для проверки
нормативов: 50 000 задач, 10 000 сделок, 5 000 клиентов.

**Время отклика.** Измеряется на стенде 3 vCPU / 6 ГБ RAM, на указанном объёме данных,
показатель p95, кэш прогрет, 50 элементов на странице.

| Операция | Норматив (p95) | Недопустимо |
|---|---|---|
| Открытие списка задач | 300 мс | больше 1 с |
| Открытие карточки задачи или сделки | 200 мс | больше 500 мс |
| Сохранение изменений | 300 мс | больше 1 с |
| Поиск и фильтрация | 500 мс | больше 2 с |
| Агрегация для ленты активности | 2 с | больше 5 с |

**Окружение:** Linux-сервер или рабочая машина разработчика, 3 vCPU, 6 ГБ RAM, 90 ГБ диска.
Развёртывание через `docker compose up`, без доступа в интернет после сборки образов.

**Браузеры:** Chromium актуальной версии и SberBrowser (на движке Chromium).
Проверка автотестами ведётся в Chromium.

**Интерфейс:** русский язык. Строки интерфейса вынесены в словарь, чтобы позже добавить
второй язык. Работа с клавиатуры в основных сценариях, контраст по WCAG AA.

**Эксплуатация:** ротация логов, резервная копия БД и вложений одной командой,
восстановление из копии проверяется в приёмке.

## 6. Критерии приёмки пилота

Каждый пункт покрывается автотестом на уровне API; пункты 1, 5 и 12 проверяются вручную.

1. **Развёртывание.** На чистой машине: `git clone`, `cp .env.example .env`,
   `docker compose up` → вход в систему с демо-данными не дольше 10 минут,
   без ручной правки кода.
2. **Учётные записи.** Техадминистратор создаёт 12 пользователей, назначает роли;
   пользователи входят по логину и паролю.
3. **Проект и задачи.** Бизнес-администратор создаёт проект, добавляет 3 участников,
   ставит 5 задач со сроками и исполнителями. Участники видят свои задачи в личном списке.
4. **Подзадачи.** Задача делится на 3 подзадачи; прогресс родительской задачи отражает
   долю закрытых подзадач.
5. **Доска.** Задача перетаскивается между колонками; изменённый статус виден другому
   пользователю после обновления страницы.
6. **Права пользователя.** Бизнес-пользователь не может создать задачу другому:
   API возвращает 403.
7. **Изоляция CRM.** Бизнес-пользователь и техадминистратор не читают сделки:
   API возвращает 403, в том числе при прямом запросе по идентификатору.
8. **Сделка.** Менеджер заводит клиента, контакт и сделку на 500 000 ₽, переносит её
   по трём стадиям. История показывает, кто и когда перенёс.
9. **Связь.** Сделка связана с проектом: со страницы сделки видны задачи проекта,
   со страницы проекта — связанная сделка.
10. **Производительность.** На объёме из раздела 5 нормативы отклика выполняются.
11. **Экспорт.** Данные выгружаются в JSON и загружаются обратно без потерь.
12. **Восстановление.** Резервная копия снимается и разворачивается на чистом стенде,
    данные совпадают.

## 7. Технологии и результат

**Стек:** Python 3.12 + FastAPI + SQLAlchemy 2.x + Alembic + PostgreSQL 16;
React 18 + TypeScript + Vite + TanStack Query; Docker Compose.

**Что сдаётся:**
- репозиторий с открытой лицензией Apache 2.0;
- `docker compose up` поднимает систему целиком;
- демо-данные одной командой (12 пользователей, 2 проекта, 30 задач, 10 сделок);
- README на русском и английском с инструкцией развёртывания;
- автотесты на критерии приёмки и CI, прогоняющий линтер, типы и тесты;
- `docs/`: решения (ADR), модель данных, описание API (OpenAPI генерируется автоматически).

## 8. Материалы на входе

**CRM клуба единоборств** — `github.com/AmadeyM111/CRM_for_Martial_Arts_Academy`.
Десктопное приложение на Tkinter (Python, SQLAlchemy, SQLite/PostgreSQL, MIT, тестов нет;
проверено 13.10.2026). Берём только идеи модели данных: клиенты, контакты, история.
Код интерфейса не переносится, веб-слой пишется заново.

**Аналоги, что берём:**
- **Kaiten** — канбан-доски, пространства под проекты, низкий порог входа,
  минималистичный интерфейс. Это образец для нашего UX.
- **Битрикс24** — полноценная сущность сделки вместо карточки на доске.
  Не берём перегруженность функциями.
- **Pyrus** — маршруты согласования. Не берём в пилот.

**OSS-материалы (только как референс, код не переиспользуется):**
- **TaskNotes** (MIT, плагин для Obsidian, TypeScript) — удачные представления задач:
  список, канбан, календарь; повторяющиеся задачи. Берём идеи для R2.
- **TaskBoard** (MIT, PHP + Angular, **не поддерживается с 2020 года**) — простая модель
  доски и три роли. Использовать только как иллюстрацию, код устарел.

## 9. Как ведётся работа

Разработка идёт по SDD-циклу: spec → plan → tasks → (тесты → код → ревью) → приёмка,
командой `/sdd`. Источник истины для реализации — `specs/<папка>/spec.md`, настоящий
документ — вход для спецификаций. Правила кода и команды — в `AGENTS.md`.

Порядок работ:
1. **R1.0 Фундамент:** БД, миграции, аутентификация, пользователи и роли, CI, развёртывание.
2. **R1.1 Проекты и задачи:** модель, API, список и карточка.
3. **R1.2 Доска:** колонки, перетаскивание, фильтры.
4. **R1.3 CRM:** клиенты, контакты, сделки, воронка, связь с проектом.
5. **R1.4 Приёмка:** демо-данные, экспорт, резервная копия, проверка нормативов.
