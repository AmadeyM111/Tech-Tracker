# ADR-0020. Доступ ИИ-агентов: учётная запись агента, ключи доступа, инструменты MCP

> Номер изменён с 0015 на 0020: на main уже два файла `0015-*`. Содержание не менялось.

- **Дата:** 2026-10-31
- **Статус:** принято (решения владельца по `specs/007-ai-agent-tools/spec.md` v0.4: Q-1…Q-13,
  2026-10-30)
- **Дополняет:** ADR-0004 (новый способ аутентификации — ключ доступа; пароли и сессии людей не
  меняются)
- **Уточняет:** ADR-0006 (три новых действия журнала аудита), ADR-0012 (запись событий задач и
  комментариев; лента активности по-прежнему отложена)
- **Связано:** `specs/007-ai-agent-tools/spec.md` (FR-1…FR-42, NFR-1…NFR-7, раздел 6);
  `specs/007-ai-agent-tools/plan.md` (PD-1…PD-5, PD-11…PD-15, §4.2, §4.7, §4.9);

## Контекст
До 007 трекером пользовались только люди через браузер: аутентификация — только по
cookie-сессии (ADR-0004), программного доступа без пароля нет. Владелец хочет, чтобы ИИ-агент
(проверяется на Claude Code) вёл в трекере свою работу: заводил задачи, менял статусы, закрывал
их и оставлял результат комментарием. Требования: доступ без браузера, пароля и cookie;
учётные данные агента отзываются в любой момент; действия агента видны как действия агента;
права не шире роли (002); правила обязательных полей (006) действуют и для агента; существующие
интерфейс и API не ломаются (NFR-1). Claude Code подключает внешние инструменты по протоколу
MCP, поэтому протокол — часть контракта (spec 007, раздел 3.7).

## Решение

### Учётная запись агента
- Агент работает под **обычной учётной записью рабочего пространства с признаком «агент»**
  (`app_user.is_agent`). Отдельной роли нет: права — роль 002 «Пользователь» или
  «Бизнес-админ» либо «без роли». Роль ТА агенту назначить нельзя ни при создании, ни сменой
  роли: 422 `agent_role_not_allowed`, без записи в журнал (FR-2).
- Создаёт её только ТА: `POST /api/v1/admin/agents` с телом `{login, role}` или флажок «Учётная
  запись ИИ-агента» в «Учётных записях». Признак задаётся только при создании и не меняется.
  В журнал аудита — одна запись `user.agent_created`.
- Пароля у агента нет по смыслу: в `password_hash` хранится Argon2-хеш случайного значения,
  которое сразу выбрасывается. Вход по логину и паролю отклоняется тем же ответом, что неверный
  пароль (401 `invalid_credentials`). Сброс пароля агенту — 422 `agent_password_not_allowed`.
- Во всём остальном это обычный пользователь: участник проектов (добавляет БА), исполнитель,
  автор задач и комментариев, виден в справочнике и в «Учётных записях».

### Ключ доступа
- **Формат:** `gtk_` + base64url от 32 случайных байт из `secrets` без `=` (43 символа, всего
  47; 256 бит случайности, NFR-3).
- **Хранение:** в таблице `api_key` только **SHA-256 секрета** (`secret_digest`, 32 байта,
  `UNIQUE`). Префикса, «последних символов» и любой части секрета нет ни в БД, ни в перечне, ни
  в журнале. Ключ опознаётся по идентификатору (UUID) и названию.
- **Секрет показывается один раз** — в ответе на выпуск (`201`, заголовок
  `Cache-Control: no-store`). Повторно получить его нельзя никому: ни ТА, ни оператору. В
  интерфейсе секрет живёт только в состоянии окна и исчезает при его закрытии.
- **Выпуск, перечень, отзыв — только ТА** (`/api/v1/admin/agents/{user_id}/api-keys`, `…/revoke`;
  кнопка «Ключи» в строке агента). Выпуск и отзыв — по одной записи журнала аудита
  (`user.api_key_issued`, `user.api_key_revoked`) с идентификатором и названием ключа, без
  секрета. Повторный отзыв и отзыв истёкшего ключа — 204 без записи (D-5).
- **Срок действия** обязателен: по умолчанию 90 суток, от 1 до 365 суток (`expires_in_days`,
  целое число). Бессрочных ключей и продления нет: выпускается новый ключ. Окончание срока
  записей в журнал не создаёт.
- **Не больше 5 действующих ключей** на учётную запись агента; шестой — 422
  `api_key_limit_reached`. Ключ выпускается только агенту (422 `not_an_agent`) и только
  незаблокированному (422 `user_blocked`).
- **Блокировка агента отзывает все его ключи** в той же транзакции (одна запись
  `user.blocked`, отдельных записей об отзыве нет). Разблокировка ключи не восстанавливает.

### Аутентификация по ключу
- Ключ передаётся только в заголовке `Authorization: Bearer <ключ>`. Наличие **любого**
  заголовка `Authorization` делает запрос запросом по ключу: cookie не читается. Другая схема,
  пустое значение, два заголовка — «ключ не по формату» (401). Ключ в пути или параметрах
  адреса не аутентифицирует.
- Любой отказ — один и тот же 401 `{"detail": "Требуется вход в систему", "code":
  "not_authenticated"}`: ключ пустой, не по формату, неизвестен, отозван, истёк; учётная запись
  заблокирована или не состоит в пространстве. По ответу причину не определить (FR-13).
- Роль, блокировка и членство читаются из БД на каждый запрос; без роли — 403 `no_role`.
  Запрос по ключу не создаёт, не продлевает и не завершает cookie-сессии и не ставит cookie.
  Перебор паролей агента ключ не блокирует (ключ не зависит от счётчика неудачных входов).
- Субъект запроса — учётная запись агента; у запроса запоминается идентификатор ключа.

### Объём доступа: 10 операций
По ключу доступны ровно 10 маршрутов обычного API (перечень `AGENT_OPERATIONS` по имени
маршрута в `backend/app/api/deps.py`): «кто я» (`GET /api/v1/me`), проекты агента
(`GET /api/v1/projects`, только где агент — участник, даже у агента-БА), «мои задачи»
(`GET /api/v1/me/tasks`), задачи проекта (`GET /api/v1/projects/{id}/tasks`), карточка задачи
(`GET /api/v1/tasks/{id}`), создание задачи (`POST /api/v1/projects/{id}/tasks`), создание
подзадачи (`POST /api/v1/tasks/{id}/subtasks`), изменение задачи и смена статуса
(`PATCH /api/v1/tasks/{id}`), чтение и добавление комментариев
(`GET`/`POST /api/v1/tasks/{id}/comments`). Форматы ответов и ошибок — как в обычном API.
Любой другой маршрут с заголовком `Authorization` получает 403 `forbidden` до обработчика (ключ
при этом не проверяется). Вторая линия защиты — `backend/app/domain/access/policy.py`: по ключу
нельзя удалить задачу, править и удалять комментарии; в карточке задачи по ключу
`permissions.delete = false`, у комментариев `edit` и `delete` — `false`.

### Лимит частоты
Не больше **120 запросов в минуту на ключ** (фиксированное окно 60 с). Счётчик и время
последнего использования хранятся в строке `api_key` и обновляются одним атомарным
`UPDATE … RETURNING` с немедленной фиксацией: лимит верен при любом числе процессов `api` и
переживает отказ запроса. Запрос сверх лимита — 429 `too_many_requests` с заголовком
`Retry-After` (секунды до конца окна, не меньше 1); данные не меняются. Лимит одного ключа не
влияет на другие ключи и на сессии людей. Время последнего использования обновляется только у
запросов в пределах лимита.

### Следы действий агента
- Автор задач, подзадач и комментариев агента — его учётная запись; в API в каждой ссылке на
  пользователя есть `is_agent`, интерфейс показывает рядом с логином агента метку «ИИ»
  (карточка задачи — автор и исполнитель, комментарии, доска, списки задач, «Учётные записи»).
- События задач и комментариев (`task.created`, `task.updated`, `comment.created`,
  `comment.deleted`) с 007 пишутся для всех авторов (FR-42). У событий по ключу заполнен
  `domain_event.api_key_id`, у действий людей — `NULL`. Событий в журнале аудита, интерфейсе и
  API нет: лента активности отложена (001/FR-38).

### Инструменты MCP
- Свой минимальный сервер MCP в одном модуле `backend/app/agent_mcp.py`, **только стандартная
  библиотека Python** (проверяется AST-тестом), без импортов кода трекера. Транспорт — stdio
  (JSON-RPC 2.0, одно сообщение — одна строка UTF-8), методы `initialize`, `ping`,
  `tools/list`, `tools/call`; версии протокола `2025-06-18`, `2025-03-26`, `2024-11-05`.
  Процесс работает на машине агента и обращается к API трекера по ключу; точки MCP в сервере
  трекера нет (Q-9).
- Запуск: `python3 -I <клон>/backend/app/agent_mcp.py` (установка пакета не нужна) или
  консольная команда `gostracker-mcp` после установки пакета `backend`.
- **Ровно 11 инструментов**, по одному на действие FR-18…FR-27: `whoami`, `list_projects`,
  `list_my_tasks`, `list_project_tasks`, `get_task`, `create_task`, `create_subtask`,
  `set_task_status`, `update_task`, `list_comments`, `add_comment`.
- Конфигурация — только из окружения процесса: `GOSTRACKER_URL`, `GOSTRACKER_API_KEY`,
  необязательный `GOSTRACKER_CA_FILE`. Ключа нет ни в описаниях, ни в параметрах, ни в
  результатах инструментов (FR-38).
- Транспорт: адрес — только origin `https://хост[:порт]`; `http://` — только для `localhost`,
  `127.0.0.1`, `[::1]`. Переадресации не выполняются (ошибка `redirect_not_allowed`), системные
  прокси не используются, таймаут 30 с. В stderr пишутся только имя инструмента и HTTP-статус
  или код ошибки.

## Безопасность (сводка)
| Мера | Как сделано |
|---|---|
| Секрет не восстанавливается из БД | хранится только SHA-256; 256 бит случайности делают перебор прообраза невозможным и без «соли» и секрета сервера |
| Секрет виден один раз | ответ на выпуск с `Cache-Control: no-store`; интерфейс держит секрет только в окне, без кэша запросов |
| Ограниченный объём доступа | 10 операций (FR-17); вне перечня — 403 `forbidden`; права — не шире роли (002) |
| Ограниченный срок | 90 суток по умолчанию, максимум 365; продления нет |
| Отзыв | ТА в любой момент; блокировка агента отзывает все его ключи сразу |
| Лимит | 120 запросов в минуту на ключ, 429 с `Retry-After`; не больше 5 действующих ключей |
| Единый отказ | 401 `not_authenticated` с одинаковым телом при любой причине |
| Маскирование в логах приложения | `redact_text` (`backend/app/core/logging.py`) заменяет на `***` любое вхождение `gtk_` + не меньше 8 символов до пробельного символа или разделителя контекста (`API_KEY_LEAK_PATTERN`, plan §4.2) — в сообщениях, трассировках, пути access-лога, именах и значениях полей; заголовок `Authorization` маскируется по имени (001/FR-57) |
| Журнал web (nginx) | сервер 443 пишет формат `gt_access` (`deploy/web/default.conf.template`): метод, `$uri` без строки запроса, статус; вместо `$remote_user` — литерал `-` (nginx заполняет его из `Authorization: Basic`) |
| Транспорт | ключ уходит только по HTTPS (кроме loopback), без переадресаций и прокси |
| Без внешних вызовов | трекер и инструменты не делают внешних вызовов и не шлют телеметрию (NFR-6) |

## Причины
- Решения владельца Q-1…Q-10 (2026-10-30): агент — учётная запись с признаком, ключи выпускает
  только ТА, интерфейс в «Учётных записях», по ключу — только FR-18…FR-27, метка «ИИ», срок
  90/365, лимиты 120 в минуту и 5 ключей, идентификатор ключа в событиях, транспорт stdio,
  область ключа — членство в проектах.
- Обычная учётная запись даёт агенту все правила 001/002/006 без второй матрицы прав;
  существующие маршруты дают тот же формат ответов и ошибок (FR-28) без дублирования.
- SHA-256 достаточно для 256-битного случайного секрета и не добавляет к запросу заметного
  времени (NFR-2: замер AC-48 — разница p95 ключа и сессии в пределах ±1,05 мс при пороге 20 мс).
- Счётчик лимита в БД — тот же приём, что `last_activity_at` у сессий; верен при нескольких
  процессах `api`.
- Свой сервер MCP на стандартной библиотеке не добавляет зависимостей (allowlist не меняется) и
  не требует ставить бэкенд на машину агента; нужные 4 метода протокола — небольшой модуль.

## Альтернативы и почему отвергнуты
- **Отдельная роль «Агент» в матрице 002.** Вторая матрица прав и правки всех гейтов; права
  агента разошлись бы с правами человека той же роли. Владелец выбрал учётную запись с
  признаком (Q-1).
- **Вход агента по паролю и cookie-сессия.** Пароль пришлось бы хранить у агента, сессии
  истекают по простою, проверка Origin и cookie рассчитаны на браузер; отзыв — только через
  блокировку. Отвергнуто владельцем (Q-1).
- **Ключи у людей (личные токены) и вход людей по ключу.** Расширяет поверхность атаки на
  учётные записи людей и ТА; вне рамок (spec 007, раздел 6).
- **Точка MCP по HTTP в составе сервера трекера.** Новая открытая поверхность, сессии и
  потоковые ответы в сервере, требования облачных клиентов к OAuth. Владелец выбрал локальный
  процесс по stdio (Q-9).
- **OAuth, mTLS, внешний провайдер.** Несоразмерно пилоту в одной установке без внешних
  сервисов (NFR-6); вне рамок.
- **Бессрочные ключи.** Утёкший и забытый ключ действовал бы вечно. Отвергнуто владельцем
  (Q-6): срок обязателен, максимум 365 суток.
- **Хранить префикс или «последние символы» секрета для опознания; id ключа внутри секрета.**
  Кладёт в БД подстроку секрета длиной 8 и больше (нарушение FR-6, AC-39). Ключ опознаётся по
  идентификатору и названию.
- **HMAC с `SECRET_KEY`, как у сессий.** Смена `SECRET_KEY` молча отозвала бы все ключи; при 256
  битах случайности секрет сервера не нужен.
- **Argon2 для ключей.** Сотни миллисекунд на каждый запрос (NFR-2); медленный хеш нужен
  только для низкоэнтропийных паролей.
- **Свой заголовок `X-API-Key`.** Нестандартно; `Authorization` уже маскируется логгером.
- **Лимит в памяти процесса или в Redis.** Память процесса умножает лимит при нескольких
  процессах и сбрасывает его при перезапуске; Redis — новый сервис и зависимость.
- **Отдельные маршруты `/api/v1/agent/*`.** Дублируют 10 обработчиков и схем; FR-28 требует
  формат обычного API.
- **Официальный пакет `mcp` или сервер на Node.** Около 10 транзитивных пакетов и проверка
  лицензий либо второй рантайм на машине агента (D-7, plan PD-12).
- **10 инструментов (один `update_task` со статусом).** FR-27 называет две операции с
  комментариями, а отдельный `set_task_status` однозначно описывает закрытие как `done` (AC-42).

## Последствия
- **Дополнение ADR-0004.** Появился второй способ аутентификации — ключ в `Authorization:
  Bearer`. Пароли, сессии, проверка Origin для cookie-сессий не меняются (AC-47).
- **Basic-аутентификация прокси перед API не поддерживается.** Любой заголовок `Authorization`
  считается ключом: со схемой `Basic` маршруты агента отвечают 401, остальные — 403. Ставить
  перед поставляемым стеком прокси с Basic-аутентификацией нельзя — перестанет работать и
  интерфейс.
- **`http://` для инструментов — только loopback.** Поставляемый nginx переадресует 80 → 443;
  переадресации инструмент не выполняет, поэтому адрес — всегда `https://` (кроме локальной
  разработки на `localhost`). При самоподписанном сертификате нужен `GOSTRACKER_CA_FILE`.
- **Контракт API — только добавления (NFR-1):** поле `is_agent` в ссылках на пользователя,
  `MeResponse`, `AdminUser`; маршруты `/api/v1/admin/agents*`; коды `agent_role_not_allowed`,
  `agent_password_not_allowed`, `not_an_agent`, `api_key_limit_reached`; 429
  `too_many_requests`. Описание API пересобрано (`docs/api/openapi.json`).
- **Журнал аудита:** три новых действия — «Создание учётной записи агента», «Выпуск ключа
  доступа», «Отзыв ключа доступа» (с названием ключа).
- **Рост `domain_event` без очистки.** С 007 каждая успешная правка задачи и каждое создание или
  прямое удаление комментария — людьми и агентами — добавляет строку в `domain_event`. Таблица
  только дописывается (триггеры запрещают `UPDATE`, `DELETE`, `TRUNCATE`), `gostracker
  maintenance` её не чистит, механизма очистки нет. Рост линейный от числа правок; оператору —
  следить за размером БД (запрос — в «Порядке обновления», команда 3). Политика хранения —
  вопрос следующей версии.
- **Откат миграции 0008 теряет данные:** таблицу `api_key` (все ключи), признак `is_agent` и
  `domain_event.api_key_id`. Учётные записи агентов после отката становятся обычными учётными
  записями без известного пароля; после повторного обновления признак «агент» у них не
  восстанавливается (`DEFAULT false`), а задать его можно только при создании. События задач и
  комментариев остаются.
- **Повтор без защиты от дублей.** Ключей идемпотентности нет (раздел 6 spec): повтор создания
  после обрыва связи может создать дубль.
- **Модель данных:** `docs/data-model.md` описывает `app_user.is_agent`, `api_key`,
  `domain_event.api_key_id` и запись событий FR-42. Синхронизация spec 001 (FR-4, FR-41, FR-57,
  модель данных) — отдельной задачей R7-T25.

## Остаточные риски (приняты, решение владельца — на финальной приёмке R7-T26)
- **Маскирование в логах приложения обрывается на разделителе.** Маска закрывает ключ от `gtk_`
  до первого пробельного символа Юникода или разделителя контекста: `"`, `'`, `` ` ``, `<`,
  `>`, `&`, `;`, `,`, `(`, `)`, `[`, `]`, `{`, `}`, `|`. Если ключ испорчен таким символом на
  позициях 4–38, открытой может остаться голова (до 11 символов вместе с `gtk_`) или хвост без
  префикса. Порча самого префикса (`GTK_`, `gtx_`) не опознаётся. Принято в plan §4.2
  (open-items п. 15).
- **Журнал web (nginx):** (a) `$uri` в формате `gt_access` пишется без маскирования — ключ,
  ошибочно подставленный клиентом в путь, попадёт в access-лог web; (b) сервер 80
  (переадресация) пишет журнал в стандартном формате со строкой запроса (`$request`) — ключ в
  `?…` по `http://` попадёт в журнал; (c) `error_log` nginx при ошибках апстрима (502, 504) пишет
  строку запроса целиком, формат журнала на него не действует. Настоящий клиент (`agent_mcp.py`)
  передаёт ключ только в заголовке и не ходит по `http://` вне loopback, поэтому риск — только
  при ошибке стороннего клиента. Также `$uri` берётся после внутреннего перенаправления:
  маршруты интерфейса пишутся как `/index.html` (наблюдаемость, не безопасность).
- **Секрет вне трекера.** После «Копировать» ключ лежит в буфере обмена (и в истории буфера,
  если она включена); если ключ задан значением в конфигурации подключения Claude Code, он
  хранится там открытым текстом. Это зона ответственности оператора машины агента
  (`docs/agents.md`, «Безопасность ключа»).
- **Лимит считается раньше проверки учётной записи.** Неотозванный ключ учётной записи вне
  пространства получает 401 на первые 120 запросов в минуту и 429 на следующие; время
  последнего использования обновляется и у таких отказов (через API недостижимо: блокировка
  отзывает ключи; open-items п. 2).
- **Часы назад в окне лимита.** Если часы сервера отведены назад внутри окна, окно не
  сбрасывается и `Retry-After` может превысить 60 с (лишний отказ, обхода лимита нет;
  open-items п. 1).

## Порядок обновления (миграция 0008)
Миграция `backend/migrations/versions/0008_agent_api_keys.py` только добавляет: столбец
`app_user.is_agent` (`DEFAULT false`), таблицу `api_key`, столбец `domain_event.api_key_id`
(без значения по умолчанию, строки журнала не переписываются, триггеры неизменяемости не
мешают). Существующие данные не меняются, записей в журнал миграция не пишет. Порядок
обеспечивает `backend/docker-entrypoint.sh`, как в ADR-0013: `gostracker bootstrap` (миграции
до `head`), затем `exec uvicorn`; если миграция падает, API не стартует, транзакция
откатывается целиком, повторный запуск безопасен.

Правила — те же, что в ADR-0013, раздел «Порядок обновления»: обновлять рабочий стек только
командой `dc up -d --build --wait` одним выпуском; стек с занятым портом 80 — только API
(`dc up -d --build --wait api`), веб-часть пересобрать, когда порт свободен
(`dc up -d --build --wait web`), иначе в интерфейсе не будет управления агентами и метки «ИИ»;
при ручном запуске — сначала `gostracker bootstrap`, потом API.

Чек-лист владельца перед обновлением рабочего стека (функция `dc` и правило `-p <имя>` — как в
ADR-0013, «Команды чек-листа»):
1. Сделать резервную копию БД (команда 1) в отдельный файл на каждый стек, вне клона; тома
   `pgdata` и `appdata` не удалять и не пересоздавать. Проверить, что файл не пуст (`ls -l`).
2. Обновить: `dc up -d --build --wait`.
3. Проверить (команда 2): версия схемы `0008`, агентов и ключей пока нет, вход ТА работает. На
   стенде выполнить ручные проверки web из чек-листа приёмки (`nginx -t`, передача
   `Authorization`).
4. Откат — команда 4 (только если без него нельзя: теряются ключи и признак агента).

**Команды чек-листа.** Выполняются в каталоге клона; определение функции `dc`:
```bash
dc() { docker compose "$@"; }
# stack under another Compose name: define instead
# dc() { docker compose -p <имя> "$@"; }
```

Команда 1, резервная копия (до обновления, схема `0007`; дамп содержит хеши паролей — в
репозиторий не класть):
```bash
dc exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > ~/<имя-стека>-006.dump
ls -l ~/<имя-стека>-006.dump
```

Команда 2, проверка после обновления:
```bash
dc exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT version_num FROM alembic_version;
SELECT count(*) FILTER (WHERE is_agent) AS agents FROM app_user;
SELECT count(*) AS api_keys FROM api_key;
SQL
```
Ожидается `0008`, `agents = 0`, `api_keys = 0` (сразу после обновления).

Команда 3, размер журнала событий (периодически; рост — см. «Последствия»):
```bash
dc exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT pg_size_pretty(pg_total_relation_size('domain_event')) AS domain_event_size;
SELECT action, count(*) FROM domain_event GROUP BY action ORDER BY count(*) DESC;
SQL
```

Команда 4, откат `downgrade 0007` (образом этой версии; `api` остановлен, `db` работает).
Перед откатом выпишите агентов и их ключи — после отката признак «агент» не восстановить:
```bash
dc exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT u.login_display, u.is_blocked, k.name, k.expires_at, k.revoked_at
FROM app_user u LEFT JOIN api_key k ON k.user_id = u.id
WHERE u.is_agent ORDER BY u.login, k.created_at;
SQL
dc stop api
dc run --rm --no-deps --entrypoint alembic api downgrade 0007
```
После отката запускайте образ версии 006 (`dc up -d --build --wait` в клоне, переключённом на
версию 006). Образ версии 007 (этой) при старте снова выполнит `0008`; ключи и признак агента
при этом не вернутся. Бывшие учётные записи агентов заблокируйте (пароля у них нет, но ТА мог бы
его сбросить). Восстановление копии из команды 1 возвращает данные на момент копии; готовой
команды восстановления здесь нет — она разрушает данные стека (см. ADR-0013, «Откат»).
