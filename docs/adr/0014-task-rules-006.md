# ADR-0014. Приоритеты «Низкий/Средний/Высокий» и обязательные поля задачи (баг-репорт Ч1)

- **Дата:** 2026-10-21
- **Статус:** принято (решения владельца по `specs/006-bugreport-ch1/spec.md`: Q-1 а), Q-2 б), 2026-10-20)
- **Уточняет:** ADR-0007 (срок задачи)
- **Связано:** `specs/006-bugreport-ch1/spec.md` (FR-8…FR-11, FR-15…FR-17, FR-23, D-1, D-5);
  `specs/006-bugreport-ch1/plan.md` (PD-5, PD-20); `docs/data-model.md`

## Контекст
Владелец прислал баг-репорт Ч1 (пп. 1–8). Часть замечаний меняет правила и контракт API задач:
приоритет «Обычный/Высокий» заменяется на «Низкий/Средний/Высокий» (п. 2), а исполнитель, срок и
описание становятся обязательными при создании задачи (пп. 3–5). Эти изменения несовместимы со
старыми запросами: `AGENTS.md` требует записывать ломающие изменения API в `docs/adr/`.

## Решение
- **Коды приоритета** в API и БД: `low`, `medium`, `high`. Прежний код `base` не принимается
  (422 `validation_error`) ни при создании, ни при изменении. Новая задача и подзадача без
  приоритета получают `medium`.
- **Миграция 0007** (`backend/migrations/versions/0007_three_priorities.py`): `base` → `medium`,
  `high` остаётся `high` (в том числе у мягко удалённых задач); `CHECK` `ck_task_priority_valid`
  пересоздаётся на три значения. Всё в одной транзакции.
- **Создание задачи** (не подзадачи): описание (хотя бы один непробельный символ), срок и
  исполнитель обязательны. Срок не раньше «сегодня» по Europe/Moscow. Исполнитель не передан →
  создатель (для любой роли). Явный `null` исполнителя у БА → 422. Подзадачи остаются
  «быстрыми»: достаточно названия.
- **Изменение задачи** (FR-23, `PATCH`): для задач верхнего уровня нельзя снять исполнителя или
  срок, сделать описание пустым и поставить срок раньше «сегодня»; проверяются только реально
  меняемые поля, старые данные без срока или исполнителя не мигрируются и не мешают правке
  других полей. Для подзадач изменение прежнее.
- **Ошибки:** срок в прошлом — отдельный код `due_date_in_past` (422); отсутствие и пустота
  обязательных полей — общий `validation_error`.

## Причины
Задача без исполнителя не видна в «Моих задачах», без срока её нельзя спланировать, без
описания непонятно, что делать. Код `medium` совпадает со смыслом «Среднего». Срок в прошлом
может появиться на границе суток уже после проверки в форме, поэтому интерфейсу нужен
отдельный код для сообщения у поля срока.

## Альтернативы и почему отвергнуты
- **Оставить `base` как код «Среднего» (псевдоним) и добавить `low`.** Отвергнуто: код расходится
  со смыслом, два кода для одного значения усложняют проверки и документы. Внешних клиентов API
  нет, интерфейс и API обновляются вместе (D-1).
- **Общий `validation_error` и для срока в прошлом.** Отвергнуто: интерфейс проверяет
  обязательность сам, а срок в прошлом возможен только на границе суток; по общему коду нельзя
  показать правильное сообщение у нужного поля (D-5).

## Последствия
- **Ломающие изменения API:** `base` отклоняется; `POST /api/v1/projects/{id}/tasks` без
  описания, срока или с пустыми значениями — 422; `PATCH /api/v1/tasks/{id}` с обнулением
  исполнителя, срока, описания — 422. Внешних клиентов API нет (D-1), совместимость не
  сохраняется; интерфейс, демо-данные и тесты обновляются вместе с API.
- **Откат миграции:** `low` и `medium` → `base`, `high` без изменений; различие «Низкий/Средний»
  при откате теряется, откат работает всегда. Повторное обновление после отката даёт `medium`
  вместо `low` и `medium`.
- **Существующие данные:** задачи без исполнителя, срока или с пустым описанием остаются как
  есть и показываются «Без исполнителя», «Нет срока», «Описание не указано».
- **Документы:** `docs/data-model.md`, `docs/acceptance/mvp-demo.md` обновлены; в `specs/001-pilot-r1/spec.md`
  и `specs/004-no-board-create/spec.md` правки по таблицам 9.1 и 9.2 spec 006 вносятся отдельной задачей (R6-T16).
