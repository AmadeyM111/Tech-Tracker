# ADR-0022. Облачные MCP-клиенты: OAuth 2.1 на /mcp (вариант B; с 2026-11-12 — без шлюза)

- **Дата:** 2026-11-08
- **Статус:** принято (решение владельца 2026-11-08, вариант B; уточнено 2026-11-12: «ставим» — подключение ChatGPT и других облачных клиентов через OAuth на `/mcp`). Реализация — спека 028.
- **Связано:** отменяет запрет ADR-0018 п. 5 для облачных клиентов, и только через шлюз; п. 1–4 и 6–7 ADR-0018 не меняются.
  NFR-3 (трекер не делает исходящих запросов ради шлюза); ADR-0004 (сессии без изменений); ADR-0006 (аудит);
  ADR-0013 (роли). Правило ТЗ §2 и `AGENTS.md` (внешние адреса в пилоте) меняет владелец; агент эти файлы не правит.
  ADR-0019 — не связано (регистрация, ветка `feat/self-registration`). Черновик облачного шлюза, который назывался
  ADR-0019 (файл вне репозитория), перенумерован в 0022. Номер 0020 занят в `feat/r1.0-foundation`, 0021 зарезервирован под спеку 023.
- **Спека:** `specs/028-mcp-oauth/` (T-14, черновик 2026-11-12). Без утверждения спеки реализацию не начинать.

## Решение
Облачные клиенты (GPT, Claude, GigaChat, DeepSeek) подключаются к трекеру через **шлюз в DMZ**. Трекер остаётся закрытым.

1. **Наружу выходит только MCP.** Шлюз в DMZ принимает по HTTPS (TLS 1.2 и выше) только `/mcp`; всё остальное
   на шлюзе отклоняется. Внутренние адреса трекера (`/api/v1`, веб-интерфейс, база данных) наружу не открываются.
2. **Шлюз пересылает вызовы** на внутренний адрес трекера. Трекер не делает исходящих запросов ради шлюза (NFR-3).
3. **Аутентификация облачных клиентов — OAuth 2.1 (authorization code + PKCE)**, как в T-14 F2. Токен привязан
   к пользователю, срок — не больше 90 дней, клиент виден в ленте отдельной меткой (ADR-0018 п. 6).
   Права токена — права владельца, набор инструментов — тот же, что у локальных клиентов (ADR-0018 п. 1 и п. 7).
4. **Отзыв.** Отзыв токена и блокировка учётной записи отзывают все токены, включая облачные (ADR-0018 п. 3).
   Выпуск и отзыв пишутся в аудит (ADR-0006) вместе с IP-адресом и именем клиента.
5. **Локальные клиенты** (Claude Code, Codex CLI, Cursor) остаются на персональных токенах ADR-0018 и на
   `gtrack mcp` без изменений.
6. **Ограничения шлюза.** Список провайдеров по IP-диапазонам, обновляемый оператором. Публичный вход отключается
   одной переменной конфигурации. Проверка заголовков `Host` и `Origin` (защита от DNS rebinding), ограничение частоты запросов.
7. **Данные.** Передача данных проекта облачной модели разрешена решением владельца 2026-11-08, как и публичный адрес.
   Уходит то, что пользователь видит через MCP; больше ничего.

## Поправка 2026-11-12 (решение владельца: «ставим»; спека 028)
Прод уже имеет публичный адрес с TLS (Caddy → nginx → api), а ChatGPT обращается к `/mcp` без токена и требует
«завершить авторизацию». Поэтому:
- **Шлюз в DMZ (п. 1, 2, 6 выше) в этой поставке не строится.** Облачные клиенты ходят на тот же публичный `/mcp`; наружу
  дополнительно выходят только пути OAuth (спека 028, раздел «Маршрутизация»). Решение о шлюзе остаётся в силе как будущий
  вариант усиления (отдельный ADR), если ИБ его потребует.
- **Authorization server — свой, минимальный, внутри api** (authorization code + PKCE S256, динамическая регистрация клиентов
  RFC 7591, метаданные RFC 8414 и RFC 9728, `resource` по RFC 8707). Закрыт открытый пункт «своя реализация или внешний провайдер».
  Внешний провайдер OIDC отвергнут: у пилота нет такого провайдера, а пользователи и сессии уже в трекере.
- **Токены облачных клиентов** — непрозрачные, в БД только хеш: access-токен короткий (1 час), refresh-токен с ротацией
  (срок и потолок — спека 028, Q-4; верхний предел 90 дней из п. 3 сохраняется). Права — права пользователя, набор
  инструментов — тот же, что у `gtrk_`. Отзыв — в разделе «Доступ для агентов» вместе с `gtrk_`; блокировка учётной записи
  отключает и их (п. 4).
- **Аудит** выдачи и отзыва — как у `gtrk_` (ADR-0018 п. 3); IP-адрес в журнал аудита не пишется (только в журнал доступа приложения).
- **Данные.** Разрешение владельца на передачу данных облачной модели (п. 7) действует; протокол ИБ по провайдерам (открытый
  пункт ниже) — отдельный процесс и разработку не блокирует.
- Открытые пункты «Спека T-14 не написана», «Реализация OAuth», «Проверка провайдеров» закрыты спекой 028 (требования ChatGPT
  и Claude.ai проверены по официальной документации, ссылки — в спеке); «Threat model» — раздел 7 спеки 028; «Эксплуатация
  шлюза» снимается вместе со шлюзом.

## Причины
- Решение владельца 2026-11-08: облачные модели нужны; данные облачной модели — разрешены; публичный адрес — разрешён.
  Выбран вариант B.
- Шлюз в DMZ отделяет публичный вход от трекера: наружу выходит один путь `/mcp`, а не весь API.
- ADR-0018 п. 5 сам требовал отдельного ADR для облачных клиентов; этот документ и есть такой ADR.

## Альтернативы и почему отвергнуты
- **Открыть трекер наружу напрямую.** Публичными станут весь API и веб-интерфейс. Отвергнуто.
- **Туннель к localhost.** Ранее отвергнут в ADR-0018 (конфликт с ТЗ §2 и `AGENTS.md`); здесь тоже не используется.
- **Персональный токен (`gtrk_`) вместо OAuth для облачных клиентов.** Пользовательские коннекторы облачных моделей
  обычно требуют OAuth, а простой bearer-токен в их интерфейсе не настраивается. Это сведения из открытых источников
  от 2026-11-08; их нужно проверить по документации каждого провайдера. Для облачных клиентов OAuth, для локальных — токены.
- Другие варианты шлюза в этом ADR не разбираются: выбран вариант B.

## Последствия
- ADR-0018 п. 5 отменяется для шлюза. Текст ADR-0018 не редактируется: решение сохраняется в истории.
- Появляется внешний контур: шлюз в DMZ — отдельный компонент. Где он живёт, кто его эксплуатирует — вне трекера.
- Спека 020 («Вне рамок»: OAuth) меняется дельта-спекой, а не правкой `020`.
- Правила ТЗ §2 и `AGENTS.md` меняет владелец.
- Реальные данные в облачные клиенты — только после протокола ИБ (R2-42, Q-4 задачного списка).
- Миграций ADR не требует.

## Открытые пункты
Пункты ниже открыты. Решение «принято» от них не зависит, но T-14 без них не стартует.
- **Протокол ИБ** с перечнем провайдеров (GPT, Claude, GigaChat, DeepSeek) и юрисдикций, куда уходят данные. Не готов.
  До его утверждения реальные данные в облачные клиенты не передаются.
- **Спека T-14 не написана.** Пока её нет, реализация не начинается.
- **Реализация OAuth:** свой минимальный authorization server в бэкенде или внешний провайдер по OIDC.
  Свой сервер — больше кода под проверку безопасностью.
- **Проверка провайдеров** до спеки: remote MCP по URL у каждого провайдера, требует ли каждый OAuth, диапазоны IP,
  GigaCode по STDIO на нашей версии.
- **Threat model** публичного эндпоинта `/mcp` до внедрения.
- **Эксплуатация шлюза:** хост, сертификат, ответственный оператор.
- **Приоритет T-14** в R2 (этап 3) — решение владельца.
