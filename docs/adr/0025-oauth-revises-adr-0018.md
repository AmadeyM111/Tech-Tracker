# ADR-0025. Пересмотр ADR-0018 в части OAuth: облачные клиенты подключаются через OAuth 2.1 на /mcp

- **Дата:** 2026-11-12
- **Статус:** принято (решение владельца 2026-11-12: «ставим»; ChatGPT и другие облачные клиенты)
- **Пересматривает:** ADR-0018 — пункт «Альтернативы: OAuth 2.1 для MCP» (отвергнут как избыточный для localhost-пилота) и пункт «Публичный адрес для ChatGPT через туннель» (отложен), а также п. 5 решения (облачные клиенты не поддерживаются). Остальные пункты ADR-0018 (п. 1–4, 6–7: персональные токены `gtrk_`, права владельца, отзыв по блокировке, лента, набор инструментов) **остаются в силе**.
- **Связано:** ADR-0022 (облачные клиенты, вариант B, поправка 2026-11-12), спека `specs/028-mcp-oauth/`, ADR-0004 (сессии), ADR-0006 (аудит), ADR-0013 (роли).
- **Текст ADR-0018 не редактируется:** в его шапку добавлена только ссылка на этот ADR (статус «частично пересмотрен»), чтобы решение и причины пересмотра были видны с обеих сторон.

## Решение
Для облачных клиентов (ChatGPT, Claude.ai и других, соблюдающих спецификацию MCP) вводится OAuth 2.1 (authorization code + PKCE) на публичном `/mcp`; authorization server — внутри api (ADR-0022, поправка). Локальные клиенты (Claude Code, Codex CLI, Cursor) остаются на персональных токенах `gtrk_` и на `gtrack mcp` без изменений. Права облачного клиента равны правам пользователя, выдавшего согласие; отзыв и блокировка действуют так же, как у `gtrk_`.

## Причины (почему вывод ADR-0018 больше не верен)
- ADR-0018 исходил из «пилот на localhost»: внешних вызовов нет, OAuth не окупается. Условия изменились: у пилота публичный адрес с TLS, владелец решил подключать облачные клиенты и разрешил передачу данных облачной модели (ADR-0022, решение 2026-11-08).
- Облачный клиент не может ввести персональный токен: ChatGPT при обращении к `/mcp` без токена требует «завершить авторизацию» (по документации OpenAI не поддерживаются пользовательские API-ключи; ссылки — в спеке 028, §2). Ответ 401 на такие запросы мы уже видим в журнале.
- Туннель к localhost (отвергнутый вариант) не нужен: публичный адрес есть, правила ТЗ §2 о внешних адресах для него снимаются решением владельца, а не обходом.

## Альтернативы и почему отвергнуты
- Оставить ADR-0018 как есть и не подключать облачные клиенты — противоречит решению владельца.
- Выдавать облачному клиенту `gtrk_` — клиент не умеет его вводить; токен в чате облачной модели хуже OAuth (виден модели).
- Внешний провайдер OIDC — нет такого провайдера; пользователи и сессии уже в трекере (ADR-0022, поправка).

## Последствия
Появляется поверхность OAuth на публичном адресе (модель угроз — спека 028, §7); `PUBLIC_BASE_URL` становится обязательным для OAuth; в nginx добавляются маршруты `/.well-known/oauth-*`; одна аддитивная миграция (`0014_mcp_oauth`, согласуется отдельно). Реальные данные в облачные клиенты — после протокола ИБ по провайдерам (ADR-0022).
