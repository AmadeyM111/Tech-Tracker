# ADR-0013. Три роли: роль «Смешанная» упразднена

- **Дата:** 2026-10-16
- **Статус:** принято (владелец продукта, 2026-10-16)
- **Заменяет:** ADR-0003 (роль «Смешанная» и самоназначение ролей)
- **Уточняет:** ADR-0004, ADR-0005, ADR-0006, ADR-0009, ADR-0012
- **Связано:** ТЗ §4 (`docs/brief/vision.md`); `specs/002-three-roles/spec.md` (FR-1…FR-22, NFR-5,
  раздел 5.3, решения владельца Q-1…Q-6); `specs/002-three-roles/plan.md` (§4.5, §4.10, §8 R-9);
  `specs/001-pilot-r1/spec.md` (OI-13, OI-57, OI-120, OI-127, FR-41, FR-66, FR-69)

## Решение
В системе остаются ровно три роли: техадминистратор (ТА, `tech_admin`), бизнес-администратор
(БА, `business_admin`) и пользователь (П, `user`), плюс состояние «без роли». Роль «Смешанная»
(`mixed`) упразднена. Её системные права (настройки, учётные записи, роли, журнал аудита)
принадлежат только ТА, её права на проекты — БА. ТА по-прежнему не имеет доступа к
бизнес-данным (проектам, задачам, комментариям). При обновлении системы миграция `0006`
снимает роль `mixed` у всех пользователей, пишет в журнал аудита по одной записи на каждого
бывшего пользователя с ролью «Смешанная» (СМ) от автора «система» и сужает ограничение
`role_valid` до трёх значений. Если после снятия ролей в пространстве не остаётся активного ТА,
роль ТА вместо снятия получают все активные бывшие СМ (FR-16).

## Отличия действующей матрицы от ТЗ §4
Перечень по разделу 5.3 spec 002. Действующая матрица прав — раздел 5.2 той же спецификации.

1. **Колонка «Смешанная» удалена** — отступление от ТЗ §4: в ТЗ у роли есть своя колонка
   матрицы, в системе роли нет (решение владельца (1)).
2. **БА удаляет любой проект** вместо «только свой» в ТЗ §4 — отступление от ТЗ §4
   (решение владельца (4), подтверждено ответом на Q-2). Это права бывшей смешанной роли,
   которые перешли к БА.
3. **Толкование строк ТЗ для БА** — не отступление от ТЗ, а изменение ранее принятого
   толкования:
   - «свой проект» в строке «Изменение чужой задачи в своём проекте» для БА — проект, где он
     участник, а не где он владелец. Это отменяет OI-120, OI-127 и толкование «свой проект =
     где владелец» (001/FR-19, ADR-0012);
   - «Добавление участников в проект — да» действует для БА буквально: добавление и
     исключение участников в любом проекте, включая себя. Это отменяет сужение ADR-0009 п.1
     («БА-не владелец не добавляет») и OI-13, OI-57. Такое право соответствует ТЗ §4
     буквально.

Строка ТЗ §4 «Чтение задач чужих проектов — нет» для БА действует без исключений: БА, не
участвующий в проекте, не читает его задачи, подзадачи и комментарии (FR-10). Доступ к
содержимому даёт только участие, а добавить себя в проект БА может сам (см. «Риски»).

## Правила, которые фиксирует решение

### Несколько ТА, признака «первичный» нет (Q-1)
ТА в пространстве может быть сколько угодно. «Первичный ТА назначает роль ТА другим» из
запроса владельца означает: роль ТА назначает любой активный ТА. Особого статуса у ТА первого
запуска нет. Назначение, смена и снятие роли, в том числе себе, пишутся в журнал аудита по
001/FR-41 без изменений (ADR-0006).

### Последний администратор и параллельные действия (FR-7)
Правило ADR-0009 п.5 «последний администратор не может заблокировать себя или снять с себя
роль» применяется к ТА. «Активный ТА» — незаблокированный пользователь с ролью ТА; несменённый
одноразовый пароль этому не мешает.
- Если у инициатора нет другого активного ТА, действия над собой (снять роль, сменить на БА
  или П, заблокироваться) отклоняются с 422 `last_account_admin`; данные и журнал не меняются.
- Если другой активный ТА есть, те же действия выполняются.
- Действие над другим ТА допустимо, если в момент выполнения инициатор сам активный ТА. Если
  параллельный запрос лишил его роли или заблокировал, запрос получает 403 (или 401, если
  сессия уже завершена).
- Параллельные запросы дают результат, равный какому-либо последовательному порядку: если до
  них был активный ТА, он есть и после. Проигравший запрос может получить 503 `service_busy`
  с заголовком `Retry-After`; данные и журнал по нему не меняются.

Реализация: действия с учётными записями идут под advisory-блокировкой пространства и
блокировкой строк «активные ТА ∪ цель», проверка «остаётся хотя бы один активный ТА»
выполняется до фиксации (plan 002 §4.4).

### Замена владельца проекта любым БА
Владельцем проекта может быть только участник с ролью БА (422 по 001/FR-70 в иных случаях).
Если владелец заблокирован или не имеет роли БА (в том числе после снятия роли `mixed` или
замены её на ТА по FR-16), нового владельца назначает любой БА, даже если сам не участвует в
проекте. БА может назначить владельцем себя, если он участник проекта. Правило «ТА выдаёт
роль СМ бизнес-сотруднику, а не себе» (ADR-0009 п.4) отменено. Порядок действий оператора:
если в пространстве нет активного БА, ТА назначает роль БА бизнес-сотруднику; система этого
не проверяет. Передача владения пишется в журнал аудита без изменений.

## Обновление существующих данных (миграция 0006)

### Снятие роли и запись в журнал от «системы»
Миграция `backend/migrations/versions/0006_three_roles.py` выполняется в одной транзакции:
- роль `mixed` у каждого пользователя (заблокированного или нет) заменяется на `NULL` («без
  роли»), кроме случая FR-16;
- на каждого бывшего СМ добавляется ровно одна запись журнала, такая же, как при ручном
  действии (`user.role_removed` или `user.role_changed`, `details.role_from = mixed`,
  `details.role_to`), с `actor_id = NULL` (автор «система»), `in_audit = true`;
- `ck_workspace_member_role_valid` пересоздаётся с тремя значениями.

Это **первое обновление схемы, которое пишет в журнал аудита**: миграции `0001`–`0005`
журнал не меняли. Правило 001/FR-41 «автоматические действия первого запуска в журнал не
пишутся» остаётся в силе, на чистой установке журнал пуст. Если пользователей с ролью `mixed`
нет, записей не добавляется. Журнал только дописывается; прежние записи с ролью `mixed`
остаются, в интерфейсе она показывается как «Смешанная роль» (Q-6).

Не меняются: владение проектами, членство, исполнители, авторство, логин, пароль, признаки
блокировки и одноразового пароля, серверные сессии (FR-14). Бывший СМ без роли может войти,
выйти и сменить пароль; остальные запросы получают 403 (001/FR-66, FR-67). Задачи бывших СМ
находит и переназначает БА.

### FR-16: обновление не оставляет систему без администратора (Q-3)
Если после снятия ролей в пространстве нет ни одного активного ТА, роль ТА получают все
активные (незаблокированные) бывшие СМ, каждый с записью `user.role_changed` от «системы».
Заблокированные бывшие СМ и в этом случае становятся «без роли». Если активный ТА остался,
роль снимается у всех. Последствия для получивших роль ТА (допустимы по 001/FR-68):
- они теряют доступ к проектам, задачам и комментариям: 403 (ТЗ §4, 001/BR-2);
- они остаются владельцами проектов, участниками и исполнителями, кем были; это единственный
  способ, которым ТА оказывается владельцем, участником или исполнителем (новые назначения ТА
  по-прежнему отклоняются, 001/FR-70);
- владельца из их числа заменяет любой БА, задачи переназначает БА-участник;
- роль ТА с них может снять или сменить любой активный ТА (FR-6, FR-7).

### Откат
- `alembic downgrade 0005` возвращает прежний `CHECK` с четырьмя значениями, но **роль `mixed`
  не возвращает** и журнал не меняет. Бывшие СМ после него остаются без роли (или с ролью ТА по
  FR-16); роли им возвращает ТА вручную по записям журнала (`role_from = mixed`). Выполнять
  `downgrade` нужно образом 002: в образе 001 нет ревизии `0006`.
- Восстановление резервной копии 001 возвращает роли вместе со всеми данными на момент копии
  (изменения после копии теряются). Запускать на восстановленной БД нужно образ 001
  (`dc up -d --build` в клоне, переключённом на версию 001; функция `dc` с `-p <имя>` — см.
  «Команды чек-листа»): образ 002 при старте снова выполнит `0006` и снимет роли.
- Образ 001 не стартует на схеме `0006`: в нём нет этой ревизии, его `gostracker bootstrap`
  падает на `alembic upgrade head`, а контейнер `api` при `set -e` не поднимается. Для запуска
  001 на этой БД сначала нужен `downgrade 0005` образом 002 или восстановление копии 001.
- Автоматического восстановления ролей нет (spec 002, раздел 7).

Команда отката — «Команда 4» в блоке «Команды чек-листа» раздела «Порядок обновления».

## Причины
- Решение владельца продукта (2026-10-16): три роли, ТА — чисто системная роль, по
  разделению обязанностей из ТЗ §4. ADR-0003 оставлял обход этого разделения (самоназначение
  «Смешанной»); теперь системные права и бизнес-данные не совмещаются в одной учётной записи.
- Права на проекты, которые были у СМ, нужны бизнес-стороне: БА получает их без системных
  прав (Q-2).
- Явное правило «активный ТА» и защита от параллельных гонок нужны, пока ТА может быть
  несколько и каждый может менять роль другого.
- Запись в журнал от «системы» сохраняет аудит ролей, который ADR-0006 ввёл ради
  самоназначения: пропавшая роль не должна исчезнуть бесследно.
- Отступление от ТЗ §4 допускается только новым ADR (001, C-6; spec 002, NFR-5).

## Альтернативы и почему отвергнуты
- **Оставить роль «Смешанная»** (ADR-0003): противоречит решению владельца и сохраняет
  совмещение системных прав и бизнес-данных.
- **Оставить БА «только свой проект» (владелец) и запрет добавлять себя**: владелец отменил
  OI-13, OI-57, OI-120, OI-127 (Q-2); прежнее толкование расходилось с ТЗ §4 буквально.
- **ТА с признаком «первичный»** или особые права ТА первого запуска: владелец выбрал
  «первичный = любой активный ТА» (Q-1); отдельный признак усложнял бы правило последнего
  администратора.
- **Запретить ТА менять свою роль** или требовать подтверждения вторым ТА: вне рамок, хватает
  правила последнего администратора (FR-7) и аудита.
- **Не назначать никого при обновлении**: система могла остаться без администратора учётных
  записей. Решение владельца (Q-3): все активные бывшие СМ получают роль ТА.
- **Назначить ТА только одному бывшему СМ** (первому или по алфавиту): произвольный выбор;
  владелец выбрал всех активных.
- **Назначить бывшим СМ роль БА**: бывший СМ получил бы доступ к бизнес-данным без решения
  владельца; автоматическое назначение, кроме FR-16, вне рамок.
- **Снимать роль ручным SQL оператора**: нарушает NFR-2 (обычное обновление версии) и не
  оставляет записи в журнале.
- **Не писать в журнал при обновлении**: владелец потребовал запись (решение (2)); без неё
  нельзя восстановить роли при откате.
- **Аудит добавления БА себя в проект**: не принят в этой фиче (Q-5), см. «Риски».

## Последствия
- Код: в `Role` и API три значения; `mixed` в запросах отклоняется с 422 (FR-18); набор
  возможностей БА расширен (`project_manage_any`); права читаются из БД на каждый запрос, поэтому
  сессии бывших СМ получают новые права сразу.
- Схема БД: `role_valid` допускает три значения; применение миграции `0006` обязательно для
  кода 002 (см. «Порядок обновления»).
- Демо-данные: вместо `demo.mixed` добавлен БА `demo.ba4`, 12 демо-пользователей сохраняются
  (Q-4).
- Тексты ADR-0003 (статус: заменено), ADR-0004, ADR-0006, ADR-0012 помечены ссылкой на этот
  ADR, исторический текст не менялся. ADR-0005 и ADR-0009 уточняются этим ADR; где в них
  упоминается СМ, действуют правила этого ADR.
- Модель данных: `docs/data-model.md` описывает три роли и миграцию `0006`.

## Риски
- **Q-5: добавление БА себя в проект не аудируется.** Любой БА может, добавив себя в проект,
  читать и менять задачи любого проекта, а изменение состава участников проекта в R1 в журнал
  аудита не пишется (журнал содержит учётные записи, роли и передачу владения). Решение
  владельца: в этой фиче не аудируется; вернуться к вопросу перед корпоративным внедрением.
- **Активный ТА без бизнес-данных, но владелец проекта.** После FR-16 ТА может остаться
  владельцем проекта, к которому у него нет доступа; проект остаётся управляемым через любого
  БА.

## Порядок обновления
Код 002 требует схему `0006` и не должен работать на схеме ≤ 0005 с пользователем, у которого
роль `mixed`: в коде 002 такого значения нет, и любой запрос, затрагивающий этого пользователя
(вход, `/me`, учётные записи, участники проекта, назначение исполнителя), даёт ошибку
значения и ответ 500. ТА при этом не может исправить роль через API.

В поставке этого окна нет. Порядок обеспечивает `backend/docker-entrypoint.sh`:
1. `gostracker bootstrap`: advisory-блокировка, `alembic upgrade head` (миграция `0006`),
   `run_bootstrap` (ключ, первый ТА);
2. `exec uvicorn`: API запускается только после успешного шага 1.

Если миграция падает, команда завершается ненулевым кодом и API не стартует; транзакция
откатывается целиком (версия остаётся `0005`, роли и журнал прежние, FR-17), повторный запуск
после устранения причины безопасен и даёт тот же результат.

Правила:
- обновлять рабочий стек только командой `dc up -d --build --wait` (функция `dc` с `-p <имя>`
  этого стека, см. «Команды чек-листа» ниже), одним выпуском (код 002 вместе с миграцией);
  промежуточные образы без `0006` не собирать и не разворачивать на БД с данными 001;
- при ручном запуске сначала `gostracker bootstrap`, потом API; `uvicorn` без `bootstrap` на
  БД с данными 001 не запускать;
- после восстановления БД из резервной копии 001 (схема ≤ 0005) при работе на коде 002
  перезапустить сервис `api` командой `dc restart api` (функция `dc` с `-p <имя>` — см.
  «Команды чек-листа» ниже): миграция `0006` выполнится при старте и снова снимет роль `mixed`.
  Чтобы остаться на 001, запускать на такой БД образ 001 (`dc up -d --build` в клоне,
  переключённом на версию 001; см. «Откат»).

Остаточный риск: при ручном запуске миграции на работающем API миграция берёт сильные
блокировки на `workspace_member` и `app_user` и ждёт их без ограничения (`lock_timeout = 0`),
а новые запросы API встают в очередь за ней; через 30 с (`lock_timeout` сервера `db`) они
получают 503 `service_busy`. Если PostgreSQL прервёт миграцию, она откатывается целиком
(FR-17). Штатный путь (контейнер `api` с `docker-entrypoint.sh`) запускает миграцию до
`uvicorn`, поэтому живого API при миграции нет.

Чек-лист владельца перед обновлением рабочего стека. Команды — ниже, в блоке «Команды
чек-листа». До пункта 1 определите там функцию `dc` и выберите проект Compose (`-p <имя>`):
если из одного клона запущено несколько стеков, команда без нужного `-p` затронет не тот стек.
1. Сделать резервную копию БД (команда 1); тома `pgdata` и `appdata` не удалять и не
   пересоздавать. Проверить, что файл не пуст.
2. Выписать пользователей с ролью `mixed` и активных ТА (`is_blocked = f`; команда 2): так видно,
   кто станет «без роли», а кто получит роль ТА по FR-16 (если активных ТА нет).
3. Обновлять только командой `dc up -d --build --wait`, одним выпуском (определение `dc` и
   правило `-p <имя>` — в «Командах чек-листа» ниже).
4. Проверить после обновления (команда 3): версия схемы `0006` (`alembic_version`); на каждого
   бывшего СМ есть запись журнала `user.role_removed` или `user.role_changed` с автором
   «система» (`actor_id IS NULL`); в столбце `role_now` у них `NULL` или `tech_admin`; вход ТА
   работает.
5. Откат: см. подраздел «Откат»; роли `mixed` он не возвращает.

**Команды чек-листа.** Выполняются в каталоге клона. Сервис `db` и переменные `POSTGRES_USER`,
`POSTGRES_DB` (по умолчанию `tracker`) заданы в `docker-compose.yml` и `.env.example` и читаются
внутри контейнера `db`; флаг `-T` отключает TTY и нужен для перенаправления stdin/stdout: `psql`
читает запросы из stdin, а двоичный вывод `pg_dump` уходит в файл. Имя проекта Compose по
умолчанию — имя каталога клона. Если стек запущен под другим именем Compose
(`COMPOSE_PROJECT_NAME` или `-p`), добавляйте `-p <имя>` ко всем командам, включая `stop` и
`run` (README, «Быстрый старт»); имя видно в `docker compose ls`. Чтобы не повторять ключ,
ниже все команды вызывают функцию `dc`; определите её один раз в текущем окне терминала
(работает в bash и zsh):
```bash
dc() { docker compose "$@"; }
# стек под другим именем Compose: вместо строки выше определите
# dc() { docker compose -p <имя> "$@"; }
```
Дамп пишется вне клона (`~/gostracker-001.dump`): в нём хеши паролей, и в репозиторий он
попасть не должен.

Команда 1, резервная копия (пока схема ≤ `0005`):
```bash
dc exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > ~/gostracker-001.dump
ls -l ~/gostracker-001.dump
```

Команда 2, бывшие СМ и ТА до обновления:
```bash
dc exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT u.login_display, m.role, u.is_blocked
FROM workspace_member m JOIN app_user u ON u.id = m.user_id
WHERE m.role IN ('mixed', 'tech_admin') ORDER BY m.role, u.login;
SQL
```

Команда 3, проверка после обновления (версия схемы и записи от «системы»):
```bash
dc exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT version_num FROM alembic_version;
SELECT d.id, u.login_display, d.action, d.details->>'role_from' AS role_from,
       d.details->>'role_to' AS role_to, m.role AS role_now
FROM domain_event d
JOIN app_user u ON u.id = d.entity_id
LEFT JOIN workspace_member m ON m.user_id = d.entity_id AND m.workspace_id = d.workspace_id
WHERE d.actor_id IS NULL AND d.in_audit
  AND d.action IN ('user.role_removed', 'user.role_changed')
ORDER BY d.id;
SQL
```

Команда 4, `downgrade 0005` (образом 002; `api` остановлен, `db` работает):
```bash
dc stop api
dc run --rm --no-deps --entrypoint alembic api downgrade 0005
```
После неё можно собрать и запустить образ 001 той же функцией `dc` (`dc up -d --build` в клоне,
переключённом на версию 001), а ТА вернёт роли по записям журнала. Запуск образа 002
(`dc up -d --build --wait`) снова выполнит `0006`. Восстановление копии 001 возвращает роли на
момент копии; перед ним `api` должен быть остановлен (`dc stop api`), а `pg_restore` в БД стека
нужно выполнять с `--clean --if-exists` (либо восстанавливать в пересозданную пустую БД);
запускать после него нужно образ 001 (`dc up -d --build` в клоне, переключённом на версию 001).
Готовой команды восстановления здесь нет: она разрушает данные стека, поэтому оператор
выполняет её осознанно.

## Не принято в этой фиче
Необязательная проверка при старте API, что в БД нет ролей вне набора `Role` (падать сразу,
а не отдавать 500). Мера добавила бы защиту от запуска кода 002 на схеме ≤ 0005, но в план не
включена: это решение владельца, отдельное от настоящего ADR.
