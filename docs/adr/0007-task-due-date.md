# ADR-0007. Срок задачи — календарная дата

- **Дата:** 2026-10-13
- **Статус:** принято
- **Связано:** ТЗ §3 («Время»); `specs/001-pilot-r1/spec.md` (OI-15, OI-61, OI-62, OI-94,
  FR-18, FR-27a, FR-46, NFR-5, BR-12, AC-60, AC-68); `specs/001-pilot-r1/consensus-2026-10-13.md`
  (З-2); `docs/open-questions.md` (вопрос 10)

## Решение
Срок задачи — календарная дата без времени и часового пояса в формате `YYYY-MM-DD`, в БД
и в API. Это явное исключение из правила ТЗ §3 «в БД и API только UTC, ISO 8601» и из
требования spec FR-46. «Сегодня», «завтра», «просрочено» и другие фильтры по сроку
считаются по календарной дате в часовом поясе Europe/Moscow. В R1 часовой пояс —
константа, он не настраивается.

## Причины
- Срок задачи по смыслу — день, а не момент времени: «сдать 20 октября».
- Если хранить дату как полночь UTC, при отображении в Europe/Moscow и при расчёте
  «просрочено» возможен сдвиг на сутки. Это тот класс ошибок, от которого ТЗ §3 хотело
  уйти правилом UTC.
- ТЗ §3 задаёт отображение в Europe/Moscow. Единая константа даёт однозначный ответ на
  вопрос «что сегодня».

## Альтернативы и почему отвергнуты
- **Дата-время в UTC:** пользователь вводит день, а системе приходится выбирать время
  суток; появляется сдвиг на сутки на границе.
- **Настраиваемый часовой пояс пространства:** в R1 одно пространство и одна команда;
  настройка ничего не проверяет в пилоте.

## Последствия
- В API поле срока имеет формат даты, а не даты-времени. Значение с временем или
  несуществующая дата отклоняются с 422.
- Все прочие даты-время (создание, изменение, история, лента, аудит) остаются в UTC.
- Расчёт «сегодня» на сервере использует Europe/Moscow. Тесты фиксируют часы и проверяют
  границу суток (spec AC-68).
- В правило «Время» в `AGENTS.md` добавлено исключение для срока задачи со ссылкой на этот
  ADR.
